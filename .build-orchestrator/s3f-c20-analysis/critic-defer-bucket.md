# critic:defer-bucket

Read-only analysis for ruling S3-R26 (workflow wf_bc7908d4-1ad, on 8e1fb24). UNCONFIRMED marks what the agent read but did not run.

## verdict

sound with amendments

## refutations

- R1. Refutes the claim that the side table changes no answer; reachability UNCONFIRMED. (1) While the verdict's own replay runs, the after-replay put-back keeps the bucket out of eventsAfterFollow. The drain takes the whole batch off the queue before replaying it (EngineFollow.swift:199-201), so followBarrier (:97-99) reads false inside V's replay whenever the rest of the queue fits in V's batch. Today, a bucket that runs past the 512-event boundary leaves its later joins in the queue, and the barrier stays up during V's replay. (2) The reader that changes is checkRunSettled (EngineRuns.swift:576). V's replay reaches it through resolveAll (EngineJobs.swift:627), retryLater (EngineFailures.swift:268) and decideSpaceFailure (:610). (3) With the barrier down, the orphan pass (EngineRuns.swift:650-660) counts as failed `.cancelled`, and may settle the run on, a run claim whose join waits in the bucket. The visit's reroute has already moved that claim to the verdict's transfer (EngineDispatch.swift:1184), while T's job does not hold the run's interest; the bucket join is later dropped by stillWants (EngineFollow.swift:724). In visit-first the claim was still on its old job when V arrived, so it is never orphaned. (4) The run's admittedBySpace sweep (EngineRuns.swift:646, which reaches judgeSpaceSweep through EngineJobs.swift:773-781) is likewise judged inside V's replay instead of after the joins. (5) The same exposure exists today, but only when the whole queue fits one batch; the design extends it to buckets of any size. (6) Reachability needs a transferring run whose claim a later apply moves onto a job whose verdict waits. The ensure path applies a fetched manifest whatever the run's phase (EngineCommands.swift:719-723), so this looks plausible, but no probe exists.

## amendments

- A1 (preferred; resolves R1 and the new turn boundary). (1) At EngineFollow.swift:192-201, the batch formation, materialize the buckets instead of putting them back after the replay. While scanning the batch's prefix, splice each waiting verdict's bucket into eventsAfterFollow and eventStamps at the verdict's index + 1, newest first, and remove its key from the side table, before `count` is computed. Then form and replay the batch with today's code unchanged. (2) This reproduces today's queue exactly from the moment the drain reaches V. It keeps every batch boundary: the 512-event cap, endsDrainBatch, drainIDsLeft and followMoving (:211-215). It keeps RR-21's re-insert of `(left, stamp)` ahead of `batch[(offset+1)...]` (design-minimal.md step 12), so there is no three-part prepend to write. It keeps today's barrier state inside V's replay. (3) It removes the after-replay put-back and the extra batch end. (4) The cost is one O(E + bucket) splice per bucketed verdict entering a batch. The number of buckets is bounded by the attempts in flight behind the barrier, since the pump starts nothing while the barrier is up (EngineDispatch.swift:95). (5) K1-K4, followedLane, withdrawPurgedJoins and the recount still cover the buckets the drain has not reached yet.
- A2 (only if the after-replay put-back is kept). (1) Change EngineFollow.swift:97-99 to `self.followOwed || !self.state.eventsAfterFollow.isEmpty || !self.state.joinsBehindVerdicts.isEmpty`. At turn boundaries this changes nothing, because K1 means a non-empty bucket's verdict waits in the queue. Inside V's replay it keeps EngineRuns.swift:576 returning early for every bucket size. (2) Trade-off: in shapes where the whole queue fits one batch, today's barrier is down inside V's replay, and a run-settle check there would now move to the drain's tail (EngineFollow.swift:227). (3) Write the head re-insert as one ordered prepend, `[(left, stamp)]` (RR-21), then the bucket newest first with its stamps, then `batch[(offset+1)...]`, and not as separate `insert(at: 0)` calls, whose order decides the result.
- A3 (failing test first, P3). (2) Run it with a bucket of 1 and the queue fitting one batch (today's exposure), and with a bucket of 600 or more (the widened case). (3) Assert that a is answered as in visit-first (fetched or `.notFound`, never `.cancelled` or missing) and that both invariant functions are clean. (4) If the 1-join case already fails on today's code, fix the root in checkRunSettled. Either add `!self.state.drainingAfterFollow` to the guard at EngineRuns.swift:576, since the drain's last batch re-checks at EngineFollow.swift:227. Or have the orphan filter at :650 keep claims whose join waits (`joinsAfterFollow[current.token]?[asset] == transfer`), mirroring the acceptance at EngineCommands.swift:1812-1815.
- A4 (K2 recount). In followBarrierViolations' loop (EngineCommands.swift:2016-2030), walk each verdict's bucket, newest first, at that verdict's position, not after the loop. The recount keeps the last join it meets for each (token, asset) (`joins[join.token, default: [:]][join.asset] = …`, :2025). Walked after the loop, a bucket join would override a later queue join for the same pair, which today's order does not. This is an edge case and probably unreachable (UNCONFIRMED).
- A5 (G4 placement pins). (1) Extend T1 with an event whose replay order changes an answer, placed after V in V's batch, for example a `.conditions` element as in EngineFollowBarrierUnlistedTests.swift:64-77. (2) Add a white-box readForTests check of the queue head after V's turn. Together they kill the mutants that put the bucket behind the batch's rest or at the queue's tail. (3) Once RR-21 has merged, add a case where V leaves a `.reroutes` rest and also has a bucket, which kills a mutant that puts the bucket ahead of `.reroutes`. (4) The newest-first order itself needs no pin: it is order only by S3-R16 item 3 (EngineFollow.swift:958-961).

## checked_claims

- The deferral call site is unique. deferBehindVerdict is called only from addInterest's branch (EngineJobs.swift:117-123), which requires inFollowVisit and not bringingInbound. That limits it to visit (EngineFollow.swift:802-813) or continueVisitRemainder (:820-847) under withReading, where worldStamp returns the reading (:250-253). So a stamp stored in the bucket equals today's (:977). CONFIRMED.
- (transfer, epoch) is unique per attempt. lastEpoch is bumped at job creation (EngineJobs.swift:137) and at start (EngineDispatch.swift:697-698). So the VerdictKey names the same `.attemptFailed` or `.spaceFailure` event that today's lastIndex finds (EngineFollow.swift:965-972). CONFIRMED.
- Every non-empty bucket has its verdict waiting. defersFailure records the deferral and queues the event in one turn (EngineFollow.swift:463-466). Only the drain (:200), drainEverything (EngineShutdown.swift:118) and the unspawnable branch (:393) remove events; a purge only marks joins withdrawn (EngineCommands.swift:1071). Today's `verdict ?? events.count - 1` fallback is reachable only if the verdict and unfailed clauses (EngineCommands.swift:2043-2054) are broken. CONFIRMED, so K1 is sound.
- No bucket grows during a drain batch. defersToFollow is false while draining (EngineFollow.swift:104). The drain's visits run either with bringingInbound set (:825) or outside inFollowVisit (followAfterVerdict, :586-593). CONFIRMED.
- Order. Today each deferral goes in at lastIndex(V) + 1, newest first; every other deferral is appended at the tail (EngineFollow.swift:234). A put-back at the head, newest first, ahead of the batch's rest therefore equals today's order. The order among the joins behind one verdict is order only (doc at :958-961, S3-R16 item 3). CONFIRMED.
- The design extends every non-replay consumer of `.join` events. Those events are read only by replay (EngineFollow.swift:359), withdrawPurgedJoins (EngineCommands.swift:1054), the invariant recount (:2022) and followedLane (EngineFailures.swift:823). CONFIRMED.
- followedLane does not depend on position. Its loop (EngineFailures.swift:821-836) takes the maximum lane; its break is only an early exit at `.userInitiated`, and its withdrawn set ignores position (:845-863). CONFIRMED.
- The joinsAfterFollow-based acceptances (EngineCommands.swift:1707-1712, :1777-1783, :1812-1815) still hold, because the registration at :975 is kept. CONFIRMED.
- Shutdown loses no answer. drainEverything answers every waiter and group whatever the queue holds (EngineShutdown.swift:50-140), so clearing the table there drops nothing. CONFIRMED.
- The unspawnable branch (EngineFollow.swift:390-399) is unreachable: it has 0 hits (s3f-probes-c20/correct/logs/covdiff.log). So the head order `.reroutes`, bucket, rest equals today's. Owed items are interests taken off T; bucket joins are interests moved onto T while elsewhere. They cannot share an interest, so step 15's one-place clause holds. No conflict, provided the prepend is one ordered insert.

## c2_concerns

- Follow turns that defer, users shape (UNCONFIRMED). Each moved id still pays the move bookkeeping: removeAsset, reroute (with releaseRunClaim or a waiter update) and dropInterest. Measured users-shape follow turns are 7.18-8.01 ms (userSharedApplyTurns, s3f.md:4849) and 9.29-9.50 ms (PARTIAL-MOVE users=true; 10.10 ms with TSan on the host, s3f-c20-issues.json:97). So the design's 2-5 ms estimate is likely low and the margin to 10 ms is about 2 ms; it needs a figure.
- The put-back or splice turn (UNCONFIRMED). Copying 10,000 JoinAfterFollow values, each holding a ManifestEntry with string retains, into the queue head costs an estimated 1-3 ms. It lands on top of V's replay, which drainVerdictTurns puts at 4.08-4.13 ms (s3f.md:4851). Under A1 the same turn may also replay up to 511 joins. It should still fit c2Budget, but it must be measured in the users shape.
- Purges and 429s are not a new risk. withdrawPurgedJoins and followedLane each make one O(bucket) pass per purge or 429, the same order as today's queue walks.

## g4_concerns

- No listed test (T1, T1-skip, T-PG, T-FL, T-FL', T-SD, F-K1, F-K3, F-SPACE, F-K4) kills a put-back placed behind the batch's rest or at the queue's tail. T1's queue is V plus its bucket, so head and tail coincide. Needed: an event in V's batch after V whose replay order changes an answer, such as a `.conditions` element, plus a white-box check of the queue head after V's turn.
- With RR-21, no listed test kills a mutant that puts the bucket ahead of the `.reroutes` rest. That needs a verdict that leaves both owed reroutes and a bucket.
- No test covers a run-kind bucket (T-RUN in A3), so R1's settle-check difference goes unobserved.
- The bucket branches are reached only in `.sweepFollowsFirst`; visit-first runs never call deferBehindVerdict (EngineFollowBarrierTests.swift:97-108). The design should state this so the both-orders convention is not read as coverage.
- F-SPACE alone leaves the `.attemptFailed` put-back mutant alive; T1 kills it. This needs no change, only care when the mutant tally is assessed.

## residual_risks

- A new drain-turn boundary after each bucketed verdict, if the after-replay put-back is kept (UNCONFIRMED). (1) Today that boundary exists only where the 512-event cap, an endsDrainBatch event or drainIDsLeft falls. (2) Inputs the barrier does not defer, chiefly a later apply's follow, can then run between V and its joins. replayJoin's reroute covers the endpoint (EngineFollow.swift:704-707). (3) But T can lose its last interest meanwhile and be removed. The join then recreates T with attempts 0 and no backoff, where today and visit-first keep attempts and backoff, which can change the answer at the retry cap. (4) S3-R16 counts this as timing unless a probe shows a changed answer. A1 removes it.
- Pre-existing, out of scope, UNCONFIRMED: a rerouted run claim is lost. (1) resolveAll delivers to the run, and recordRunOutcome then sets `run.outstanding[T] = nil` (EngineRuns.swift:519). (2) That wipes a claim a visit had rerouted onto T (EngineDispatch.swift:1184) while its join waits behind T's verdict, whenever T's job holds the run's interest for another id with the same content. (3) The join is then dropped by stillWants (EngineFollow.swift:724), and the id is neither fetched nor failed; visit-first joins it to a new T job. (4) Today's code and the design behave the same here.
- Pre-existing, out of scope, UNCONFIRMED: orphaned run claims in a whole-queue batch. Run joins can be deferred behind the barrier: materializeRun runs before pump's barrier check (EngineDispatch.swift:93; EngineRuns.swift:495-499, then the deferral at EngineJobs.swift:110-115). A verdict replayed before them in a batch that holds the whole queue can then orphan their claims through the same checkRunSettled pass. A3's root fix would close this too.
- Pre-existing, UNCONFIRMED: the drain's followAfterVerdict joins at once, with inFollowVisit false (EngineFollow.swift:586-593 and the guard at EngineJobs.swift:117), onto a job whose own verdict waits later in the queue. That verdict then answers the id; visit-first's would not when the apply came after that verdict arrived.
- Pre-existing and accepted: the joins behind one verdict replay newest first, the reverse of visit-first's visit order. S3-R16 item 3 classes this as order only (EngineFollow.swift:958-961), and the design keeps it.
