## Contract changes and authorised edits outside WP-C's write set
- **R1 / CCR-2 (merge-gating, approved):** orphan GC versus `apply` adoption of a launch orphan. WP-B's `adoptKnownBlob` binds a launch orphan only while `state.core.orphans[key]` still equals the confirmation the plan saw; the orphan entry is cleared in the turn that dooms it (done inside `doomOrphans`, so the §1.1 rule-1 exemption was not needed). The former `withKnownIssue` test now asserts I-2.
- **R2 / CCR-1 (approved):** package primitive `StoreInternals.doomOrphans(_:) -> [BlobKey]` (additive): orphan GC dooms `.unreferenced` with the listed size, eligible after the deletion grace, so the reaper unlinks under I-3 and a publication or adoption rescues it. C-13 was not extended to it (it would need a place-without-records primitive).
- **R3 / OI-1 (WP-B bug, fix approved):** `ApplyPlan` no longer lists `absent(.evicted)` records and `adoptKnownBlob` refuses them, so neither `apply` nor `admit` can undo an eviction; only the launch adoption may re-adopt.
- **R4 (C2):** every cleanup path holds the store actor ≤ 10 ms at 10,000 records (measured in the new `Tests/ZTronAssetKitBenchmarks/BenchCleanup.swift`, OI-7 — add it to ARCHITECTURE §1.2's benchmark files for WP-C). Residual linear stretches at maxEntries (100,000) are recorded with measurements in c.md (C-22): they are **assigned to Stage 3 hardening**, not a Level 3 blocker (SPEC's reference scale is 10,000).
- **Authorised test edits outside WP-C:** WP-A's `R-MAN-3` heap-measurement tests (OI-8 and its sibling) were made deterministic on the iOS Simulator without weakening their bounds; WP-D's 500-download loopback test got a request timeout its queue can meet under load (OI-10); WP-B Core tests where B-16 seams had real APIs (four files). Ratified.
- Any further package/internal additions the ledger finds in WP-B files (e.g. `holders(of:known:)`) are ratified if c.md justifies them; list them in ADR-051.

- **R6 / CCR-3 (approved, cycle 7):** WP-B passes `apply`'s eviction plan to the hook in chunks of `AssetStore.evictionChunk` records cut at blob boundaries, behind the write fence, yielding and re-validating between chunks, so the hook holds the actor ≤ 10 ms at 10,000 records for a whole-store plan (measured 13.9–20.4 ms before).
- **R7 (cycle 7):** a quarantine that lands during a maintenance eviction counts toward that eviction's released bytes (proven over-eviction, probe ZP6-overlap-quarantine).
- **R8 (accepted exception → Stage 3 hardening):** evicting or purging one blob shared by more than ~6,500 records still exceeds 10 ms in one turn (15.4 ms for 10,000 holders); chunking one blob's holders is assigned to Stage 3.
- **R9 (docs):** legacy migration phase 3 may need several calls under access stamps (`finished: false`); ARCHITECTURE RE-S29 and §4.7 must say the caller (WP-F) calls `migrateLegacy` again while `!progress.finished`, backing off when `remaining == 0 && !finished`.

- **OI-15 (decided at merge):** ruling R3 stays literal for Level 3 — an evicted record is re-adopted only by the launch adoption, so an evicted record whose new content is already live in another blob is downloaded again by the engine. This costs a redundant download in a rare case, never correctness; narrowing R3 (let `apply` bind an evicted record to a different, already-live key) is assigned to Stage 3 hardening.
- **Final close-out state:** cycles 1–8; the cycle-8 verification found 0 blocking issues in both lenses (18 non-blocking, all recorded or routed). Merged as 38d23f9.

## Deviations — NEEDS-HUMAN-REVIEW (R5)
From SPEC R-STO-11 / store.md §7 (legacy migration): **C-12** checksum-less legacy files that have no local checksum are dropped and downloaded again instead of hashed inside `open()`; **C-13** an undecodable legacy manifest degrades the launch and adopts nothing (its files are not kept as protected orphans); **C-14** a legacy root on another volume is dropped (no store copy primitive for EXDEV); **C-15** phase 4 keeps files it cannot attribute and a non-empty root (R-STO-11 says "remove the legacy directory"). **C-14 cycle-2 amendment (legacy deferral bound)** a legacy file that fails to read or move 3 times in one lifetime is abandoned for good (counted dropped, its asset downloaded again, the file left in the legacy root unattributed) — the bound is per lifetime with no backoff, so an ENOSPC streak or EIO burst can exhaust it; a lifetime-based bound would need a persisted per-file count (a CCR). Also accepted without review tag: **C-6** eviction does not rank Apple-adopted assets after ordinary ones (records carry no tier; would need an index-format change), **C-2** eviction's budget counts pending reclaim while `FreeSpace.budgetBytes` (WP-B) does not, **C-4** `lastCleanupAt` is stamped only by a cleanup run that changed something.
