> Generated by `Tests/Fixtures/generate_fixtures.py`; do not edit by hand. Re-running the generator reproduces every file byte for byte (`python3 Tests/Fixtures/generate_fixtures.py --check` verifies the tree on disk, recomputes every checksum and byteSize, and fails on any drift).

Tests locate this directory through `#filePath`; nothing here is a SwiftPM resource. The prior art shipped no example manifests (`docs/RECON.md` section 1), so these are synthetic, but every checksum is the real SHA-256 of a real payload file in `payloads/`, so the series can drive a fake CDN end to end. ## 1. Conventions

- **Wire shapes (R-MAN-1).** `v1.json` .. `v4-removal.json` are the *legacy bare JSON array* and contain exactly the seven legacy keys `identifier`, `fileExtension`, `remotePath`, `localPathComponents`, `localFileName`, `byteSize`, `checksum` and nothing else. `localPathComponents` is present on every entry (the legacy decoder required it). `localFileName` is **omitted** (not `null`) where the manifest has no opinion, in which case the derived name (last dot-segment of the identifier) applies; `byteSize` and `checksum` are present on every entry of the series. `v1.envelope.json` is the envelope shape `{"schemaVersion": 1, "assets": [...]}` (section 4).
- **Entry order** is identical in every file of a series (v1 order, with removed entries dropped); array order carries no meaning for classification.
- **Checksums.** `checksum` is the full lowercase hex SHA-256 of the payload file; `byteSize` is its length. Both are recomputable from `payloads/`.
- **AWS tier** `remotePath = media/<sha256[:16]>/<identifier>.<ext>` (SPEC 2.3). A content change therefore changes `remotePath`; a directory change never does.
- **Apple tier** `remotePath = ZTronMedia/<kind>/<identifier>.<ext>` where `<kind>` is one of `images` (heic, png, jpg), `vectors` (svg), `video` (mp4), `audio` (wav, mp3). The `remotePath` is `<packID>/<path inside pack>`; the catalog lives in the essential pack `ZTronCatalog`, the media in the on-demand pack `ZTronMedia`. The path carries no hash, so for the two content changes of v2 the file name gains a `.v2` marker (`.../<identifier>.v2.<ext>`); that lets **one** fake pack directory serve every version of the series.
- **Identifier lists** in this document and in `expectations.json` are sorted ascending by UTF-8 bytes.
- **Classification** follows R-MAN-4: `contentChanged` = checksum differs (takes precedence); `metadataChanged` = same checksum but `remotePath`, directory (`localPathComponents`), file name (`localFileName`), tags or policy differ; an absent `policy` equals `standard` and absent `tags` equal `[]`; `unchanged` = none of those; `added` / `removed` = identifier only in the newer / older manifest. Every identifier lands in exactly one class.
- **The dedupe pair.** `bo7.ri.character.keeper.portrait` and `bo7.ri.character.keeper.card` are two different identifiers whose entries reference the **same payload bytes** (identical `checksum` and `byteSize`, different `remotePath` file names). They exist to exercise content-addressed deduplication and reference counting; neither is touched by any transition or by the envelope extension fields.

### 3.2 What changes between versions

- **v1 -> v2 `v2-checksum-change.json`** - exactly **2** assets get new payload bytes: `bo7.ri.easter.egg.vehytherion.temple.icon` and `bo7.ri.ambience.crypt`. For each: `checksum`, `byteSize` (icon only; the crypt variant keeps 2,044), and `remotePath` change; nothing else. AWS: the `<sha256[:16]>` directory changes. Apple: the file name gains `.v2`. All other 11 entries are byte-identical to v1.
- **v2 -> v3 `v3-directory-change.json`** - exactly **3** assets change only `localPathComponents` and/or `localFileName`; `checksum`, `byteSize` and `remotePath` stay the same (no download is needed): `bo7.ri.easter.egg.vehytherion.temple.outline` (directory only, one component appended), `bo7.ri.music.main.theme` (file name only; the `localFileName` key appears), `bo7.menu.background` (directory and file name). All other 10 entries are identical to v2.
- **v3 -> v4 `v4-removal.json`** - exactly **2** assets are removed: `bo6.tm.easter.egg.control.room.outline` and `waw.ndu.round.start.sting`. The remaining 11 entries are identical to v3. (The shared payload files stay in `payloads/` and the Apple pack: the fake pack serves every version.)

The v2 and v3 change sets, and the v4 removal set, are pairwise disjoint, and none of them contains the dedupe pair.

## 5. Negative fixtures (`manifests/invalid/`)

One file per violation, named after it. Per-entry files are bare arrays of three entries: a valid entry, the violating entry (index 1) and a valid entry, so a test can assert that *only* the violating entry is quarantined and the other two survive (R-MAN-2). The violating entry is a copy of an otherwise valid asset with exactly one field changed. Whole-manifest rejections (`manifestRejected`) must produce a typed error and **never crash** or hang. `expectations.json` (`invalid`) carries the same data in machine-readable form.
