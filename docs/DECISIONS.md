## ADR-001 — Storage location · **NEEDS-HUMAN-REVIEW**
- **Context.** Promise 1 ("no mid-use waiting") cannot hold if the OS may silently purge essential assets. The prior art used `Library/Caches/CDNAssets` with the sync stamp in `UserDefaults` (D-6).
- **Options.** (a) `Caches/` — OS-purgeable, no backup cost, no module-owned eviction needed. (b) `Application Support/` excluded from backup, module-owned quota/eviction. (c) `Documents/` — visible in Files, backed up.
- **Decision.** (b) by default: `Application Support/ZTronAssetKit/v1/`, `isExcludedFromBackup = true`, file protection `completeUntilFirstUserAuthentication`. `StorageLocation.caches` and `.custom(URL)` remain selectable (R-STO-10).
- **Consequences.** The module must own eviction (R-CLN-4) and OS-purge recovery still matters for `.caches` (R-CLN-7). Storage is not reclaimed by the OS under pressure — the budget and `purge` API are the user's levers.

## ADR-002 — On-disk layout and index format · **NEEDS-HUMAN-REVIEW**
- **Context.** D-10: a pretty-path layout makes a directory change a set of non-atomic moves; D-14: manifest text became path components.
- **Options.** (a) Keep pretty paths. (b) Content-addressed blobs + one atomically replaced index (SPEC §4.3). (c) SQLite.
- **Decision.** (b). `blobs/<aa>/<sha256>.<ext>`, `staging/<uuid>.part|.resume`, `store.lock`, and `index.bin`: a compact, versioned binary format (magic, `schemaVersion`, `generation`, length-prefixed records, SHA-256 trailer to detect torn writes) replaced via write-temp → `F_FULLFSYNC` → rename. Final details are fixed in `ARCHITECTURE.md` (Stage 1). SQLite is rejected: a dependency-free binary index meets P-2 and keeps crash enumeration (R-STO-5) tractable through the `FileSystem` seam.
- **Consequences.** Directory changes are index edits; identical bytes dedupe; the index is rebuildable from blob names + the last manifest. Legacy files are adopted by hash (R-STO-11). Debugging needs a dump tool rather than `cat` (provided via `diagnosticReport()`).

## ADR-003 — Blocking work off the cooperative pool
- **Context.** C2 / §4.2: hashing, copying and directory enumeration must not block a cooperative-pool thread for more than ~10 ms. At an iOS 15 floor there is no `Mutex`, `OSAllocatedUnfairLock` or custom executors.
- **Options.** (a) Dedicated GCD queue(s) bridged with `withCheckedThrowingContinuation` + `withTaskCancellationHandler`. (b) Chunked work on the pool with `Task.yield()` between chunks.
- **Decision.** (a) for anything that touches the file system: production code never performs a blocking file-system call directly from an async context; it submits *bounded* units (one rename, one ≤ 1 MiB read, one index commit) to an injected blocking-I/O executor — a dedicated `DispatchQueue` in `.live()`, bridged with `withCheckedThrowingContinuation`. Long operations (hashing 256 MiB, enumerating 10,000 blobs) are decomposed into such units with `Task.checkCancellation()` between them, so cancellation needs no shared mutable flag (no lock, no `@unchecked`). CPU-only work on ≤ 1 MiB (one SHA-256 update, < 1 ms) may run inline. (b) is used for pure in-memory work (diff/plan over 10,000 entries), yielding periodically. Stage 1 fixes the exact interfaces in `ARCHITECTURE.md`.
- **Consequences.** P-9 (heartbeat gap) and P-6 (≥ 0.7× one-shot hash throughput despite the hops) prove it. Tests inject an executor that runs inline so they stay deterministic.

## ADR-004 — Typed throws
- **Context.** R-ENV-6 (SHOULD). Typed throws are a compile-time feature; concrete error types back-deploy.
- **Decision.** Public async APIs throw `AssetError` concretely (`throws(AssetError)`) wherever the compiler accepts it at the iOS 15 floor; APIs that run caller-supplied throwing closures (`withAsset`) stay untyped. Internal layers use their own closed error types (`ManifestError`, `TransferError`, `StoreError`) mapped once at the facade.
- **Consequences.** Callers can switch exhaustively over `AssetError` (R-CAR-7).

## ADR-012 — Layout deviations from SPEC §4.3 · **NEEDS-HUMAN-REVIEW**
- **Context.** SPEC §4.3 recommends `store.lock`, `index.bin`, `blobs/<aa>/<sha256>.<ext>`, `staging/<uuid>.part|.resume`. Crash safety (H-1) and recovery need more (store.md §2).
- **Options.** (a) SPEC layout verbatim (one index file, UUID staging names). (b) SPEC layout plus a previous generation and a transient temp file, a persisted doomed set, and deterministic staging names. (c) A write-ahead log.
- **Decision.** (b). Under `<base>/ZTronAssetKit/v1/`: `store.lock`; `index.bin` (current), `index.prev` (previous generation, a fallback against single-file corruption), `index.tmp` (transient); `blobs/<aa>/<64 hex>.<ext>`; `staging/<TransferID>.<epoch>-<sequence>.<kind>` (ADR-013). The index is the binary format of store.md §2.3 with these amendments: DOOMED entries carry a `DoomReason` (ADR-018); the header records the launch epoch; every header field is range-checked before arithmetic (store-1 S1-04). Every file is listed in `ARCHITECTURE.md` §3.
- **Consequences.** Two extra index names and one header field to document and fixture (R-STO-12 golden fixtures per schema). Load cost stays far inside P-2 (three candidates read: about 2× of 2.8 ms measured).
- **Amendment (contract-fix round 4).** STAMPS has no `lastMaintenanceAt`: store.md §2.3 listed it, but nothing read it and no API the engine reaches could set it, so `CleanupState.lastMaintenanceAt` was removed rather than persisted as an always-absent field (ADR-046 amendment). The schema is not shipped; `schemaVersion` stays 1.

## ADR-013 — Staging names are `<TransferID>.<epoch>-<sequence>.<kind>` · **NEEDS-HUMAN-REVIEW**
- **Context.** SPEC §4.3 says `staging/<uuid>`. transport.md proposed `<TransferID>.part` (deterministic, self-describing at relaunch). transport-1 TR1-1 and transport-2 T2-02 showed that one name per content lets two producers write the same path while the store hashes it; T2-06 showed per-process attempt numbers are not comparable across launches.
- **Options.** (a) UUIDs from the seeded random source. (b) `<TransferID>.part`. (c) `<TransferID>.<epoch>-<sequence>.<kind>`, with `epoch` = the store's launch epoch (the index generation allocated at `open()`, persisted, strictly increasing) and `sequence` an engine counter.
- **Decision.** (c), implemented by `StagingFileName` and `TransferAttempt` (Model). Kinds: `part`, `parttmp`, `resume` (our own JSON `ResumeSidecar`), `resumetmp`, `verifying` (claimed by the store for publication, store-1 S1-12). No manifest text in any name (R-SEC-2); no randomness (C4); unique per start; self-describing at relaunch (H-6). Every rename into or out of staging is exclusive (`RENAME_EXCL`): an `EEXIST` is a uniqueness bug, never a replace.
- **Consequences.** A resumed attempt first moves the previous attempt's partial to its own name (`StagingSink.continuePartial`). Staging GC parses names; anything that does not parse is foreign and collected (R-CLN-3).

## ADR-014 — Test fakes and availability
- **Context.** The unsafe gate scans all of `Sources/`, `ZTronAssetTestSupport` included (≤ 3 escapes in total; target 0). Fakes with synchronous APIs (`FileSystem`, `TimeSource`, `LegacyDefaults`, `LogTap`, transfer handles) need a lock. `Mutex` is iOS 18 / macOS 15. The reviewer of the Stage 1 contracts verified with the compiler that `@available` on a `@Suite` is rejected ("Attribute 'Suite' cannot be applied to this structure because it has been marked @available…"), and so is a `@Test` inside such a suite.
- **Options.** (a) `@unchecked Sendable` lock boxes (burns the escape budget). (b) Actor fakes only (impossible for synchronous protocol requirements). (c) Actors where the protocol is async; `Mutex` fakes behind `@available(macOS 15.0, iOS 18.0, *)` elsewhere, gated **per `@Test` function**. (d) An unannotated factory funnel with `#available` + `preconditionFailure`.
- **Decision.** (c). Async-protocol fakes are actors and ungated (`FakeDeviceConditionsSource`, `FakeMemoryPressureSource`, `SteppedBlockingExecutor`, `ScriptedSnapshotSink`). `ManualTimeSource`, `FakeFileSystem`, `FakeLegacyDefaults`, `RecordingLogTap`, `FakeTransferHandle`, `FakeRemoteSource`, `FakeTransferBackend`, `FakeStagingSink` are gated `@available(macOS 15.0, iOS 18.0, *)`. Tests that use them carry **single-platform** `@available(macOS 15.0, *)` on each `@Test` function, never on a `@Suite`. Verified in round 1: `SyncContractTests` and `AppleHostedContractTests` build and pass that way; `ZTronAssetTestSupport` typechecks at `arm64-apple-ios15.0` with zero diagnostics. **(d) is rejected** (contract-fix round 2): its `#available` would be a second one under `Sources/`, and the R-APL-5 scan (`R-APL-5: the package contains exactly one #available`) covers **all** of `Sources/`, `ZTronAssetTestSupport` included. A cast to an ungated protocol (`StagingAttachable`, ADR-045) is the pattern when ungated code must reach a gated fake.
- **Consequences.** Test hosts need macOS 15+ (this host is macOS 27). Production floors are unchanged (ADR-005). Zero escapes in `ZTronAssetTestSupport`; exactly one `#available` in `Sources/` (`AppleHostedTier.resolve`).

## ADR-015 — Index commit durability and directory barriers
- **Context.** store.md D1 and its proposed "two-level durability" ADR. store-1 S1-01 (state built on a namespace a killed process never synced), S1-02 (the root's own entry in `<base>` never synced), S1-07 (ENOSPC livelock), S1-14 (`F_FULLFSYNC` 4×/s), S1-15 (`fsync` fallback masks EIO).
- **Decision.** Ordered commits sync `index.tmp` with `F_BARRIERFSYNC` and the root with a barrier; durable commits (`flush`, `close`, migration "done", before an Apple pack release) use `F_FULLFSYNC` on the file, the root, `ZTronAssetKit` and `<base>`. After creating `ZTronAssetKit` the store barrier-syncs `<base>` (and any ancestor it created). `open()` marks `blobs/` dirty and barrier-syncs the root before any launch deletion; every adoption (launch, `apply`, migration) dirties its fan-out. On ENOSPC at commit step 2 the unit removes `index.tmp` and `index.prev` and retries once; `open()` never fails because a post-load commit failed (read-only `degradedReadOnly`). The sync fallback to `fsync` applies only to ENOTSUP/EINVAL/ENOTTY. `FakeFileSystem`'s `processKill` keeps the current/durable split, and R-STO-5 enumerates kill→power-loss pairs across two lifetimes.
- **Consequences.** One extra barrier per launch and per adopted fan-out (≈ 0.37 ms each); P-5 keeps its margin because ordered commits no longer `F_FULLFSYNC`.

## ADR-016 — Snapshot acknowledgement and URL holders
- **Context.** H-2/I-3 rest on "the mirror installed a snapshot without the blob". store-2 S2-02: an ignored install still returned, and a reopened store restarted versions; S2-12: engine-held snapshot copies hand out URLs no acknowledgement covers; S2-13: allocation points unspecified; sync-2 S2-12: releasing a large snapshot on main costs milliseconds.
- **Decision.** `SnapshotKey(epoch, version)`, `epoch` = launch epoch, `version` allocated synchronously when the snapshot is built. `SnapshotSink.install` returns `InstallAck { installed, accesses, retired }`; the store counts an acknowledgement only when `installed.epoch == myEpoch`; the mirror swaps only for a greater key and has an explicit `reset()`; the replaced snapshot is handed back in `retired` and released off the main actor. `AssetSnapshot` is `package`; only the mirror derives URLs from it; the engine resolves through `AssetStore.location(for:extensions:recordingAccess:)` (current actor state).
- **Consequences.** Implemented in `Sources/ZTronAssetStorage/Snapshot/AssetSnapshot.swift` and `Sources/ZTronAssetKit/Mirror/SnapshotMirror.swift`; tested (`R-STO-13: the mirror ignores an out-of-order snapshot and acknowledges what readers see`).
- **Amendment (contract-fix round 3): install rate.** The store is the only caller of `install`, so it owns the ≤ 10 Hz rule of sync-2 S2-12. `publish(_:binding:expecting:urgency: AssetPriority)`: `.userInitiated` installs before returning; `.prefetch` and `.bulk` install at most once per `StoreConfiguration.snapshotInstallInterval` (from `SyncTuning.snapshotInstallInterval`, default 0.1 s, clamped ≥ 0), the trailing install being a store deadline (`nextDeadline()`, `runDueWork()`, `StoreWorkReport.installedSnapshot`; ADR-022). Options considered: an `installSnapshotNow()` call (rejected: one more await on every user publish, and the lane is known at the call) and rate-limiting everything (rejected: delays the page the user just opened). Consequence: O(N) snapshot builds and main-actor hops fall from one per commit to ≤ 10 per second during a bulk sync; returned locations come from actor state, so a coalesced install never delays a `resolve`. Regression test `R-STO-13: bulk publishes install at most one snapshot per snapshotInstallInterval and a user-initiated publish installs at once` (WP-B).

## ADR-017 — Deletion grace, the awake clock and the reaper · **NEEDS-HUMAN-REVIEW** (consumer contract)
- **Context.** store.md D4. store-1 S1-13 and store-2 S2-03: the reaper busy-loops when a key is past its deadline but blocked by a lease, a missing ack or a lagging commit. store-2 S2-14: `UIImage(contentsOfFile:)` reloads purged data from the path, and `CLOCK_MONOTONIC` keeps counting while the device sleeps, so a suspended app loses its grace.
- **Decision.** A blob is deleted only when: an acknowledged snapshot of the store's epoch lacks it; `deletionGrace` (default 10 s) has passed on the **awake clock** (`TimeSource.uptimeNow()`, `CLOCK_UPTIME_RAW`); the generation that dropped it is committed; no lease holds it; no publication of the key is in flight; and one fresh no-op install after the deadline proved the main actor ran. There is no reaper loop: `AssetStore.nextDeadline()` reports a deadline only for keys whose sole remaining blocker is time, and lease release, acknowledgement and commit completion re-arm the engine's alarm (ADR-022). Public contract, on `AssetLocation`: a URL stays readable for at least `deletionGrace` of awake time after the snapshot without it is installed and for the whole of a lease; consumers that may re-read a path later load through `Data` or hold a lease (`withAsset`).
- **Consequences.** `TimeSource` gained `uptimeNow()`; `ManualTimeSource.sleepDevice(for:)` models device sleep. The R-CAR-6 adoption guidance must tell the carousel to load images through `Data` or a lease.

## ADR-018 — Blob reference discipline and doom reasons
- **Context.** store-2 S2-01 (concurrent publications corrupt `refCount`), S2-04 (a committed generation with `DOOMED ∋ k` and a present reference to `k`), store-1 S1-03 (a power loss resurrects a purged or quarantined blob that launch adoption re-binds as verified), S1-05 (dedupe, rescue, checksum-less publishes and retried `apply` re-download after a kill), S1-06 (a wrong-bytes blob reused forever), S1-11 (degraded fallback deletes the older generation's DOOMED keys).
- **Decision.** One operation gains a reference (`acquireReference`): it awaits an in-flight publication (`publishing: [BlobKey: Task]`) or deletion of the same key, rescues `doomed(.unreferenced)`, increments `live`. Every table update after an await is read-modify-write. `DOOMED` is derived from the blob table at commit capture, never maintained separately; at load the store repairs `DOOMED \ referenced` and counts it (`StoreMetrics.doomedRepairs`). Doom reasons: `unreferenced` (adoptable, rescuable), `purged` and `corrupt` (never re-adopted, never rescued; a verified publish replaces a corrupt name with `rename(.replacing)`). Launch adoption iterates records and binds only `absent(neverFetched|evicted|healing)`, `needsHeal` and stale records. `apply` adopts before it dereferences. Checksum-less and rescue publishes are committed before they return. In degraded mode DOOMED keys are protected like orphans.
- **Consequences.** Implemented by WP-B/C against `DoomReason`, `Residency`, `AbsenceReason` (`Sources/ZTronAssetStorage/Store/AssetRecord.swift`).

## ADR-019 — Foreground transfers are data tasks streaming into staging
- **Context.** transport.md chose download tasks. transport-2 T2-01 (critical) measured that every interrupted foreground download task leaves `CFNetworkDownload_*.tmp` in the per-user temp directory, outside the store root and invisible to GC, quota and reports; this team's probes left about 794 MiB there (still present; the human must remove them, `ARCHITECTURE.md` §15). transport-1 TR1-2, TR1-4, TR1-5 and T2-07 trace further defects to URLSession resume data (it embeds the key, fails with −1002 when stale, and lives in a private archive).
- **Options.** (a) Keep download tasks and sweep `CFNetworkDownload_*.tmp` at launch (writes outside the root, still loses partials). (b) Data tasks whose delegate appends each chunk into `staging/<name>.part` through `StagingSink` (the `FileSystem` seam), resuming with `Range` + `If-Range` from our own sidecar.
- **Decision.** (b) for every foreground transfer, manifest included. Partial bytes never leave the root; GC, quota, `StorageReport` and purge see them; resume data no longer exists on the foreground path, so no key is ever at rest in staging (ADR-T4 is moot). The size guard measures bytes written into staging and aborts early on the manifest's `byteSize` (`SizeGuard`). Only the opt-in background session (ADR-026) still uses download tasks, whose temp files the OS keeps in the daemon's space and whose completed files are moved into staging before the delegate returns. **Loopback tests and benchmarks (P-10, P-11) use only the data-task path.**
- **Consequences.** `StagingSink` gained `createPartial`, `appendPartial`, `continuePartial`; `ResumeSidecar` and `ResumePoint` replace resume data. Checksum-less transfers are never resumed (transport-1 TR1-3).

## ADR-020 — Single-flight per content (`TransferID`)
- **Context.** sync.md single-flighted per `AssetID`; transport-1 TR1-1: two manifest entries with one checksum then run two transfers into one staging name.
- **Decision.** The engine keys jobs by `TransferID` (`c-<sha256>` for checksummed content, `l-<sha256(id ‖ 0 ‖ remotePath)>` for legacy entries, `m-manifest`); interests carry the asset ids. One verified staged file is published for every id expecting that content (`AssetStore.publish(_:binding:expecting:urgency:)`). A job's lane is the maximum over its interests.
- **Consequences.** Dedupe costs zero extra downloads; per-asset waiters still resume independently (H-3).

## ADR-021 — `TransferHandle` with synchronous controls
- **Context.** sync.md proposed a per-transfer control stream; transport.md a handle. sync-1 S1-06: `.bufferingNewest(1)` drops a `pause` followed by `setPriority`, and promotion was not ordered before the next start; sync-2 S2-19: an unfinished control stream leaks a consumer task per transfer.
- **Decision.** `TransferHandle` (Model) with `setPriority`, `pause`, `cancel` synchronous and nonisolated, plus a single-consumer `updates` stream whose terminal element is always last. No control stream exists. A restart is a new attempt with a new handle, never a restart inside a handle (transport-2 T2-08).
- **Consequences.** The engine promotes and preempts inside synchronous actor code; `FakeTransferHandle` records controls in call order under a lock, so the R-NET-10 ordering test is deterministic.

## ADR-022 — The store owns no task: the engine's alarm drives store deadlines
- **Context.** store.md gave the store a reaper task and a deferred-commit task; sync.md's X-4 claimed either owner satisfies P-14. sync-2 S2-02 (critical): with a store-owned reaper, `blocked(.awaitingSpace)` has no wake-up. store-2 S2-03 (reaper busy loop) and S2-08 (store-owned tasks make R-STO-5 op sequences nondeterministic).
- **Decision.** `AssetStore` owns no task and no timer. It reports `nextDeadline()` (time-only blockers) and executes `runDueWork()` (coalesced commit, reap batches) when the engine's single alarm fires; `StoreWorkReport.reapedBytes` wakes `awaitingSpace` jobs. Store calls that may change a deadline (lease release, acknowledgement, commit) are routed through the engine, which re-arms its alarm.
- **Consequences.** One owner for every timer (P-14, R-SYN-14); store tests drive `runDueWork()` explicitly, so op order is deterministic.

## ADR-023 — Event broadcast and backpressure
- **Context.** sync.md §10 (pull-based queues). sync-2 S2-17: subject bound ignored pruned ids, bulk terminal events flood the UI, a stored stream keeps its subscription; sync-1 S1-19.
- **Decision.** Pull-based per-subscriber queues (`AsyncStream(unfolding:onCancel:)`), progress newest-wins per key at ≤ 10 Hz with a trailing emission after a quiet period, terminal events coalesced per subject and never dropped. Per-asset terminal events of **bulk** work are folded into `syncProgress`/`syncFinished` instead of being broadcast. A pruned id's subject is retired with its `assetRemoved` event. Transfer progress keys are retired with their transfer. A subscription registers on the first pull and is released on cancel, on deinit of the stream and at shutdown.
- **Consequences.** Per-subscriber memory is bounded by `progress keys (≤ max + 3) + subjects (≤ non-bulk assets with unread terminal events + 5)`; documented on `AssetEvent`.

## ADR-024 — Keyed randomness
- **Context.** sync-2 S2-16: one RNG consumed in actor-arrival order gave 3 different schedules for one seed in 200 runs.
- **Decision.** `RandomSource` exposes one seed; every draw is `KeyedRandom.next64(seed:key:counter:)` keyed by what is drawn (asset, attempt, breaker trip), never by draw order. `StableHash` (FNV-1a) derives keys reproducibly across processes.
- **Consequences.** `Backoff.delay` is implemented this way and tested (`R-SYN-5: backoff delays are full jitter keyed by asset and attempt and reproducible from the seed`).

## ADR-025 — Over-budget catalogs admit the largest fitting prefix
- **Context.** sync-2 S2-07: an all-or-nothing space check never syncs anything, not even `essential` assets, when the catalog exceeds the default budget; S2-06 and S2-08 (spurious failures with nothing to fetch, unknown sizes estimated at 8 MiB).
- **Decision.** `StoragePolicy.admitLargestFittingPrefix` (default `true`): the planner admits the longest prefix of the stable fetch order (essential first) that fits after permitted eviction, and skips the rest as `overBudget`; with `false`, an over-budget plan fails with no side effect (R-SYN-11). A plan with zero fetch bytes always fits. Unknown sizes are not estimated in the plan; the per-fetch headroom ledger admits them.
- **Consequences.** A run that skipped entries as `overBudget` never ends `.complete`, so the stamp is not written and the sync stays due; the report lists the skipped bytes.

## ADR-026 — Background `URLSession` and app-key exposure · **NEEDS-HUMAN-REVIEW**
- **Context.** R-NET-3 (SHOULD) wants a background session for bulk transfers. In a background session the OS follows redirects without calling the delegate (NSURLSession.h:1732), so the app key is sent to any redirect target (transport.md E-13), and neither the 5-hop limit (R-NET-4) nor the size cap (R-NET-7) can be enforced while the app is not running (transport-2 T2-09).
- **Options.** (a) No background session. (b) Background always on (violates R-NET-4/R-NET-7, MUSTs). (c) Built, off by default, used only for bulk, key-free requests, unless the owner opts in.
- **Decision.** (c). `BackgroundTransferPolicy.disabled` is the default. `.enabled(options)` requires the app to forward the AppDelegate hook. `KeyRedirectExposure.refuse` (default) keeps every key-bearing request in the foreground; `.acceptedByOwner` is the owner's explicit acceptance that, for background bulk transfers only, the key may follow OS redirects and the hop limit and size cap are checked only after the fact (bytes from a cross-origin redirect are discarded). R-NET-4 tests cover the default `.refuse`.
- **Consequences.** With today's AWS tier (key always required) production bulk transfers stay foreground unless the owner opts in. The owner must decide whether to keep `.acceptedByOwner` in the public API or remove it.
- **Amendment (contract-fix round 3): production wiring.** `HTTPRemoteSource(configuration:staging:log:)` builds its background backend with `makeBackgroundBackend(_:staging:policy:)`: `nil` when disabled or the namespace is invalid, else `BackgroundTransferCoordinator(driver:staging:options:)` over `LiveBackgroundSessionDriver` and a `.background` `SessionDelegate` (construction only; the session is created by `activate()` after the store opened, ADR-028). `SessionDelegate` carries a session-event stream created in `init` (`sessionEvents`), the delivery path for background completions and for the foreground `didBecomeInvalidWithError` that `invalidate()` waits for (transport-2 T2-04). WP-D owns every Transport body, Stage 1 ones included. Background-delegate tests call the delegate methods directly with unresumed tasks and files inside the repository, never real download tasks (ARCHITECTURE §14).

## ADR-027 — Apple-tier pack retention (H-7) · **NEEDS-HUMAN-REVIEW**
- **Context.** No stable pack-file URL exists (APPLE-API-VERIFICATION §1.4); removal is whole-pack (§1.5). transport-2 T2-13: "release when every entry is adopted" never fires with a scope or quota; pack bytes are invisible to quota and reports. store-1 S1-10: releasing after a non-durable publish loses the asset on power loss.
- **Decision.** Adopt-and-release: stream the pack file into staging, hash, publish into `blobs/`; release a media pack (never the catalog pack) once every catalog entry mapped to it is adopted **in a durably committed generation** or excluded by the keep-scope (`PackReleasePlanner`, implemented and tested), at most once per pack per catalog generation. Default `PackRetention.releaseAfterAdoption`; `.keepPacks` keeps the prior art's double residency. `StorageReport.sourceCopyBytes` reports bytes the OS still holds. Apple-adopted assets rank after ordinary evictable ones, because evicting one after its pack was released costs a whole-pack re-download.
- **Amendment (contract-fix round 2): the seams behind this decision.**
  - *Keep-scope = the client's retention scope.* `AssetClientConfiguration.retentionScope: AssetScope` (default `.all`) and `AssetClient.setRetentionScope(_:)` carry what the app wants kept (R-CAR-5: the paywall maps to it at launch and whenever it changes). The engine uses it as the scope of every bulk run; the store (`AssetStore.setRetentionScope(_:)`, in-memory, pushed by the engine after `open()`) evicts entries outside it before any entry inside it and lists them in `AdoptionReport.excludedRemotePaths`, so a pack whose remaining entries the paywall excludes is released (transport-2 T2-13). Changing the scope deletes nothing and starts no run; `purge(.scope(_:))` deletes, `ensureAvailable(scope:)`/`sync(.force)` fetch.
  - *Atomic durable adoption report.* `AssetStore.adoptionReport()` captures the present records, the applied manifest and the exclusions synchronously, commits the holding generation durably, and returns only what it captured (REENTRANCY R15), so a publish that lands during the commit is never reported adopted (store-1 S1-10).
  - *Source-held bytes reach the report through the Model.* `RemoteSource.sourceCopyBytes()` (0 for HTTP; the Apple source sums `PackBackend.installedBytes` of adopted, unreleased packs); `SyncEngine.storageReport()` fills `StorageReport.sourceCopyBytes` with it, because Sync reaches AppleHosted only through Model protocols.
- **Consequences.** Double residency is bounded by one pack between first adoption and release. Owner decides the default and confirms the retention-scope semantics (no proactive deletion).

## ADR-028 — Launch reconciliation order and staging GC
- **Context.** transport-2 T2-03 (critical): staging listed before the background session existed loses work the OS delivers in between; an offline launch's empty plan cancelled every live task. store-2 S2-11, store-1 S1-17, transport.md X-T6.
- **Decision.** `start()` runs: `store.open()` (lock, load, reconcile blobs; staging **not** collected) → build the remote source → `activate()` the background session if enabled → `reattachedTransfers()` → `store.stagingInventory()` → `TransferReconciler.plan(live:staged:wanted:)` with `wanted` = applied entries that are not present (never the run's network plan) → execute → `store.collectStaging(keeping:)`, which also keeps any unclaimed file younger than `stagingClaimGrace` (1 h). A complete `.part` makes a `.resume` for the same transfer garbage.
- **Consequences.** H-6's "not lost, not duplicated" holds in the most common case; the fake background driver delivers completions only on `activate()` so the test encodes the real OS order.

## ADR-029 — Legacy migration phase 2 runs after `open()`
- **Context.** store-2 S2-09 and sync-2 S2-11: hashing the whole legacy catalog inside `open()` blocks every API (seconds on the upgrade launch) and the "publish every 64" snapshots would precede reconciliation.
- **Decision.** `open()` performs lock, load, reconciliation and legacy phase 1 (plan from `manifest.json` + `local-checksums.json`, one ordered commit), then publishes the first snapshot. Phase 2 (hash and rename) runs as an engine-owned, resumable task through `AssetStore.migrateLegacy(maxFiles:)`, publishing progressively; a `resolve` or lease of a legacy id not yet adopted calls `adoptLegacyNow` first (one hash, far cheaper than a download). Phases 3–4 run when nothing remains. The UserDefaults key is removed only after a durable "done" commit.
- **Consequences.** Lookups hit adopted legacy files early; no snapshot precedes reconciliation.

## ADR-030 — Manifest application API
- **Context.** sync.md planned a `ReconcileStep` applied with `expectedGeneration`; store.md applied a manifest itself. sync-1 S1-12: a whole-snapshot generation guard makes `ensureAvailable` fail under a running bulk sync. X-1, X-2, X-3.

## ADR-031 — Circuit-breaker liveness and the 403 family
- **Context.** sync-1 S1-03 and sync-2 S2-01 (critical): a half-open probe that is cancelled or fails for another cause wedges the breaker forever. sync-2 S2-05: an ambiguous object 403 was quarantined until the entry changes. transport-1 TR1-5/6/7/11.
- **Decision.** Probe resolution is total: success closes; a same-cause failure re-opens with `trips + 1`; any other exit (different cause, offline, cancelled, paused, superseded, shut down) returns to `halfOpen(probe: nil)`; a watchdog deadline (`CircuitBreakerPolicy.probeWatchdog`, 60 s) re-arms a silent probe; the probe is never a preemption victim. An ambiguous object 403 fails the asset for the run (`.nextRun`) and feeds the auth-suspect counter; it never quarantines. A 403 after our own key stripping is `rejected(.keyWithheldOnRedirect)`, never key rejection; 401 and −1012/−1013 are `transient(.authenticationChallenge)` (proxies, captive portals). The 403 hint checks body shape before purpose.
- **Consequences.** `CircuitBreaker.Outcome.abandoned` and `.neutral` exist in the contract.

## ADR-032 — Integrity bookkeeping lives in the store
- **Context.** sync-2 S2-04: integrity counters in the engine's `Job` die with it, and the interactive retry cap (2) is below `maxIntegrityAttempts` (3), so every visit to a corrupt asset re-downloads it. transport-2 T2-12: Apple-tier catalog/pack skew classified as integrity quarantines good content.

Catalog/pack skew is `transient(.sourceVersionSkew)`, which triggers one best-effort update check and never quarantines.

So `RetryDisposition.untilEntryChanges` really is persisted for both causes ARCHITECTURE §7.6 names, and a relaunch never re-requests a 404. Test `R-NET-6: a 404 is not requested again until its manifest entry changes, across a relaunch` (WP-F). (2) *One recording path.* The engine records integrity bookkeeping (`recordIntegrityFailure`) for transport **and** store integrity failures; `publish` deletes the staged bytes, counts the metric and throws, and never calls the WP-C stub itself (ADR-046).

## ADR-039 — Engine-owned entry tasks and shutdown discipline
- **Context.** sync-1 S1-04 (critical): shutdown closed the store under a purge asleep in its grace window and under `start()`; S1-08 (shared work in a caller's task); S1-09 (owned-task keys reused); store-1 S1-09 (close races unit continuations).
- **Decision.** Every store-touching entry point (`start`, `purge`, `ensureAvailable`, `performMaintenance`, `reportUnreadable`, `setPinned`, `setRetentionScope`, leases, migration) runs as an engine-owned task, keyed by a unique spawn id, joined by its caller through the waiter pattern; a caller's cancellation withdraws only its interest. `shutdown()`: lifecycle `shuttingDown` → cancel and join every owned task (the memory-pressure observer included) → resume every continuation table with `.shutDown` → `remote.invalidate()` → `store.close()` (drains in-flight units, durable flush, unlock) → `clientShutDown` → `shutDown`. `invalidate()` returns after the **foreground** delegate's last callback (transport-2 T2-04) and after the Apple source's in-flight `writeStaged` calls; the opt-in background session is released without waiting for the OS's tasks (contract-fix round 2: `finishTasksAndInvalidate` would make shutdown wait for hours), and a file it moves into staging after close is an ordinary staged file for the next launch's reconciliation (ADR-028). `StagingSink` therefore promises nothing after close (an immutable sink cannot observe it without a lock). Shutdown in `created` never opens the store. Inside the store every resumption re-checks the phase. After shutdown every API fails with `.shutDown` (ADR-042).
- **Consequences.** R-SYN-15's "no task leaks" is provable with the census (`EngineIntrospection.ownedTasks`, `ManualTimeSource.pendingSleepers`, `FakeRemoteSource.activeTransfers`, `FakeDeviceConditionsSource.activeObservers`).

## ADR-042 — After `shutdown()` every API fails with `.shutDown` (R-SYN-15) · **NEEDS-HUMAN-REVIEW** (public signatures)
- **Context.** R-SYN-15 (MUST): "any API used afterwards fails with a typed error". - **Consequences.** Callers write `try await` on queries; the compatibility shims (`CDNSyncCoordinator` and friends) absorb it. ## ADR-046 — Stage 2 dependency levels and the storage ownership split (orchestrator decision)
- **Context.** PROMPT §5 ran WP-B and WP-C in parallel with write sets `{FileSystem,Store,Index,Blobs,Lock,Snapshot}` and `{Integrity,Cleanup,Eviction,Migration}`, but the round-2 contract put all 16 of WP-C's `AssetStore` methods as stubs inside `Store/AssetStore.swift` over `private` state: WP-C could not implement them in its own directories (an actor extension can neither add stored properties nor read `private` state), and both packages would edit one actor body, a guaranteed merge conflict (CLAUDE.md P2). `Staging/` and `Layout/` were in nobody's write set. The orchestrator also decided the Stage 2 order.
- **Options.** (a) Keep parallel B and C and grant both `AssetStore.swift` (conflicts by construction). (b) Sequence C after B and grant C `AssetStore.swift` (ownership by time, not by path). (c) Sequence C after B **and** split by path: WP-C's API in `extension AssetStore` files in its directories, the shared state declared in the contract.
- **Decision.** (c). Work packages run in dependency levels, each in its own worktree `.worktrees/<wp>` (ADR-009) with its own scratch path: **L1** {H test support, A model} → **L2** {B storage core, D transport, E Apple tier} → **L3** {C integrity, cleanup, eviction, migration, on merged B} → **L4** {F sync engine} → **L5** {G facade, then K compatibility shims in `Tests/ZTronAssetCompatibilityTests`}; **I** (docs) at the end. The orchestrator merges and commits a level before the next starts. Storage: `AssetStore.environment` and `AssetStore.state: StoreState` are internal; `StoreState` holds one sub-struct per owner (`core`: WP-B; `cleanup`, `eviction`, `integrity`, `migration`: WP-C), each in its owner's directory, extendable only by its owner. WP-C's methods live in `Eviction/`, `Cleanup/`, `Integrity/`, `Migration/` (signatures unchanged). WP-B provides primitives for WP-C (`Store/StoreInternals.swift`: `ensureOpen`, `setResidency(_:of:dooming:)`, `markDirty`, `requireCommitted`, `publishSnapshot(urgency:)`, `reapDeletable(maxKeys:)`, `hashFile(at:)`, `adoptVerifiedFile(at:digest:byteCount:for:)`); WP-B calls WP-C only through two opt-in hooks (`runLegacyPhaseOne()` when legacy migration is enabled, `applyEviction(_:)` when `apply` gets a plan), so WP-B is complete and testable before WP-C exists. `Staging/` and `Layout/` belong to WP-B. `recordAccesses`, the I-3 deletion machinery, the streaming hash and launch reconciliation are WP-B's, because they sit on WP-B's commit and acknowledgement paths; §11's WP column follows (R-INT-1/2/5/6, R-CLN-1, R-CLN-7, P-6, P-13 → B; R-CLN-5 → B and C). Every WP writes only its own test files and its own benchmark file (ARCHITECTURE §1.2); contract test files, `ARCHITECTURE.md` and `DECISIONS.md` stay orchestrator-owned, and a WP drafts its ADRs in `docs/adr-drafts/<wp>.md` for the orchestrator to number.
- **Consequences.** File ownership is decided by path alone, so a merge conflict is an ownership bug, as P2 requires. WP-C depends on WP-B's internals (the `core` fields and primitives), which the sequencing makes safe. B and C no longer overlap in time, which lengthens the critical path by one level; D and E absorb the parallelism of L2. PROMPT §5's parallel "B, C, D, E" is superseded by this plan (PROMPT.md itself is not edited).
- **Amendment (contract-fix round 4).** The round-4 review found writes and tests the plan above left without an owner. (1) *Package-wide scans.* R-CAR-9 and R-SEC-3 were WP-I's and R-ENV-4 "all"'s, but WP-I owns no test path and "all" is nobody, so the trace gate's MUST-coverage could not be reached under the stated ownership. The orchestrator owns all six package-wide scans (R-CAR-9, R-SEC-3, R-ENV-2, R-ENV-3, R-ENV-4, R-ENV-5) in `Tests/ZTronAssetModelTests/PackageScanContractTests.swift`, written and green in this round; the R-ENV-4 scan reads its patterns and cap from `Scripts/quality-gates.json`. The alternative, reassigning R-CAR-9, R-SEC-3 and R-ENV-4 to WP-A (whose tests already host the R-ENV-1 source scan), was not taken: all six pass today, so landing them now costs less than scheduling them, and three of them check `Package.swift`, which is the orchestrator's file anyway. (2) *WP-C's legacy writes.* Legacy phase 1 may install the legacy manifest as `appliedManifest` (no ETag) while none is applied, insert `absent(.neverFetched)` records with `expectedBlob` for ids the index lacks, and set `degraded` on an undecodable legacy manifest; phase 3 may set `syncDue` (directly or through `markSyncDue()`). No other route exists: `adoptVerifiedFile` only marks existing records present and `apply` cannot run inside `open()` (REENTRANCY R1). (3) *Cleanup stamps.* `lastCleanupAt` is stamped only by WP-C's own GC, eviction and purge (it is `StorageReport.lastCleanupAt`, "the last GC, eviction or purge"), never by WP-B's reaper; `lastMaintenanceAt` is removed (no reader, no reachable writer; ADR-012 amendment). (4) *Writers with a path at the right level.* Every multi-WP row of ARCHITECTURE §11 names each test's writer: R-CAR-6 → K (ADR-033 amendment); P-7 → F (`BenchSync.swift`); the R-STO-1 foreground-transfer test and the R-CLN-10 retention-scope test → F (they need WP-D's backend and WP-C's `setRetentionScope`, merged only by L4); the R-STO-6 conformance suite is H's API that B calls (ADR-045 amendment). (5) *Shared documents.* `docs/adr-drafts/<wp>.md` is carved out of WP-I's `docs/**`, one file per WP; `docs/TRACEABILITY.md` is orchestrator-regenerated after each merge and a WP restores it before handoff (or runs only `--quick`); REENTRANCY rows a WP needs are proposed in its ADR draft and merged by the orchestrator, and the contract's already-required awaits got rows now (ARCHITECTURE §10, R16–R18, RE-S35–RE-S42).

## ADR-047 — A log-sink seam: tests never write to the unified log · **NEEDS-HUMAN-REVIEW** (public signatures)
- **Context.** `AssetLog.emit` always wrote to `os.Logger`. Once implementations log at `.info` or above, every test exercising those paths would persist lines into the system's unified-log store, outside this repository (owner directive); the existing R-OBS-1 test already emitted one `.debug` line. Transport and the Apple tier had no route to the environment's tap at all.
- **Options.** (a) Log only to the tap in tests by convention (unenforceable). (b) A `LogSink` protocol in the environment, live conformer over `os.Logger`, a test conformer that writes nothing, and one value carrying sink and tap to every layer built from the environment.
- **Decision.** (b). `LogSink` (`write(_:)`, `signposter(_:) -> OSSignposter?`) with `OSLogSink` (live; the only writer to the unified log; named only by `.live()`, like the other Model live conformers of ADR-038) and `TapOnlyLogSink` (writes nothing, no signposts). `AssetEnvironment.logSink` defaults to `TapOnlyLogSink` in `init`, so an environment assembled by hand (every test) never reaches the unified log unless it names `OSLogSink`; `.live()` names it. `LogRoute` (sink + optional tap) is how the environment's logging reaches the store (`StoreEnvironment.log`) and the remote sources (`RemoteSourceFactory.makeRemoteSource(configuration:staging:log:)`, `HTTPRemoteSource.log`, `AppleHostedRemoteSource.log`, `AppleHostedTier.resolve(…, log:, …)`). `AssetLog.emit(_:sink:tap:)` and `log(_:_:_:sink:tap:)` replace the `os.Logger`-only variants; signpost intervals are taken from the sink, so tests emit none.
- **Consequences.** Tested: `R-OBS-1: every line reaches the environment's sink and tap once, and an environment of fakes keeps the unified log untouched`; the round-2 R-OBS-1 test now routes through `TapOnlyLogSink`. An app that builds its own environment must pass `OSLogSink()` to keep unified logging (documented on `AssetEnvironment.init`). Public signatures changed: `RemoteSourceFactory.makeRemoteSource(configuration:staging:log:)`, `HTTPRemoteSource.init(configuration:staging:log:)`, `AppleHostedRemoteSource.init(configuration:backend:staging:log:)`, `AppleHostedTier.resolve(configuration:staging:packBackend:log:makeAWS:)`, `AssetEnvironment.init(…, logSink:, logTap:)`; none has shipped.
- **Review tag (contract-fix round 4).** Tagged NEEDS-HUMAN-REVIEW like ADR-042, ADR-044 and ADR-048: it changes public signatures (`RemoteSourceFactory.makeRemoteSource(configuration:staging:log:)`, a protocol requirement custom factories must adopt; `AssetEnvironment.init(…, logSink:, …)`; `HTTPRemoteSource.init(configuration:staging:log:)`; `AppleHostedRemoteSource.init`; `AppleHostedTier.resolve`) and makes an environment an app builds by hand silent in the unified log by default (`TapOnlyLogSink`) unless it passes `OSLogSink()`. Listed in the owner review list at the top of this file.

## ADR-048 — Every configuration knob reaches its consumer · **NEEDS-HUMAN-REVIEW** (public signatures)
- **Context.** Round-3 review: five settings never reached the code that needs them. `LegacyMigrationPolicy.defaultsSuiteName` was never read (the default `.live()` read `.standard`, so a configured suite's legacy stamp was neither migrated nor removed, R-STO-2/R-STO-11); `prefetchRadius` was unused; `PlanningPolicy.evictionPermitted` had no source (R-SYN-11 "policy permitting"); the store's publication cap had no `maxAssetBytes`; `DiagnosticReport.indexSchemaVersion` had no exported constant.
- **Options.** For the suite: remove the field, or derive the live environment from it. For the rest: wire each knob, or document it as unused.
- **Decision.** Wire all five. (a) `AssetClient.init(configuration:environment: AssetEnvironment? = nil)`: `nil` resolves to `.live(legacyDefaultsSuiteName: configuration.legacy.defaultsSuiteName)` (`AssetClient.resolvedEnvironment(_:for:)`); an explicit environment wins (an app passing its own `.live(…)` passes the same suite). (b) `PrefetchWindowController(client:radius: Int? = nil)` defaults to `configuration.prefetchRadius`. (c) `StoragePolicy.evictionPermitted` (default `true`; when `false` a run evicts nothing to make room, maintenance quota eviction still runs) and `PlanningPolicy(storage:includeOnDemand:now:)`, which copies it with `allowUnverifiedAssets` and `admitLargestFittingPrefix`. (d) `StoreConfiguration.limits: ManifestLimits` (publication cap, legacy decoding limits) and `snapshotInstallInterval` (ADR-016), built by `AssetClient.storeConfiguration(for:)`. (e) `StoreLayout.indexSchemaVersion: UInt16 = 1`.
- **Consequences.** Tested: `R-STO-11: the default live environment reads the legacy stamp from the configured UserDefaults suite`, `R-CAR-3: the window controller's radius defaults to the client configuration's prefetchRadius`, `R-SYN-11: the planning policy takes eviction permission, unverified admission and the prefix rule from StoragePolicy`, `R-SYN-11: the eviction switch defaults to permitted and an out-of-range snapshot install interval is clamped`, `R-STO-13: the store receives the client's snapshot install interval, manifest limits, policy and legacy layout`. Public changes for the owner to confirm: the optional `environment` of `AssetClient.init`, the optional `radius` of `PrefetchWindowController.init`, the new `StoragePolicy.evictionPermitted`.
