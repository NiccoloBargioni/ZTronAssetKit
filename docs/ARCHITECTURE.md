### 1.1 Storage: the WP-B / WP-C split (ADR-046)

`AssetStore` is one actor implemented by two work packages that run one after the other (§1.2), in disjoint files. An actor extension can neither add stored properties nor see `private` state, so the contract declares the state: `AssetStore.environment` (internal) and `AssetStore.state: StoreState` (internal), one value with one sub-struct per owner. Each sub-struct lives in a file of its owner, who may add fields to it; the Stage 1 fields are contract fields the other package relies on.

Rules that keep the split mechanical:
1. **WP-C → WP-B** only through WP-B's package API and the `StoreInternals.swift` primitives; WP-C writes `StoreCoreState` fields only where that file says so (`purgeEpoch`, `stamp`, `syncDue` (every purge clears the stamp and sets it before its first own await, SPEC R-CLN-6; C-5), record `pinned`/`integrity`/`verifiedAt`, metrics counters), always followed by `markDirty(_:)` or `requireCommitted(_:)`. WP-C's only writes into WP-B bookkeeping (`blobTable`, `blobBytes`, `orphans`, for an orphan-GC sweep) go through `doomOrphans(_:)`, which clears `state.core.orphans[key]` in the turn it dooms the key, so ruling R1's rule-1 exemption is not used (C-23). Besides the primitives and the package API, WP-C calls WP-B's internal lifecycle helpers `awaitOpen()`, `checkLive()`, `checkWritable()`, `runUnit(on:)` and `waitForKey(_:)` (a purge's wait for an in-flight deletion) and reads two bookkeeping fields, `blobBytes` (the bytes a quarantine or a failure releases, ruling R7) and `commits.mutationSerial` (legacy phase 3's guard, C-24) (ADR-052). **Legacy migration (round 4)** adds four writes it cannot make any other way, because `adoptVerifiedFile` only marks *existing* records present, no primitive inserts records, and `runLegacyPhaseOne()` runs inside `open()`, where every async API (`apply` included) awaits `open()` (REENTRANCY R1): phase 1 installs the legacy manifest as `appliedManifest` (with `etag` `nil`) only while the applied manifest is empty; it inserts records only for ids that manifest lists and the index lacks, each as `absent(.neverFetched)` with `expectedBlob` (store.md §7 "merge into records"; ADR-029's "lookups hit adopted legacy files early" and the H-10 test `R-STO-11: lookups hit adopted legacy files while migration is still running…` depend on it); it sets `degraded` when the legacy `manifest.json` cannot be decoded (store.md §7). Phase 3 sets `syncDue`, directly or through `markSyncDue()`, when not every legacy entry was adopted (and `stamp` when every one was). Since the level-3 merge phase 1 builds these writes off the actor from snapshots and assigns them whole while `opening` (C-24), and a launch whose legacy manifest cannot be decoded adopts nothing: its files stay in the legacy root (C-13, NEEDS-HUMAN-REVIEW; ADR-052).
2. **WP-B → WP-C** only through two hooks, each run only on opt-in: `runLegacyPhaseOne()` from `open()` when `configuration.legacy.enabled`, and `applyEviction(_:)` from `apply` when it receives a plan, once per chunk of whole blobs (about `EvictionState.chunk` = 1,000 records) for a larger plan, the actor released between chunks behind the write fence (ruling R6, row c-8; ADR-052). WP-B's tests use `LegacyMigrationPolicy(enabled: false)` and `eviction: nil`, so WP-B is complete and green before WP-C exists. WP-B **reads** WP-C's contract fields (`state.cleanup.leases` in the reaper, `state.eviction.retentionScope` in `adoptionReport`, `state.eviction.chunk` in `apply`'s chunked eviction, ruling R6) and its codec persists WP-C's persisted ones (`migration.phase`, `migration.legacyStamp`, `cleanup.lastCleanupAt`, STAMPS section). `lastCleanupAt` is `StorageReport.lastCleanupAt` ("the last GC, eviction or purge"): only WP-C's own operations (orphan and staging GC, quota eviction, purge) stamp it, and only when the run removed, doomed, evicted or purged something (C-4; a purge is stamped once committed and again after its wait; ADR-052); the reaper's deletions of pruned blobs in `runDueWork()` are not a cleanup run and do not. `lastMaintenanceAt` was removed in round 4: no reader existed and no API the engine reaches set it.
3. **Deviations from the reviewer's list, with reasons.** `recordAccesses` moved to WP-B instead of WP-C: every acknowledged install (REENTRANCY R6, WP-B's snapshot path) delivers `InstallAck.accesses` to it, so a WP-C stub there would make WP-B's commit path untestable. The I-3 deletion machinery (doom → deletable → reap, `nextDeadline`, `runDueWork`) is WP-B's, because it lives in the blob table, acknowledgements and commits; WP-C dooms through `setResidency` and reaps through `reapDeletable`. The streaming hash is WP-B's (`publish` cannot exist without it). The requirement column of §11 follows: R-INT-1/2/5/6, R-CLN-1, R-CLN-7, P-6 and P-13 move from WP-C to WP-B, and R-CLN-5 becomes B (acknowledgement and grace) plus C (leases).
4. **What the merged WP-B store gives WP-C (ADR-050).** (a) `ensureOpen()` checks only the phase; WP-B's writing APIs also call the internal `checkWritable()` (throws `.storageUnavailable(.rootVanished | .ioFailure)`, B-15, B-34), so WP-C's mutating APIs call it too, or a read-only or replaced-root store mutates memory that no commit can persist (their `requireCommitted` throws). (b) `setResidency(.present)` is honoured only for a key that is live or doomed `unreferenced` and not in `publishing`; otherwise nothing changes (B-14, B-18). (c) `requireCommitted` waits while `apply`'s commit fence is up (row b-8); `applyEviction(_:)` runs synchronously inside the fence; for a plan larger than `EvictionState.chunk` records `apply` cuts the plan on the bulk executor (`ApplyEvictionChunks`: runs of one blob, each chunk ending at the first blob boundary at or past the chunk) and calls the hook once per chunk with a no-op metadata unit in between, behind the fence; a plan that names a blob apart is grouped by key and its report put back in plan order (ruling R6, row c-8; ADR-052). (d) Records ⊆ applied ids must hold after legacy phase 1: a record outside the applied manifest is persisted as *detached* (B-4). (e) A key in `publishing` may already be `live` while its name is replaced (B-18), so R10's sweep set `blobTable ∪ publishing` protects it. (f) The test-target seams of B-16 (`testSetLease`, `testClearLeases`, `testSetRetentionScope`, `testSetIntegrity`, `testBumpPurgeEpoch`, `testExpect`, `testInsertRecord`, and B-23's `testRaiseApplyFence`; internal, never public, never in `Sources/`) write WP-C's fields the way WP-C's APIs will; WP-C replaces them by its real APIs where those exist, and covers the package initialisers of `AssetLease`, `EvictionVictim`, `EvictionPlan` and `VerificationReport` through those APIs (G4: no coverage-only test; the orchestrator re-checks Storage per-file coverage after L3). Done at L3 (C-17; ADR-052): `testSetLease`/`testClearLeases` → `acquireLease`/`releaseLease` (`StoreDeletionTests`), `testSetRetentionScope` → `setRetentionScope` (`StoreReentrancyTests`), `testSetIntegrity` → two `recordIntegrityFailure` calls and `testBumpPurgeEpoch` → an empty `purge` (`StoreApplyTests`), their declarations deleted; `testExpect`, `testInsertRecord` and `testRaiseApplyFence` stay (no API replaces them).

Shared and orchestrator-only: `Package.swift`, `.gitignore`, the contract files above (a WP implements bodies in them but changes no signature), every `*ContractTests.swift` (the package-wide scans of R-CAR-9, R-SEC-3 and R-ENV-2…5 among them, in `Tests/ZTronAssetModelTests/PackageScanContractTests.swift`), `Tests/ZTronAssetKitBenchmarks/{ZTronAssetKitBenchmarks,QualityBudgets}.swift`, `docs/ARCHITECTURE.md`, `docs/DECISIONS.md`, `docs/TRACEABILITY.md`. B and C are sequential, yet their files stay disjoint (§1.1), so ownership is decided by path alone and a merge conflict is an ownership bug (CLAUDE.md P2). Three rules keep the shared documents conflict-free (round 4):
- **ADR drafts.** `docs/adr-drafts/<wp>.md` is one file per work package, owned by that package and carved out of WP-I's `docs/**`. A WP records its decisions there; the orchestrator numbers them into `DECISIONS.md` at merge, so no two worktrees edit one file.
- **REENTRANCY rows.** When a WP adds an await that no row of §10 covers, it proposes the row (await, what is re-validated) in its `docs/adr-drafts/<wp>.md` and cites it in the code comment (`// REENTRANCY: <wp>-n (proposed) — …`); the orchestrator copies it into §10 at merge, keeping the proposed identifier as its final number; the code keeps citing `<wp>-n (proposed)`, the word being historical (ADR-049 for h-n, ADR-050 for the level-2 rows, ADR-052 for c-n). An await covered by a proposed row is not a review failure.
- **`docs/TRACEABILITY.md`** is regenerated by the orchestrator after each merge (`bash Scripts/verify.sh --gates-only` rewrites it). A WP restores it before handoff (`git checkout -- docs/TRACEABILITY.md`) whenever it ran `--gates-only` or `--full`, or runs only `--quick`, so branches of one level never conflict on its counts.

**iOS Simulator (owner, 2026-10-09; ADR-051).** Every test target builds and passes on the iOS Simulator as well as on macOS. Every test a WP adds follows ADR-051's gating convention (`docs/adr-drafts/ios.md` item 2: both platforms in every gate; on a `@Test` function or the helper that uses the fake, never on a `@Suite`; no new `#available` in `Sources/`; `ZTronAssetTestSupport` at the package floors), CPU-bound case loops yield once per case, and the WP runs ADR-051's simulator test command (at least `build-for-testing`) before hand-off, on its own named simulator under `caffeinate -i`. `verify.sh` does not run it (`Scripts/` is frozen), so `VERIFY: PASS` alone does not show it.

## 2. Concurrency model and environment

- **Actors hold state.** `AssetStore` (Storage) and `SyncEngine` (Sync) are actors. `AssetClient` is a `Sendable` final class with immutable stored properties. `SnapshotMirror`, `PrefetchWindowController` and `BackgroundEventsRelay` are `@MainActor` classes with `nonisolated init`, so the nonisolated `AssetClient.init` creates them (transport-2 T2-16).
- **One environment value** (SPEC §4.2, ADR-038): `AssetEnvironment` (Model) carries `FileSystem`, two `BlockingExecutor`s (metadata, bulk), `TimeSource`, `RandomSource`, `DeviceConditionsSource`, `RemoteSourceFactory`, `AppVersionSource`, `LegacyDefaults`, optional `MemoryPressureSource`, a `LogSink` and an optional `LogTap`. `.live()` is built in the facade, performs no I/O (P-12) and builds fresh conformers per call (ADR-038). **Logging (ADR-047):** every line goes through `AssetLog.emit(_:sink:tap:)` / `LogRoute`; `.live()` installs `OSLogSink` (the only writer to the unified log) and an environment assembled by hand defaults to `TapOnlyLogSink`, so tests never persist a line outside this repository; the route reaches the store (`StoreEnvironment.log`) and the remote sources (`RemoteSourceFactory.makeRemoteSource(configuration:staging:log:)`).
- **Blocking work** (ADR-003 as fixed by ADR-038): `BlockingExecutor.run(_:)` takes a bounded, non-throwing `@Sendable` unit; `run(throwing:)` rethrows typed errors through `Result`. Units: one rename, one ≤ 1 MiB read plus hash update, one index commit, up to 64 unlinks within `BlobDeletionUnit.budget` (1 ms) of the injected monotonic clock (§4.4; ADR-050), one listing. Live: `DispatchBlockingExecutor` (serial queue, `autoreleaseFrequency: .workItem`); tests: `InlineBlockingExecutor`, and `SteppedBlockingExecutor` to hold a unit at a known point (H-5). The live conformers outside the store run their blocking first reads in one unit too: the bundle enumeration (`AssetFallbackChain.prepare`) and `Info.plist` (`LiveAppVersionSource`) (ADR-038).
- **Time** (H-8): `TimeSource` has a wall clock (`now`, persisted stamps and LRU only), a monotonic clock (`monotonicNow`, every in-process deadline), an awake clock (`uptimeNow`, deletion grace only, ADR-017) and `sleep(until:)`. Tests use `ManualTimeSource`; nothing ever sleeps for real except the P-11 benchmark's loopback latency.
- **Randomness** (ADR-024): one seed; every draw is keyed by what is drawn.
- **Tasks.** The store owns no task (ADR-022). The engine owns: one alarm (iff its deadline heap is non-empty), one conditions watcher (iff work exists), one driver per transfer in flight, at most one run, one task per store-touching entry point (ADR-039), and one memory-pressure observer (iff a live `PurgeableCache` is registered, ADR-044). Every owned task is keyed by a unique spawn id. The foreground transport owns no long-lived task: its only unstructured tasks end by themselves (a handle's `cancel()` discards the partial and then cancels the data task in one short task; `SessionGate.invalidate` reads the session stream in one task until `.invalidated`). The background coordinator owns one pump (`Task.detached`) only while a background transfer is outstanding (transport-2 T2-10); each background handle control and each terminated handle stream hops to the coordinator in one short unstructured task, and a terminated conditions stream stops its observation in one short task (ADR-050).
- **Unsafe budget** (C1, R-ENV-4): **0 of 3** escapes are used in all of `Sources/`, `ZTronAssetTestSupport` included (`UNSAFE escapes found=0`). Test fakes with synchronous APIs use `Synchronization.Mutex` behind `@available(macOS 15.0, iOS 18.0, *)`; production uses it only inside the iOS 26-gated Apple tier, in exactly `PackTransferStop`, `HashingChunkSource` and `FileHandleChunkReader`, never `@unchecked`, with no await or I/O in a critical section (ADR-003 amendment, ADR-050); tests that use the fakes carry `@available(macOS 15.0, iOS 18.0, *)` on each `@Test` function (or on the helper type or function that uses the fake), never on a `@Suite`, and Apple-tier tests `@available(macOS 26.0, iOS 26.0, *)`; every gate names both platforms, because `@available(macOS N, *)` alone vanishes on iOS (ADR-014 as amended by ADR-051, verified on macOS and on the iOS Simulator). Memory probes for P-6/P-7 live in `Tests/ZTronAssetKitBenchmarks` (ADR-040). No planned escape exists; if a WP believes it needs one, it reports to the orchestrator first.
- **Typed throws** (ADR-004, ADR-042): public async APIs throw `AssetError` (`.shutDown` after shutdown, R-SYN-15); `withAsset` stays untyped; internal layers use `ManifestError`, `TransferError`, `StoreError`, `StagingError`, `PackError`, `FileSystemError`.

## 3. On-disk layout (R-STO-1, ADR-001, ADR-012, ADR-013)

The root is `<base>/ZTronAssetKit/v1/`, where `<base>` is `Library/Application Support` (default, excluded from backup, protection `completeUntilFirstUserAuthentication`), `Library/Caches`, or a custom directory (`StorageLocation`). Every URL is built by `StoreLayout`; no manifest-supplied text is ever a path component (R-SEC-2). This is every file the module creates:

| Path (relative to `<base>`) | Kind | Writer | Content and format | Write protocol | Read by | Removed by |
|---|---|---|---|---|---|---|
| `ZTronAssetKit/` | dir | `open()` | container | `createDirectory`, then barrier-sync of `<base>` (store-1 S1-02) | — | never by the module |

OS-owned files: a background download's temp file is moved into staging before the delegate returns (possibly after the store closed: it is then reconciled at the next launch, ADR-039); Apple packs are the OS's (their bytes reach `StorageReport.sourceCopyBytes` through `RemoteSource.sourceCopyBytes()`, ADR-027).

**Names.** `TransferID` is `c-<sha256>` (content with a checksum), `l-<sha256(id ‖ 0x00 ‖ remotePath)>` (checksum-less, ADR-034) or `m-manifest`. `epoch` is the store's launch epoch (the generation the launch commit carries; persisted, and unique only across launches whose launch commit succeeded over a readable index, §4.5; ADR-050), `seq` the engine's start counter (the store's own copies use sequences counting down from `UInt32.max`, B-18); so attempt tokens order across relaunches (across launches whose launch commit succeeded over a readable index, §4.5; transport-2 T2-06; ADR-050) and two starts never share a name (an exclusive rename reports `nameInUse` in the cases §4.5 lists). Anything in `staging/` that does not parse is foreign and collected; anything in `blobs/` that does not parse as `<64 lowercase hex>.<[a-z0-9]{1,8}>` in the right fan-out is foreign and deleted at launch, never adopted.

## 4. Storage (H-1, H-2, H-10; WP-B, WP-C)

store.md §1–§7 is the detailed design. Amendments from the reviews are normative and listed here.

### 4.1 Commit protocol (R-STO-4, I-5; ADR-015)
0. Promotion, only while the generation the launch loaded from `index.tmp` is pending (`CommitBookkeeping.pendingPromotion`): stat `index.tmp`; if it vanished, the promotion is complete without a commit and nothing new counts as committed; otherwise `synchronizeFile(index.tmp)` at the commit's level (a killed process may have written it without step 3), then steps 4–5 for it (with their condition and undo), then sync the root; only then does its generation count as committed, in `index.bin`. A failed sync renames nothing and leaves the promotion pending; only the stat decides that the file vanished (ADR-050).
1. Barrier-sync every fan-out that received or **adopted** a blob since the last commit, then `blobs/` if dirty (it is dirty after every open).
2. `write(index.tmp, .truncate)`. On ENOSPC remove `index.tmp`, and `index.prev` only while `index.bin` is the file the store knows to hold the committed generation (from the load's full validation or its own renames; never from a header) and a stat still finds it a file; then retry once (ADR-050).
3. `synchronizeFile(index.tmp, .barrier)` for an ordered commit, `.full` for a durable one.
4. `rename(index.bin → index.prev, .replacing)`, only when `index.bin` exists and either `index.prev` is absent or `index.bin` is the file the store knows to hold the committed generation (as in step 2); otherwise step 5 renames straight over the invalid, foreign or uncommitted `index.bin`, so `index.prev` keeps the committed generation. A step-4 rename that reports failure while `index.bin` is gone took effect and is undone (`rename(index.prev → index.bin, .exclusive)`) (ADR-050).
5. `rename(index.tmp → index.bin, .replacing)`; when it fails after step 4 moved `index.bin`, step 4 is undone (`rename(index.prev → index.bin, .exclusive)`, so nothing that did reach `index.bin` is overwritten): `index.bin` is never missing after a failed commit (ADR-050).
6. `synchronizeDirectory(root, .barrier)` (ordered) or `.full` plus `ZTronAssetKit` and `<base>` (durable).

The generation is allocated **when the state is captured**, before the unit is submitted, and is incremented for every attempt (store-1 S1-16, store-2 S2-13). DOOMED is derived inside the commit unit from the blob table captured with the state (C2), including the doom of every key whose deletion unit is in flight (`deletingDooms`) and of every key under replacement (`replacingDooms`: `live` in the table while a verified file replaces a `purged`/`corrupt` name, so a crash before that rename never adopts the rotten bytes; B-24) (ADR-018 as amended by ADR-050). Commits are coalesced to ≤ 4/s; the last commit of a run flushes as soon as the window allows (P-11 tail, transport RK-4). On ENOSPC at step 2 the fallback of step 2 runs and the write is retried once; the in-memory state stays authoritative and deletions that need the newer generation wait (ADR-050). The store carries which index name holds the committed generation (`CommitBookkeeping.committedFile`): set from the load's full validation once `open()`'s root barrier succeeded, `index.bin` after a successful commit or durable promotion, and followed through every rename a unit makes (a file renamed over it, or an `index.bin` that vanished, drops it). Nothing counts as committed until a root sync ordered the names the load read (the barrier, or a commit's step 6; B-36). The scheduled commit (`nextDeadline()`, `runDueWork()`) backs off after failed attempts: it opens at `lastAttemptAt + min(300 s, commitMinimumInterval × 2^failures)`; explicit callers (`requireCommitted`, hence `flush`, `apply`, `admit`, `markSynced`, `markSyncDue`, `adoptionReport` and checksum-less or rescue publications) wait only for the coalescing window, and `close()` commits durably at once; none waits for the backoff; only the first failure of a streak logs an error (B-29) (ADR-050).

### 4.2 Load rule
Read `index.bin`, `index.tmp`, `index.prev` in ≤ 1 MiB units; validate size (`64 + bodyLength + 32` exactly, after checking `bodyLength ≤ 64 MiB`), magic, schema and trailer; never trap (store-1 S1-04); a stat or read of an index file that fails with an error (a read that returns fewer bytes is torn, not an error) names the file unreadable; the launch is then degraded and read-only (§4.5): it commits nothing in that lifetime, every writing API throws `storageUnavailable(.ioFailure)`, and a later launch reads again (B-34; ADR-050). `nextGeneration = 1 + max(generation, launch epoch)` over headers that parsed (either ≥ 2⁶² makes the header malformed; ADR-050), computed with `addingReportingOverflow` (unreachable, since a header at or above 2⁶² does not parse; an overflow would saturate at that ceiling; ADR-050). Choose the newest valid generation; candidates whose `storeID` differs from the newest valid one's are ignored; when the chosen file is `index.tmp`, the committed generation is the newest valid one outside it (`survivingGeneration`) until a commit promotes it (§4.1 step 0) (ADR-050). `degraded` when none is valid, when `index.bin` exists but is invalid, when any candidate has a newer schema, when no index file exists but `blobs/` holds blobs, when the chosen generation carries the degraded flag, or when an index file was unreadable (B-6, B-34; ADR-050). In degraded mode the reaper deletes nothing at all (the doom set itself is untrusted, B-6) and orphans are protected until the next `apply` plus adoption (store-1 S1-11; ADR-050). At load, `DOOMED := DOOMED \ referenced` and the repair is counted. Per-entry quarantine diagnostics are not persisted: after a reload `ValidatedManifest.quarantined == []` while `quarantinedCount` is kept, so a diagnostic report built after a relaunch shows the count only (B-4; ADR-050).

### 4.3 Publication (R-STO-3, R-INT-1/2/6)
`publish(staged, binding: ids, expecting: identity, urgency: lane)`: (1) ids are validated one by one before any hashing: unknown and changed ids are skipped; `.unknownAsset`, `.assetFailed` or `.superseded` is thrown only when none remains; the returned dictionary lists the ids bound (B-11; ADR-050; sync.md X-3); (2) claim: `rename(.part → .verifying, .exclusive)`; (3) size check against `byteSize` and the cap, without hashing; (4) streaming SHA-256 in ≤ 1 MiB units on the bulk executor, cancellation-aware; (5) compare with the checksum (or record the digest for checksum-less entries, R-INT-5/6); (6) `removeItem(.resume)`; (7) `acquireReference(key)` (ADR-018: awaits an in-flight publication or deletion of the same key, rescues `doomed(.unreferenced)`, dedupes onto `live`); (8) barrier `.verifying`, create the fan-out, `rename(.verifying → blob, .exclusive)` (EEXIST: compare sizes; a `corrupt` key is replaced with `.replacing`); (9) after every await re-validate the records' identity: on a change throw `.superseded`, never return a URL (store-2 S2-15); (10) records `present`, integrity history cleared, `markDirty(.soon)`, snapshot published at the caller's `urgency` (§5). Steps 7–10 are `adoptVerifiedFile(at:digest:byteCount:for:)`, which legacy migration reuses (§1.1). Ids sharing a checksum but not an extension get one blob per extension: the destination key is acquired first, a live or rescuable one is bound in place, otherwise the placed blob is copied to a `.parttmp` of the store's own, verified and placed (B-11, B-18; ADR-050). The cap of step 3 is `StoreConfiguration.limits.maxAssetBytes` (`.oversize`, fed from `AssetClientConfiguration.limits`, ADR-048). Checksum-less and rescue publishes are committed before they return (store-1 S1-05); they share the ≤ 4/s coalescing window, so a checksum-less bulk sync publishes at most `concurrency × 4` assets per second (B-7, accepted for the legacy tier; a note for WP-F, ADR-050). Integrity failures delete the staged bytes, count `StoreMetrics.integrityFailures` and throw `.integrity`; the engine then persists the R-INT-3 bookkeeping through `recordIntegrityFailure`, one path for transport and store failures (ADR-032 as amended in round 3), so `publish` (WP-B) never calls a WP-C stub.

### 4.4 Deletion and the I-3 protocol (H-2; ADR-016, ADR-017, ADR-018, ADR-022)
`deletable(k)` ⇔ `doomed(k)` ∧ an acknowledged snapshot **of this epoch** without `k` exists ∧ `uptimeNow ≥ ackUptime + deletionGrace` ∧ the generation that dropped `k` is committed (counted only once a root sync ordered it, B-36) ∧ no lease ∧ no publication of `k` in flight ∧ a fresh no-op install after the deadline was acknowledged ∧ the store is neither degraded (B-6) nor unavailable (`rootVanished`, B-15; an unreadable index file, B-34) (ADR-050). A fresh install started after the deadline that comes back unacknowledged leaves the key acknowledgement-blocked with no deadline; every later `runDueWork()` retries the fresh install (B-8; ADR-050). Only time-blocked keys contribute to `nextDeadline()`; lease release, acknowledgement and commit completion re-arm the engine's alarm. The machinery (blob table, `deletable`, reap batches in `runDueWork()` and `reapDeletable(maxKeys:)`) is WP-B's; the lease condition reads `state.cleanup.leases`, which WP-C's `acquireLease`/`releaseLease` maintain (§1.1). Unlinks run in sorted order in units of at most 64 (`deletionBatchSize`) and at most `BlobDeletionUnit.budget` (1 ms) of the injected monotonic clock: a unit makes at least one unlink and, before each later one, stops when the time spent plus the slowest unlink it has seen would pass the budget; the keys it did not attempt go first into the next unit, unchanged (no backoff) (B-10; ADR-050). A failed unlink keeps the key doomed with backoff. Launch DOOMED keys (from a previous instance) enter the blob table as doomed and wait for the first ack plus grace (store-2 S2-07). Doom reasons `purged` and `corrupt` are never re-adopted or rescued. An orphan doomed by orphan GC (`doomOrphans`, never in any snapshot) carries `eligibleAt` = doom time + `deletionGrace` on the awake clock instead of an acknowledgement's, and still needs a fresh acknowledged install after that deadline, no lease and a store neither degraded nor unavailable; a publication (`acquireReference`) or an adoption before the reap rescues it. It is the only doom whose grace starts at the doom, and orphan GC's reap window relies on that (C-23, ruling R2; ADR-052).

### 4.5 Launch (store.md §2.6 as amended; ADR-028, ADR-029)
`open()`: resolve the base and create `ZTronAssetKit` and `v1` (syncing `<base>` after creating the container) → lock → apply attributes, create `blobs/`, `staging/` → load (§4.2) → list blobs (256 units) → **list nothing in staging yet** → reconcile records: a present record whose blob is missing or the wrong size becomes `needsHeal` and the bad name is doomed `corrupt`; a listed blob whose key is live, unreferenced, or doomed `unreferenced` (rescued) — never doomed `purged` or `corrupt` — is bound to every record that expects it (with its expected size) and accepts adoption: `absent(neverFetched|evicted|healing)`, `needsHeal` or stale (adoption dirties the fan-out); `apply`'s and `admit`'s adoption bind by the same rule except `absent(.evicted)`, which only the launch adoption takes (`ApplyPlan` does not list such records and `adoptKnownBlob` refuses them, so neither can undo an eviction; ruling R3, OI-15: kept literal at L3, so an evicted record whose new content is already live elsewhere is downloaded again), and `apply` binds a launch orphan only while `state.core.orphans[key]` still equals the size its re-stat confirmed (ruling R1) (B-12; ADR-050, ADR-052) → OS-purge detection resets the stamp (R-CLN-7) → legacy phase 1 (WP-C's `runLegacyPhaseOne()` hook, only when `configuration.legacy.enabled`, §1.1) → root barrier (the loaded generation counts as committed, in the file the load validated, only once this barrier succeeded; B-36) → the launch commit, ordered and made by every `open()` (it carries the launch epoch and promotes a loaded `index.tmp`, §4.1 step 0; a failure leaves the store open on the loaded state with the commit due), skipped when an index file was unreadable: that lifetime is read-only and degraded (B-34) → publish the first snapshot → delete foreign names under `blobs/` (ADR-050). Staging is listed only by the engine's launch reconciliation (§6.4), and collected after it.

**Launch epoch (ADR-050; B-5, B-34, B-36).** The launch epoch is the generation the launch commit carries. It is unique only across launches whose launch commit succeeded over a readable index: a read-only launch (B-34) computes `nextGeneration` without the header it could not read and may take the previous launch's epoch, and after a launch whose root barrier and launch commit both failed (B-36) a power loss can bring back older names, so a later launch may take that epoch again (a wiped root also starts again at 1). L3's staging reconciliation and staging GC (WP-C, WP-F) therefore never take epoch equality alone for "this launch" (or the engine stages nothing while the store is `storageUnavailable(.ioFailure)`); exclusive renames report `nameInUse` on a collision (ADR-013 as amended).

### 4.6 Cleanup and space (R-CLN-*)
Prune; orphan GC (`orphanGrace`; ADR-052, C-23): one run at a time (a concurrent call returns an empty result); after a full listing it decides off the actor; a key is swept only if unknown to the blob table and `publishing` both before the first listing unit and after the listing, expected by no record and older than `orphanGrace`, the store neither degraded nor unavailable; swept keys are **doomed** `unreferenced` (`doomOrphans`, §4.4), not unlinked, in chunks of 1,000 with a no-op metadata unit between, each chunk only while the reap window is closed (else the run stops and the next collects, OI-12); the reaper unlinks them under §4.4 and a publication or adoption rescues them; the result, `gcBytes` and the stamp count bytes released to the reaper. Staging GC (`stagingClaimGrace`, `stagingMaxAge`; ADR-052, C-9): the caller's claims only, a name of ours older than `stagingMaxAge` goes even when claimed, foreign names and non-files at once, launch epochs never compared. Quota eviction (ADR-052; C-1, C-2, C-3, C-21): candidates are blobs, evicted with all their records; entries outside the retention scope first, then LRU; a run evicts to make room only when `StoragePolicy.evictionPermitted`, ADR-048, while maintenance quota eviction always runs; ties larger first, then key (hash, then extension); never essential, pinned, leased, being placed or accessed within `max(minimumResidency, deletionGrace)`; the need is `bytesToFree(used, available, pendingReclaim)`: the budget resolved over usage + free space + pending reclaim, triggering when usage exceeds it or free space + pending reclaim is below the reserve, evicting down to `min(hysteresis × budget, used − reserve shortfall)` (store-2 S2-06, C-2; `FreeSpace.budgetBytes` (WP-B, reported) resolves without the pending reclaim, so the two differ for a fractional budget); candidates are computed off the actor and marked in chunks of whole blobs up to `EvictionState.chunk` (1,000) records with a no-op metadata unit between, each re-validated against its holders read with at most one scan of the records per turn; every byte any eviction, `apply`'s plan, a purge, a quarantine, a recorded failure or a record's last integrity failure released since the run measured counts toward its need (`EvictionState.releasedBytes`, C-2 cycles 6–7, ruling R7; residual: `apply`'s prune, OI-14); Apple-adopted assets are not ranked after ordinary ones (records carry no tier, C-6); the result counts bytes released to the reaper (C-3). `apply` evicts an eviction plan larger than `EvictionState.chunk` records one chunk of whole blobs per actor turn behind its write fence, through the unchanged hook `applyEviction(_:)`, which re-validates each chunk's victims in that chunk's turn; the bytes each chunk dooms count toward a running maintenance eviction's need (ruling R6, row c-8; ADR-052). Purge (ADR-052, C-5): `purgeEpoch` bumped and the stamp cleared with `syncDue` set before its first own await, both again in the turn of the last chunk; the selection is grouped and sorted off the actor and applied in chunks that end at blob boundaries (an `.evictable` blob is skipped whole when a current holder became essential or pinned or the blob leased or being placed); it returns after the selection is reaped, rescued or deferred by a lease, its reclaim pass chunked, also waiting (key waiters) for a blob of its selection that another reaper run is deleting; a purge during legacy migration leaves records still waiting for a legacy file (`absent(.neverFetched)`) to later batches. Quarantine (`corrupt` doom). Deep verification (ADR-052, C-8): cursor by `verifiedAt`, the pass tracked in memory, the due list built off the actor; a hash whose blob incarnation changed is discarded and the key stays due. `lastCleanupAt` is stamped only by a run that changed something (C-4; ADR-052). Every operation is idempotent and cancellation-safe (store.md §6.9).

### 4.6a Retention scope and the adoption report (H-7; ADR-027)
`setRetentionScope(_:)` (in-memory, any phase, starts as `.all`, pushed by the engine after `open()` and on every app change) orders eviction and defines `AdoptionReport.excludedRemotePaths`; it deletes and fetches nothing. `adoptionReport()` is atomic: it captures the applied manifest's remote paths, the present-at-current-content records and the exclusions synchronously, commits the holding generation **durably**, and returns only what it captured (REENTRANCY R15), so a pack is released only for adoptions that survive power loss (store-1 S1-10).

### 4.7 Legacy migration (H-10; ADR-029)
Phase 1 inside `open()` through the `runLegacyPhaseOne()` hook (plan from `manifest.json` and `local-checksums.json` decoded under `StoreConfiguration.limits` with duplicates kept first, driven by a **non-following** recursive listing; entries matched against listed regular files, store-2 S2-10; duplicates keep the first; one ordered commit). Phase 1 installs the legacy manifest as the applied manifest (no ETag) while none is applied and inserts `absent(.neverFetched)` records with `expectedBlob` for ids the index lacks; an undecodable legacy manifest sets `degraded` instead (§1.1 rule 1, round 4). Phase 2 after `open()` in engine-owned batches (`migrateLegacy(maxFiles:)`, hashing with `hashFile(at:)` and adopting with `adoptVerifiedFile`, §1.1), with adopt-on-demand for a resolve or lease (`adoptLegacyNow`). Phase 3 sets the stamp (every entry adopted) or `syncDue`, then commits durably; phase 4 tree removal, then the key. The stamp migrates only when every legacy entry was adopted.

**Level-3 amendments (ADR-052; C-12…C-15, C-24, rulings R5, R9).** (1) Phase 1 is skipped (nothing written, the stamp kept) when the lifetime cannot write, the root cannot be stat-ed, or the root overlaps the store's directory (path and identity comparison, the `storeHolds` walk and `reachesStore`; fan-out directories of `blobs/` are excluded as harmless; C-13). (2) An I/O error on a stat, on a read of `manifest.json` or `local-checksums.json`, a short chunk read or a listing (or either stat of a listing unit) decides nothing in that lifetime: no write, no commit, no phase change, the key kept (C-13). (3) Decoding, planning, phase 1's record writes and the reversed queue are built in one bulk unit from snapshots and assigned whole while `opening` (C-24). (4) An undecodable or unusable legacy manifest degrades the launch and adopts nothing, and its files stay in place (C-13); a checksum-less entry without a local checksum is dropped (C-12); both are deviations, NEEDS-HUMAN-REVIEW. (5) Phase 2 commits the phase-1 plan before the first move; a file-system error other than not-found or cross-device, or a full volume, defers the file (back to the head of the queue, the batch ends); after 3 deferrals in one lifetime the file is kept in place, counted dropped and excluded from phase 4 (C-14 cycle 2); a root on another volume is dropped (C-14); both NEEDS-HUMAN-REVIEW. (6) Phase 3 migrates the stamp only when the applied manifest is still the one phase 1 decoded (`manifestDigest`) and every legacy entry is present, never over a stamp the engine wrote; its check runs in chunks of 5,000 entries under `commits.mutationSerial`, and after 3 interrupted passes the call decides nothing (`remaining == 0`, `finished == false`) (C-15, C-24). (7) Phase `done` is committed durably before phase 4 on every call; phase 4 removes only what the prior art wrote (the entries' files, `local-checksums.json`, the entries' directories deepest first, `manifest.json` last, the root only if empty; never recursively, never a kept file, nothing after a failed read or listing), then the key, only once the tree is done (C-15, NEEDS-HUMAN-REVIEW). (8) The caller (WP-F) calls `migrateLegacy` again while `!progress.finished`, backing off (for example to the next maintenance window) when a call returns `remaining == 0 && !finished` (ruling R9; RE-S29).

## 5. Snapshot and the main-actor mirror (R-STO-13; ADR-016)

`AssetSnapshot` (`package`) holds only present assets with precomputed `AssetLocation`s; lookup is one dictionary probe plus a case-insensitive extension match. `SnapshotMirror.install` swaps only for a greater `SnapshotKey(epoch, version)` and returns `InstallAck { installed, accesses, retired }`; the store counts an acknowledgement only when the sink swapped in exactly the offered snapshot of its own epoch (`retired != nil` and `installed == offered`); a refusal never counts, even in favour of a newer snapshot of the same store (B-17; ADR-050); `retired` lets the store release the replaced snapshot off the main actor (sync-2 S2-12); `reset()` is explicit: at shutdown, and by the facade after a `rootVanished` reopen, before the replacement store's first install (B-17; WP-G): a replacement store's epoch comes from the index files alone and can repeat or be smaller than the mirror's, so without the reset readers keep the old store's snapshot (ADR-050). The engine never hands out a URL derived from a snapshot copy (store-2 S2-12).

**Install rate (S2-12, P-8; ADR-016 as amended in round 3).** The store is the only caller of `SnapshotSink.install`. `publish(_:binding:expecting:urgency:)` takes the lane of the work that produced the file: `.userInitiated` installs before `publish` returns; `.prefetch` and `.bulk` install at most once per `StoreConfiguration.snapshotInstallInterval` (from `SyncTuning.snapshotInstallInterval`, default 0.1 s ⇒ ≤ 10 Hz, clamped to ≥ 0 by `SyncTuning.clamped()`, passed by `AssetClient.storeConfiguration(for:)`). A publication inside the window marks a trailing install due: `nextDeadline()` reports `lastInstall + interval`, the engine's alarm calls `runDueWork()`, which installs and reports `StoreWorkReport.installedSnapshot` (ADR-022). A user-initiated install also flushes any pending bulk changes (it is a whole-state snapshot). `apply`, `purge`, `reportUnreadable` and `adoptLegacyNow` install at once; migration batches at bulk urgency. A 10,000-asset bulk sync therefore costs at most 10 snapshot builds and main-actor hops per second instead of one per commit, while the page the user just opened appears at once; the returned `AssetLocation`s come from actor state either way (ADR-016). Regression test: `R-STO-13: bulk publishes install at most one snapshot per snapshotInstallInterval and a user-initiated publish installs at once` (WP-B).

## 6. Transport and the Apple tier (WP-D, WP-E)

### 6.1 Sessions (R-NET-2, ADR-019)
**WP-D owns every body in `ZTronAssetTransport`**, including those implemented in Stage 1 (`HTTPRemoteSource`'s initialisers, `SessionDelegate.init`, `ForegroundTransferBackend.init`/`deinit`/`makeConfiguration`, `makeBackgroundBackend`); it changes no signature. One ephemeral, cache-less foreground session per `HTTPRemoteSource`, built in `start()`; `httpMaximumConnectionsPerHost` clamped 1…8 (P-10); no `httpAdditionalHeaders`; `waitsForConnectivity = false`; request timeout on the session **and** every request. Data tasks; the stateless `SessionDelegate` (immutable `let`s, `Sendable` without escapes) appends each chunk into staging through `StagingSink` on the delegate queue; per-task routing through the task's `TaskMailbox`. **Per-task decisions live on the task (D-1; ADR-050):** before `cancel()` the delegate writes a `TaskMarker` (`ztak-marker <verdict>`) into `taskDescription`, an atomic `copy` property (NSURLSession.h:785) that is free on foreground tasks because they route through their mailbox. Delegate verdicts (`oversize`, `exceeds`, `staging`, `range`, `final`, `nothttp`) overwrite a `pause` or an earlier verdict but never a `discard`; a `pause` (and the `discard` of a terminated consumer stream) is written only onto an unmarked task; the client's `discard` replaces only a `pause`. The completion honours the marker whatever ended the task: `discard` is always `cancelled(.byClient)` with no sidecar, and a verdict is applied before the URL error is classified. A handle's `cancel()` marks `discard`, discards the partial in one short task and only then cancels the task, so `cancelled(.byClient)` follows the discard; a `cancel()` on a completed task does nothing. **Task creation and invalidation meet on one `SessionGate` actor per backend (D-11):** `start` creates the data task with its priority, expected size, stream termination and mailbox inside the gate and is refused (an already-terminal `cancelled(.byClient)` handle) once invalidation began; `invalidate` calls `invalidateAndCancel()` once and one task reads `sessionEvents` to `.invalidated`, resuming every waiting caller. The production source builds the backend with the package initialiser `ForegroundTransferBackend.init(delegate:maxConnectionsPerHost:requestTimeout:appKey:log:)`; the public initialiser builds a keyless request factory (D-7). `invalidate()` returns after the foreground delegate's last callback (transport-2 T2-04), which is what keeps staging writes from landing after `store.close()`: `StagingSink` is immutable and promises nothing after close (ADR-039); `deinit` invalidates too (T2-19). **Session-level events** have no task mailbox: each `SessionDelegate` creates, in its `init`, one `AsyncStream<SessionEvent>` (`package let sessionEvents`) and its continuation (`sessionEventSink`, internal), both `Sendable`, so the delegate stays escape-free (round 3; it compiles in this round's debug, release and iOS builds under `-warnings-as-errors`). `didBecomeInvalidWithError` yields `.invalidated`, which `ForegroundTransferBackend.invalidate()` awaits; in `.background` mode the download-completion and `urlSessionDidFinishEvents` callbacks yield `.finished` and `.backgroundEventsFinished`. WP-D adds the delegate methods in `Session/`. The source logs `transport` lines through its `log: LogRoute` (ADR-047).

### 6.2 Redirects and the key (R-NET-4, R-SEC-1)
`RedirectPolicy.decide`: refuse past 5 hops, refuse non-HTTPS (plain HTTP only for loopback under the package-only `loopbackTesting` policy), refuse hosts outside the allow-list; keep the key only while every hop stays on the original origin, never re-add it. The key is attached per request by the request factory after `TransportSecurityPolicy.check`. A 403 after we withheld the key is `rejected(.keyWithheldOnRedirect)` (transport-1 TR1-6). No `URLRequest`, `URLResponse`, `URLError` or `NSError` is stored in any error, event, report or log; only `ResponseFacts`. On the background path the coordinator's request factory carries the key only when `keyRedirectExposure == .acceptedByOwner` (`makeBackgroundBackend` passes `nil` otherwise), independently of routing, which keeps every key-bearing request in the foreground under `.refuse`; so no background request can carry the key under the default even if a routing defect sent one there. The OS follows background redirects without asking, so a finished background download whose final origin differs from its original one is refused as `redirectRefused(.unenforceableInBackground)` and nothing is adopted (D-7; ADR-026 as amended by ADR-050).

### 6.3 Manifest, size, resume (R-NET-5/7/8)
Conditional GET with `If-None-Match`, 304 → `notModified`, never a cache answer; the 32 MiB cap enforced while streaming. `SizeGuard.verdict` aborts on written > cap, announced > cap + slack, or written > `byteSize` (TR1-8); the staged size is compared with `byteSize`, never `Content-Length`. Resume (ADR-050; D-2…D-5): `Range: bytes=<offset>-` + `If-Range: <strong ETag | Last-Modified>` from our sidecar. A sidecar is written (pause, connection loss or timeout) only for checksummed content, only after a 200/206 that carried a strong `ETag` or a `Last-Modified` (1…256 printable bytes), and only when the partial holds bytes; `paused(resumable:)` and `connectionLost(resumable:)` report whether it was written (D-5). The staged size and the sidecar's size are read back from staging, never counted in memory (D-2). A 206 to a resumed request continues the earlier partial only when its `Content-Range` starts at the offset and the partial (moved with `continuePartial`) is exactly that long; a 206 without `Content-Range`, another start or a vanished earlier partial is `transient(.resumeRejected)`, as are −1002 and 416 on a resumed request; a 200 answering a resumed request (validator changed) takes over the old partial's name and restarts it from zero (D-3; TR1-4, T2-07, T2-08). A 206 or 416 to a request that did not resume is `rejected(.unexpectedStatus)` (the engine retries `resumeRejected` at once, so this avoids a loop, D-4); a 3xx delivered as final is `redirectRefused(reason)` recomputed from `Location` and the hop count, `.invalidLocation` without a usable `Location`; any other 1xx/2xx is `unexpectedStatus`. The announced length is `nil` under any `Content-Encoding` other than identity and offset + `Content-Length` (saturating) for a 206; non-success bodies are counted, never staged, and past 64 KiB the task is stopped and still classified by status. Checksum-less transfers are never resumed (TR1-3), on either path. Resumed bytes are always hashed. Background continuations of URLSession resume data: §6.4.

### 6.4 Background session and launch reconciliation (R-NET-3, H-6; ADR-026, ADR-028)
Off by default; bulk and key-free only unless the owner accepts redirect exposure. **Production wiring (L2, ruling D-14.1; ADR-050):** `HTTPRemoteSource(configuration:staging:log:)` builds its background backend with `makeBackgroundBackend(_:staging:policy:appKey:requestTimeout:log:makeDriver:)` (every added parameter defaulted, so the contract call `makeBackgroundBackend(_:staging:policy:)` is unchanged; `makeDriver` defaults to `LiveBackgroundSessionDriver` and lets tests pass a fake): `nil` for `.disabled` or an invalid namespace, else a `BackgroundTransferCoordinator(driver:staging:options:policy:appKey:requestTimeout:log:)` over that driver and its own `.background` `SessionDelegate`; the key reaches it only under `.acceptedByOwner` (§6.2); building it creates no `URLSession` (the driver's `activate()` does, after the store opened, ADR-028). WP-D owns the coordinator's and the driver's bodies. The device-only driver (`BackgroundSessionBackend.swift`, ≤ 250 lines, excluded from coverage) is decision-free; the coordinator, tag codec, reconciler and relay are tested on macOS with `FakeBackgroundSessionDriver`. Launch order: open → source → `reattachedTransfers()` (which activates the background session itself: the coordinator calls `driver.activate()` before snapshotting tasks; `RemoteSource` has no `activate` member) → `stagingInventory()` → `TransferReconciler.plan(live:staged:wanted:)` (`wanted` = applied entries not present) → execute → `collectStaging(keeping:)`. `AssetClient.handleBackgroundEvents` stores UIKit's handler in the relay and completes it after the engine reports the session's preceding events staged (at once after shutdown). Shutdown releases the background session without waiting for the OS's tasks (`finishTasksAndInvalidate`); invalidation itself cancels no OS task, but the engine cancels its drivers before `remote.invalidate()` (ADR-039) and terminating a background handle's stream cancels its OS task (the Model's drop-to-cancel rule), so an explicit `shutdown()` cancels in-flight background downloads (best effort: a cancellation hop that reaches the coordinator after `invalidate()` began cancels nothing), while a killed or suspended process cancels nothing (D-10, **NEEDS-HUMAN-REVIEW**; ADR-039 as amended by ADR-050); a file the OS moves into staging after close is an ordinary staged file for the next launch's reconciliation (ADR-039).

**Routing (ADR-026 as amended; D-8, D-15, D-19.4; ADR-050).** `HTTPRemoteSource.transfer` uses the background backend only for `.backgroundEligible` + `.bulk` + `.asset` requests without a Range resume, whose `byteSize` is known, ≥ 0 and ≤ the cap (`TransferJob.backgroundByteSize`: the OS downloads a background task whole, so only the staged size can be checked), that carry no key unless the owner accepted redirect exposure, and that the coordinator admits through `startIfAdmitted(_:)`, which checks the cap and reserves a slot in one actor turn (not disabled for the process by −995/−996/−997, not invalidated, live + reserved < `maxTasks`, re-attached tasks included, T2-17); `nil` sends the transfer to the foreground and leaves background enabled. **Coordinator (D-9).** Attach-or-create by content: a buffered staged outcome of the job's `byteSize`, else the newest live OS task for that content that no cancel or pause is ending and whose terminal was not processed, else a new tagged download; a new download whose attempt name is still attached or being cancelled is refused `localIO(EEXIST)`; a joined task's staged file of another size is delivered `integrity(.truncated)`/`integrity(.sizeMismatch)` and stays in staging for the engine's discard or staging GC. Controls act only while the handle's attach token still holds the name. Unclaimed successes are buffered (oldest dropped past `maxTasks`, files left for reconciliation), unclaimed failures dropped; `reattached()` reports live tasks (`isRunning: true` for running and suspended) plus the buffered outcomes and hands those over. A download finished while the app was dead is reported by `reattached()` deterministically only in the background-relaunch case; on a foreground launch it is best-effort and the store's staging inventory adopts the file anyway (ADR-028), so WP-F's end-to-end R-NET-3 test must not depend on `reattached()` reporting it. **Pause and resume (T2-05, ruling D-14.2).** A pause records the intent before `driver.cancel(…, producingResumeData: true)` and ends `paused(resumable: data != nil)`; the data is kept in memory only (newest `maxTasks`) and only for checksummed content (a checksum-less pause reports `resumable: false`); the engine's next attempt of that content continues from it once (`startDownload(…, resumeData:)` → `downloadTask(withResumeData:)`). The task tag `ztak1 <name> <size | -> [resume]` records a continuation (`BackgroundTaskTag.forStart`, both drivers), so in every process the background delegate stages a 206 with `Content-Range` only for such a task of checksummed content (as `resumed: true`; the OS's file is the whole body, compared with `byteSize`, hashed at publication) and reads its −1002, 416 or range-less 206 as `resumeRejected`; any other 206 is `unexpectedStatus(206)` (D-19.1, D-19.2).

### 6.5 Reachability and power (R-NET-9)
`LiveDeviceConditionsSource` builds one `ConditionsObservation` actor per `conditions()` call: it owns a `PathObserving` (live: `NWPathMonitor` behind `LivePathObserver`, whose marker `Sendable` conformance is iOS 17+ and not enforced, APPLE-API-VERIFICATION #7) and the power and thermal notification tokens, observed on the injected `center` through an `OperationQueue` over the one serial queue the path observer also uses. The path observer starts before the notification observers, so the first element is the path observer's first delivery; every element is a full snapshot (`.bufferingNewest(1)`); terminating the stream stops the observation. `ConditionsMapping` is pure (implemented, tested). **Test seam (WP-D, implemented; ADR-050):** the package `init(center:makePathObserver:power:)` takes a scripted path observer and power reading, so both halves are driven without the network; `ObservationRegistry` counts active observations (`activeObservations`, `waitForObservations(equalTo:)`, event-driven), so termination is provable; `livePathObserver` lets the required test `R-NET-9: the live conditions source yields the current state first, then on change, without polling` wrap the live observer and assert power readings = path deliveries + posts on the observation's queue (posts go to the source's injected `center`, never `.default`). A notification arriving between `NWPathMonitor.start` and its first update can still read the started monitor's `currentPath` (device-only residual, D-18.5).

### 6.6 Apple tier (R-APL-*, H-7; ADR-027)
Everything runs against `PackBackend`; only `LiveAssetPackBackend.swift` (≤ 250 lines, excluded) imports BackgroundAssets, using the iOS 26.0 surface. The installed catalog is read from the essential pack first; the best-effort update check is then scheduled in a source-owned task, single-flight, and never awaited, and its `removedSources` reach the next fetch, once each, on `notModified` too (T2-14, T2-20, E-3; ADR-050). The digest, `"sha256:<64 lowercase hex>"` with the double quotes included, is the pseudo-ETag (E-2). Assets are streamed into staging and published through the hash path; skew is `transient(.sourceVersionSkew)` (T2-12). `PackReleasePlanner` (implemented) releases a media pack only when every catalog entry in it is adopted in a durably committed generation or excluded by the keep-scope; its inputs come from `AssetStore.adoptionReport()` (§4.6a), the keep-scope being the client's retention scope. A pack is released at most once per pack per catalog generation (the catalog pseudo-ETag) and never re-armed within one (ADR-027 as amended by ADR-050); the release survey runs in the caller's task in slices of 1,000 entries, off the state actor (E-16). A pack id can appear in `ReclaimReport.released` again in a later generation, so the engine treats `released` as "removed now", not as a set it accumulates (E-10). `sourceCopyBytes()` sums `PackBackend.installedBytes` for `StorageReport` (`nil` and negative values count 0; the sum saturates at `Int64.max`) over every media pack holding adopted content in the last `AdoptionReport`, released or not, every pack the source released in this process (a released pack reports no bytes; one that came back after its release, restored by the OS or downloaded again on demand, stays installed, and counted, until a reclaim in a later catalog generation releases it), and every pack whose planned removal has not yet succeeded (this third set lands with the L2 follow-up `wp/l2fu`). The set lives in memory, so a fresh source reports 0 until its first `reclaimSourceCopies` (E-11; ADR-050). BackgroundAssets cannot honour `TransferRequest.access` / `ManifestRequest.access`: the tier ignores them by necessity, and the engine gates Apple-tier dispatch and update-checking manifest fetches on its own `DeviceConditions` (E-17; WP-F; ADR-050). **The package's single `#available`** (all of `Sources/`, `ZTronAssetTestSupport` included, ADR-014) is in `AppleHostedTier.resolve`, which feeds `TierSelection.select` (pure, Model, tested over all 16 inputs).

### 6.7 Loopback server (ADR-011)
An actor over `NWListener` bound to `127.0.0.1`: `requiredLocalEndpoint` 127.0.0.1 with any port and `requiredInterfaceType = .loopback`; `acceptLocalOnly` is deliberately not set, because the iOS Simulator resets every 127.0.0.1 connection to a listener that sets it (probe table in `docs/adr-drafts/ios.md` item 3). The parameters come from the internal `LoopbackHTTPServer.listenerParameters()` and are pinned by `Test support: the listener is bound to 127.0.0.1 on the loopback interface and does not set acceptLocalOnly` and `Test support: a connection to the server's port on ::1 is refused and never reaches the server`; address the server as `127.0.0.1` (`RedirectLoopbackTests` reach it as `localhost` on both platforms, through URLSession's fallback after the refused `::1` attempt, which never reaches `acceptedConnections`: an inference from the pin test and those passing tests, not a separate measurement) (ADR-051). Never RST (non-deterministic, transport.md E-16). When a FIN directly follows the bytes (`closeAfter`), URLSession sometimes reports −1005 before delivering bytes it read (4 of 5 runs at 50 KB; 1 of 4 runs of the R-NET-8 scenario), so a gating test whose outcome depends on how many bytes arrived drops the connection with `stallAfter` + `stop()` after the client reported those bytes; `closeAfter` is used only where the outcome does not depend on the byte count. URLSession holds the first bytes of a response without `Content-Type` (MIME sniffing), so stalls happen after 512 KiB, not 1 byte. Mid-flight states use `stallAfter` + `stop()`; `LiveLoopbackDelay` sleeps only in the P-11 benchmark (ADR-050).

## 7. Sync engine (WP-F)

sync.md is the detailed design; these sections are normative, including every amendment. The defaults referred to as "ARCHITECTURE §7" in `SyncTuning` are those of sync.md §7.1 with the review amendments recorded in ADR-036.

### 7.1 Per-asset state machine (R-SYN-2)

`absent` and `present` are derived from the store; only outstanding work has a job (keyed by `TransferID`, ADR-020). Legal transitions are exactly `JobStateKind.allows(from:to:)` (implemented and tested):

| From | To | Events (sync.md §5.2 rows) |
|---|---|---|
| — (absent) | queued | interest added for an applied or point-admitted entry (T1); quarantined → no job (T2) |
| queued | downloading | dispatched by `pump()` (T3) |
| queued | blocked | lane gated by policy, breaker, throttle or space (T4) |
| downloading | verifying | `.staged` (T5) |
| downloading | failed | `.failed` with a retry disposition (T6) |
| downloading | blocked | offline / space / policy pause (T6, T16 + policy) |
| downloading | queued | `.paused` after preemption, or content superseded (T7, T22) |
| verifying | committing | store verification passed (T8) |
| verifying | failed | integrity failure (T9) |
| verifying | queued | content superseded with interests left (T22) |
| committing | failed | store failure |
| committing | queued | `.superseded` with interests left (T11) |
| failed | queued | alarm, satisfied-path edge, user request (T18–T20) |
| failed | failed | disposition re-armed |
| blocked | queued | the gate admits (T17) |
| blocked | blocked | the reason changed |
| any | — (job removed) | committed → present (T10); last interest left and not verifying/committing (T12, T13); verifying/committing finished with no interest (sync-1 S1-01); pruned (T21); shutdown (T23) |

Removal goes through one synchronous funnel (`retire`): a job with no interest that is not verifying or committing is removed and its driver cancelled; out of verifying/committing with no interest it is removed instead of retried (sync-1 S1-01). Re-attached background transfers get a system interest the first run claims or releases. An illegal transition is a debug assertion and a `MetricsSnapshot.illegalTransitions` increment; every engine test asserts 0. A transfer stream that ends without a terminal element fails the job with `transient(.incompleteCallbackSequence)` (sync-1 S1-11).

### 7.2 Single-flight, interests and continuations (R-SYN-4, R-CAR-4, H-3)

Interests (`InterestToken`) are waiters (`resolve`), groups (prefetch handles, `ensureAvailable`), runs and system interests. A job's lane is the maximum of its interests; withdrawing the highest demotes it (and re-runs admission, sync-1 S1-07). **Every continuation kind** — waiters, groups, runs, `start` and `sync` joiners, `waitUntil` — lives in a token-keyed table and is resumed only through `removeValue`; every table is settled at registration (a run with zero fetches completes at once, sync-1 S1-02), on each transition, on withdrawal, on purge (the active run ends `failed(.cancelled)`) and at shutdown. A caller's cancellation hops to the actor and withdraws only its token; that includes `waitUntil`, a census-style test seam, which ends on its caller's cancellation as TestSupport's census waits do (`CensusWaiting`, l2fu-1; ADR-050). Shared work (start, manifest fetch, runs, store-touching entry points) runs in engine-owned tasks, never in a caller's task (ADR-039).

### 7.3 Planner and stable order (R-SYN-1, R-SYN-8, P-4)

`SyncPlanner.plan(manifest:snapshot:scope:policy:freeSpace:)` is pure: one pass over the manifest (O(1) record probes), one pass over the applied manifest for prunes, a sort of the fetches only. **Fetch order is `(AssetPolicy.rank, manifestIndex)`**: essential before standard before on-demand, then publisher order (the prior art's serial order); relocations, reuses and skips in manifest order; prunes in applied-manifest order. No output depends on dictionary or set iteration. Reconciliation (relocations, reuses, prunes, the adopted manifest) is committed by `AssetStore.apply` before any fetch is enqueued (R-SYN-8); a seeded property test pins `ApplyReport == plan.reconcile` (ADR-030). Planned fetches become jobs only within the pipeline plus `runLookahead` (sync-1 S1-15); the rest stay a cursor into the plan. The merged `apply` diffs against current state and makes no digest comparison; a digest short-circuit, if the engine keeps one, is the engine's, and it stays correct after a point admission: `admit(_:)` sets the applied digest to `AssetStore.admittedDigest(after:revision:)` (SHA-256 of a domain tag, the previous digest and the manifest revision), which no fetched manifest's digest can equal, so the next fetched manifest is always applied (B-30; ADR-050). The planner reads `AssetRecord.isStale`, `referencedBlob` and `expectedKey` (package, B-13).

### 7.4 Lanes, dispatch and promotion (R-SYN-3, H-4)

Three lanes, `userInitiated` (split into `single` before `batch`) > `prefetch` > `bulk`; one slot reserved for user work; bulk ages ahead of prefetch after `bulkAging`. The pipeline cap gates **non-user lanes only** (sync-2 S2-10). Promotion of a running transfer is `handle.setPriority` inside the synchronous `join` (ADR-021); a queued job jumps to the user queue; when no slot is free a lower-lane transfer is preempted with `pause()` (never the breaker's probe). `pump()` loops after marking a victim (sync-1 S1-16). Priority changes are issued before any other start in the same actor turn (sync-1 S1-06). `interactiveConcurrencyAtCritical` caps user work at `.critical` thermal state.

### 7.5 Priority → URLSession (R-NET-10)

| Engine lane | Engine scheduling | `URLSessionTask.priority` | Session |
|---|---|---|---|
| `userInitiated` | first; reserved slot; may preempt a lower lane | `highPriority` = **0.75** | foreground |
| `prefetch` | second | `defaultPriority` = **0.5** | foreground |
| `bulk` | last; ages ahead of prefetch after 30 s | `lowPriority` = **0.25** | foreground; background only under ADR-026 |

Implemented as `AssetPriority.urlSessionTaskPriority` and tested. The priority is a hint; H-4 is guaranteed by the engine's lanes. Effective in-flight transfers per origin stay ≤ `httpMaximumConnectionsPerHost` (≤ 8).

### 7.6 `TransferError` → engine action → `AssetError` (R-NET-6, R-CAR-7)

| `TransferError` | Engine action | Breaker input | `AssetError` to waiters |
|---|---|---|---|
| `offline(reason)` | `failed(.whenOnline)`; re-queued on a satisfied-path edge (R-SYN-13); counts as blocked for run settling | none (a probe returns to half-open) | `.offline` |

| `rejected(violation)` | `failed(.nextRun)`; counted by violation | none | `.serverUnavailable(retryAfter: nil)` |
| `cancelled(.byClient)` | not a failure (T13 or T7) | probe → half-open | `.cancelled` |
| `cancelled(.bySystem)` | re-queued by the next run | probe → half-open | — |

`TransferError.failureClass` and `assetError(now:)` (Model) and `StoreError.assetError` (Storage) implement the right-hand columns and are tested; the engine overrides the two inferences noted (confirmed auth, measured free space).

**What the merged transport guarantees the engine (ADR-050; D-4, D-5, D-9, D-13, D-15, D-18.3).** The transport never answers `resumeRejected` to a request that did not resume (a 206 or 416 there is `rejected(.unexpectedStatus)`), so the immediate fresh attempt cannot loop. `backgroundSessionUnavailable` from −995/−996/−997 disables background in the coordinator itself, so the retry is routed to the foreground; the HTTP source never surfaces it for a job without a background size (`startIfAdmitted` returns `nil` and the transfer runs in the foreground with background left enabled); only a direct `BackgroundTransferCoordinator.start` of such a job, which no production caller makes, answers it with `NSURLErrorUnknown`. A timeout writes a sidecar too while `.timedOut` carries no resumable flag, so the engine looks for a sidecar before the next attempt rather than trusting a flag. A background `integrity(.truncated)` / `integrity(.sizeMismatch)` from a joined task leaves the staged file in staging for the engine's discard or staging GC. A foreground handle's `cancel()` marks `discard`, discards the partial and then cancels the task, so a completion already running may still report `staged` for a file that is gone: publishing a transfer the engine itself cancelled treats `ENOENT` as that cancellation, not as a failure to retry (WP-F).

### 7.7 Circuit breaker (R-SYN-5; ADR-031)

Per origin (`RemoteSource.originID`), a pure value (`CircuitBreaker`) owned by the engine. **Auth:** opens at once on a manifest 403 whose hint is key-rejected; ambiguous object 403s open it after 3 distinct assets with no intervening object success; cooldown 300 s doubling to 3,600 s with keyed jitter. **5xx:** sliding window of 20 outcomes, opens at ≥ 5 samples and ≥ 50 % 5xx; cooldown 30 s doubling to 600 s. **Half-open:** exactly one probe; success closes and resets trips (a cached manifest 304 never counts, sync-2 S2-21); a same-cause failure re-opens with `trips + 1`; **any other exit** (different cause, offline, cancelled, paused, superseded, shutdown) returns to `halfOpen(probe: nil)`; a probe silent for `probeWatchdog` (60 s) is abandoned. While open, `resolve` fails fast and runs end `blocked(.circuitOpen)` with a pending run on close.

### 7.8 Timers and idle silence (R-SYN-14, P-14, H-8; ADR-022)

Deadlines are data in one min-heap `(deadline, seq, reason)`: retries, throttle end, breaker cooldown and probe watchdog, store deadlines (`AssetStore.nextDeadline()`), pending-run debounce. One alarm task exists iff the heap is non-empty; firing drains due entries in `(deadline, seq)` order, re-validating each against epochs, then calls `store.runDueWork()` if a store deadline was due and re-arms. Stale entries are removed eagerly on withdrawal and settle (sync-1 S1-10). The conditions watcher exists iff work exists and is cancelled by the engine when it goes idle. **Idle** = no job, no run, no pending run, empty heap ⇒ `EngineIntrospection.isIdleSilent`, plus the environment census (`ManualTimeSource.pendingSleepers == 0`, `FakeRemoteSource.activeTransfers == 0`, `FakeDeviceConditionsSource.activeObservers == 0`, awaited with `waitForObservers(equalTo:)`). A registered `PurgeableCache` keeps one memory-pressure observer, which is work: R-SYN-14 and P-14 are measured with none registered.

### 7.9 Events and backpressure (R-SYN-12, H-9; ADR-023)

Pull-based per-subscriber queues behind `AsyncStream(unfolding:onCancel:)`; registration on first pull; released on cancel, deinit and shutdown. Progress events coalesce newest-wins per key at ≤ 10 Hz with a trailing emission after a quiet period (sync-2 S2-24). Terminal events coalesce per subject and are never dropped; bulk per-asset outcomes fold into `syncProgress`/`syncFinished`; a pruned id's subject retires with its `assetRemoved`; a transfer's progress key retires with the transfer. `clientShutDown` is delivered last on every path, waiting and lagging subscribers alike.

### 7.10 Runs, space, refresh, purge, maintenance, shutdown

- **Run:** single-flight (`sync()` joiners share the outcome), over the retention scope (ADR-027) → conditional manifest fetch (single-flight with point admission; a point-admission fetch never stores its ETag, sync-2 S2-28) → decode on the bulk executor (P-3, C2) → `freeSpace()` → plan (off-actor) → space decision **before any mutation** → `store.apply(manifest, etag:, eviction:)` → enqueue → settle → `markSynced(_:ifPurgeEpoch:)` only for `.complete`.
- **Space (R-SYN-11, ADR-025):** `available = volume(opportunistic for bulk/prefetch, important for user work) − reserve + pendingReclaim`; `budgetRoom = max(0, budget − (used − pruneBytes))`; a plan with zero fetch bytes always fits (sync-2 S2-06); unknown sizes are not estimated (S2-08); over budget → largest fitting prefix (essential first) or, with the policy off, `insufficientSpace` with zero side effects. Eviction makes room only when `StoragePolicy.evictionPermitted` (default `true`, ADR-048); the engine builds the planner's policy with `PlanningPolicy(storage:includeOnDemand:now:)` (implemented and tested), so the switch, unverified admission and the prefix rule cannot be dropped on the way. Per-fetch headroom ledger counts bytes in flight **and committed since the last free-space read** (S2-09).
- **Unknown ids (prior-art resolver parity):** one single-flight conditional fetch; a waiter is answered from the newest manifest seen (fetched or applied), never `.notFound` while a run's fetch holds a newer one (sync-1 S1-13); negative cache 60 s, LRU-bounded.
- **Refresh (R-SYN-9):** `RefreshDecision.isSyncDue` (implemented, tested). The stamp lives in the index (R-STO-2).
- **Purge (R-CLN-6):** `purgeEpoch` bumped before any await; the active run ends `failed(.cancelled)`; non-user interests on purged ids withdrawn; user waiters re-queue; the store bumps its own `purgeEpoch` and clears the stamp, with `syncDue` set, before its first own await and again in the turn of its last chunk (ADR-052).
- **Maintenance (R-SYN-16):** deadline on the monotonic clock; staging GC → orphan GC → eviction → deep verification in bounded batches; cancellation honoured between batches.
- **What the store's cleanup and migration calls mean for the engine (ADR-052).** `migrateLegacy(maxFiles:)` is called again while `!progress.finished`, with a backoff (for example to the next maintenance window) when a call returns `remaining == 0 && !finished` (RE-S29). `collectStaging(keeping:)` keeps only the engine's claims, so every transfer still worked on is claimed, those with a publication in flight included (R14). Quota eviction's and orphan GC's `bytesFreed`/`filesRemoved` are bytes and blobs released to the reaper, unlinked later by `runDueWork()` (`reapedBytes`); a concurrent `collectGarbage` returns an empty result at once. A purge waits in the caller's task: a caller cancelled during its waits gets `.cancelled` although the purge is committed, bytes a non-acknowledging sink holds back are in neither `bytesFreed` nor `bytesDeferred`, and `purgeEpoch` moves twice when it purged something. An evicted record is re-adopted only at launch, so one whose new content is live in another blob is downloaded again (OI-15). A maintenance eviction overlapping a pruning `apply` can free up to the pruned bytes more than needed (OI-14; an engine that runs maintenance apart from a sync's `apply` never meets it). The synchronous dry run `evictionPlan(toFree:protecting:)` holds the actor about 2.5 ms at 10,000 records and about 38 ms at `maxEntries` (OI-4; an off-actor version is a Stage 3 contract change). Phase 3's durable commit before the `UserDefaults` key removal is shown by code reading only (`FakeFileSystem` makes `.barrier` and `.full` identical, OI-2): no fake test can prove it.
- **Retention scope (R-CAR-5, ADR-027):** `setRetentionScope(_:)` replaces the engine's scope (the next bulk run's) and pushes it to the store in an owned task (RE-S33); it starts no run.
- **Pins (R-CLN-4, ADR-044):** `setPinned(_:pinned:)` through the store in an owned task.
- **Memory pressure (R-CLN-11, ADR-044):** `observeMemoryPressure(epoch:handler:)` starts or stops one owned observer of `AssetEnvironment.memoryPressure`; only the newest epoch applies; the handler (the facade's relay) may stop it from inside; shutdown stops it.
- **Storage report and diagnostics:** `storageReport()` adds `RemoteSource.sourceCopyBytes()` to the store's report (RE-S32); `diagnostics()` returns `EngineDiagnostics` (counters, the last 32 `DiagnosticError`s, app version, launch epoch, generation, stamp, retention scope).
- **Shutdown (R-SYN-15, ADR-039, ADR-042):** see ADR-039's order; `AssetClient.shutdown()` then resets the mirror so `lookup` returns `nil` and closes the cache relay. `AssetClient.deinit` spawns `engine.shutdown()`; shutdown in `created` never opens the store. Afterwards every engine entry point returns `.failure(.shutDown)` (`sync`: `.failed(.shutDown)`; `registerGroup`: holds nothing; a new event stream yields `clientShutDown` and finishes); releases and `shutdown()` are idempotent no-ops.

## 8. Facade (WP-G)

`AssetClient(configuration:environment: AssetEnvironment? = nil)`: resolves a missing environment to `.live(legacyDefaultsSuiteName: configuration.legacy.defaultsSuiteName)` (`resolvedEnvironment(_:for:)`, ADR-048), builds the store's configuration with `storeConfiguration(for:)` (location, policy, legacy layout, manifest limits, clamped snapshot install interval), stores values, creates the mirror, the store and engine actors, the background relay and the purgeable-cache relay; no I/O, no task, no `Bundle`/`UserDefaults` read, no URLSession (P-12, sync-2 S2-18). `start()` is single-flight; every async API awaits it. `lookup` (main actor) reads the mirror only. `resolve` returns a URL; `prefetch` returns a `PrefetchHandle` whose release is ordered after its registration and, for a re-lane, after the successor's registration (`cancel(after:)`), the task holding the old handle until that release ran so its deinit cannot release early (sync-1 S1-05, implemented and tested); `awaitRegistration()` reports `.shutDown`. The handle reaches the engine through `PrefetchRegistry` (`SyncEngine` conforms; tests use a gated fake). `PrefetchWindow.targets` (implemented): current, +1, −1, +2, −2…; `PrefetchWindowController(client:radius: Int? = nil)` defaults its radius to `configuration.prefetchRadius` (ADR-048) and creates the new handle before releasing the old. `withAsset` leases through the engine (so lease release re-arms the alarm). The fallback chain (`AssetFallbackChain`): `prepare(kinds:)` builds the bundle index in one unit on the client's bulk executor (C2, ADR-038); `locate` is bundle → local, synchronous, no file-system work on main; `fetch` is `resolve` plus the candidate-extension check (ADR-037). Retention scope (`configuration.retentionScope`, `setRetentionScope(_:)`), pins (`pin`, `unpin`) and purgeable caches (`register`, `unregister`, main actor, held weakly by `PurgeableCacheRelay`) are ADR-027 and ADR-044. Observability: `AssetLog` lives in the Model (subsystem `com.ztron.assetkit`, categories `store`/`sync`/`transport`/`apple`, `hashed(_:)`, `emit(_:sink:tap:)`), every line to the environment's `LogSink` (`OSLogSink` live, `TapOnlyLogSink` in tests) and to the optional `LogTap` with its subsystem (ADR-043, ADR-047); `DiagnosticReport.indexSchemaVersion` is `StoreLayout.indexSchemaVersion`; `MetricsSnapshot`; `DiagnosticReport` (Codable, no `AppKey`) from `SyncEngine.diagnostics()`. After `shutdown()` every API fails with `.shutDown` as ADR-042 lists. **Replaced root (ADR-050; B-15, B-17):** after `rootVanished` every store commit and mutating API throws `.storageUnavailable(.rootVanished)` while reads keep working; the facade owns the reopen, and calls `SnapshotMirror.reset()` before the replacement store's first install (§5), because the replacement's epoch can repeat or be smaller than the mirror's. SPEC §4.1's "public re-exports" are one `@_exported import ZTronAssetModel` in `AssetClientConfiguration.swift`, so apps import only `ZTronAssetKit` (the only product); it is a compile-time attribute with no runtime effect, not a private API in the sense of R-SEC-3.
