## D-1 — Per-task decisions live on the task: `TaskMarker` in `taskDescription`
- **Context.** `SessionDelegate` holds only `let`s (Sendable without an escape, ARCHITECTURE §6.1), so a decision taken in one callback (size guard, staging failure, range mismatch, a client pause) cannot be remembered in the delegate for `didCompleteWithError`, where a `-999` must be told apart from a client cancellation.
- **Options.** (a) A lock-protected table in the delegate (needs `Mutex`, iOS 18, or an escape). (b) Re-derive the reason at completion from byte counts (transport.md §7.1; impossible for staging failures and range mismatches). (c) Write the verdict onto the task before `cancel()`: `URLSessionTask` is `Sendable` and `taskDescription` is an atomic `copy` property (NSURLSession.h:785); foreground tasks route through their `TaskMailbox`, so the slot is free.
- **Decision.** (c), `TaskMarker` (`ztak-marker <verdict>`). Delegate verdicts (`oversize`, `exceeds`, `staging`, `range`, `final`, `nothttp`) overwrite a `pause` or an earlier verdict but never a `discard`; a `pause` (and the `discard` of a terminated consumer stream) is written only onto an unmarked task; the client's `discard` (handle `cancel()`, `cancel(_:keepingPartial: false)`) replaces only a `pause`. So a verdict is never hidden by a client intent, and a write into a partial the client already discarded (`ENOENT`) can never turn the client's cancellation into `localIO` (review round 1). The completion honours the marker whatever ended the task: `discard` is always `cancelled(.byClient)` (no sidecar), and a verdict stands at any completion that was already queued when its cancel was issued, nil error or not (a `-1005`/`-1001` behind the judged chunk; review round 2): the verdict is applied before the URL error is classified, so a judged transfer never writes a sidecar and a full disk is never reported as a timeout. Only `pause` depends on the error being `-999`. A response that reaches a `discard`ed task opens, moves and truncates nothing (`.cancel`), and a `discard`ed task is not reported by `liveTransfers()` even before its cancellation reaches the task (review round 2). The remaining race (a verdict written between a pause's check and its write) loses the verdict and reports `paused`; the next attempt meets the same verdict. A marked task appends nothing more, except under `pause` (the bytes are valid and keep the resume point longer). Only `encoded` writes markers, so decoding is exact on the verbs and lenient on their numbers (an unparsable number reads as unknown) rather than carrying failure branches no input can reach.
- **Consequences.** No state in the delegate; every decision is visible in tests through behaviour: the precedence tests assert `foregroundOutcome` results, never a decoded marker (review round 3). The codec has one test of its own (`R-NET-6: the task-marker codec round-trips every marker and decodes nothing else`), which also covers the decoder's unknown-verb branch (`ztak-marker bogus` → `nil`). Two defensive lines stay uncovered by design: `redirectDecision`'s guard for a task without an original or current URL (URLSession always has both when it asks about a redirect) and the `@unknown default` of the thermal mapping.

## D-2 — The staged size is read back from staging, never counted in memory
- **Context.** The size compared with `byteSize` must be the bytes on disk (R-NET-7; decoded bytes under gzip), and the delegate keeps no counter.
- **Decision.** At completion the delegate appends an empty `Data` to the partial: `StagingSink.appendPartial` returns the partial's size (one bounded unit on the delegate queue). The same read gives the sidecar's `receivedBytes`.
- **Consequences.** One extra open/seek per completed or paused transfer. Observed: URLSession can report `-1005` before delivering the last bytes it read (1 of 4 runs of the R-NET-8 scenario staged fewer than the 1 MiB the server sent); the sidecar therefore always records what staging holds, and the test asserts the `Range` offset equals it.

## D-3 — Response handling: size guard first, error bodies counted not staged
- **Decision.** In `didReceive response`: a 200, or a 206 to a resumed request, passes `SizeGuard` with the announced length **before** the partial is opened (an announced oversize leaves no file), then opens it: a 206 continues the earlier partial only when `Content-Range` starts at the resume offset **and** the partial (moved with `continuePartial`) is exactly that long, else `resumeRejected` (also when the earlier partial vanished, `ENOENT`: it cannot be continued, and `localIO` would only back off before the same failure); a 200 answering a resumed request (validator changed) takes over the old partial's name and truncates it, so nothing stale is left. Every other status is let through without staging; its body length (`countOfBytesReceived`) is the 403 evidence, and past 64 KiB the task is stopped and still classified by status. The announced length is `nil` under any `Content-Encoding` other than identity, and offset + `Content-Length` for a 206.
- **Consequences.** R-NET-7's "aborted early" holds before any byte is written; gzip responses are judged by decoded bytes only. The per-chunk guard is proven by close-delimited bodies the server stalls on after cap + 256 KiB (or 512 KiB for `byteSize`): only an abort while streaming ends them before the request timeout; with the guard's branches removed all three tests fail (review round 2 mutation run).

## D-4 — Status-table choices left open by transport.md §3.4.1
- **Decision.** A 206 or 416 to a request that did not resume is `rejected(.unexpectedStatus)`, not `resumeRejected` (the engine retries `resumeRejected` at once without backoff, ARCHITECTURE §7.6, so a server answering 416 to plain GETs would loop). A 206 to a resumed request without `Content-Range` is `resumeRejected`. A 3xx delivered as final is `redirectRefused(reason)` with the reason recomputed by `RedirectPolicy` from `Location` and the hop count; without a usable `Location` it is `.invalidLocation`. A 1xx/2xx other than 200/206 is `unexpectedStatus`.

## D-5 — Resume sidecars
- **Decision.** A sidecar is written (one per pause, connection loss or timeout) only for checksummed content (`TransferID.Kind.content`, TR1-3), only after a 200/206 that carried a strong `ETag` or a `Last-Modified` (bounded like an `ETag`: 1…256 printable bytes), and only when the partial holds bytes. `paused(resumable:)` and `connectionLost(resumable:)` report whether it was written. A timeout writes one too (the engine looks for sidecars, `TransientCause.timedOut` has no flag). The resumed request is rebuilt by the request factory with the current key (TR1-5).

## D-6 — URL building mirrors the prior art
- **Context.** TR1-10: join `baseURL` and `remotePath` by path components; the prior art used `baseURL.appendingPathComponent(remotePath)`.
- **Decision.** `RemoteURL.make` appends each `/`-separated component with `appendingPathComponent` (percent-encoding it: a space is `%20`, a literal `%` is `%25`, as before) and rejects empty components, `.`/`..` (also percent-encoded), `?`, `#` and `\` with `rejected(.invalidURL)`. The configured `manifestPath` goes through the same join.
- **Consequences.** A manifest that lists already percent-encoded paths would be double-encoded, exactly as in the prior art.

## D-7 — Where the key lives
- **Context.** `TransferJob` carries no secret, `TransferBackend.start(_:)` takes only the job, and neither `ForegroundTransferBackend.init(delegate:maxConnectionsPerHost:requestTimeout:)` nor `makeBackgroundBackend(_:staging:policy:)` takes the key.
- **Decision.** One internal `RequestFactory` (policy, key, timeout) is the only code that sets the key header, after `TransportSecurityPolicy.check`. The foreground backend gets it through a new package initialiser (the public one builds a keyless factory); the production `HTTPRemoteSource.init(configuration:staging:log:)` calls `makeBackgroundBackend(_:staging:policy:appKey:requestTimeout:log:)` (ruling 1, review round 3), which passes the key to the coordinator **only when** `keyRedirectExposure == .acceptedByOwner`, so under the default `.refuse` no background request can carry it even if a routing defect sent one there. The contract call `makeBackgroundBackend(_:staging:policy:)` takes the defaults (no key) and its existing test is unchanged.
- **Consequences.** The rule is tested through the package function itself with the canary key and a fake driver (`R-NET-4: the production background backend carries the key only when the owner accepted redirect exposure, with the configured timeout and log route`), which needs the defaulted `makeDriver` parameter: the function otherwise builds `LiveBackgroundSessionDriver`, whose session may not be created in tests (ARCHITECTURE §14).

## D-8 — Routing to the background session (ADR-026, transport.md §10.7)
- **Decision.** `HTTPRemoteSource.transfer` uses the background backend only for `.backgroundEligible` + `.bulk` + `.asset` requests without a Range resume (the background session cannot continue our partial), that carry no key unless the owner accepted redirect exposure, and that the coordinator admits (not disabled for the process by −995/−996/−997, not invalidated, fewer live tasks than `maxTasks`, re-attached tasks and admitted starts included, T2-17). Everything else is foreground. **Review round 3:** the cap is now exact. Before, `admits()` and `start` were separate actor calls and `start` awaited the activation and the listing before it attached, so K concurrent `transfer()` calls could all pass the check and reach `maxTasks + K − 1` live tasks (the earlier wording, "exceed it by one", understated this). The source now calls `startIfAdmitted(job)`, which checks the cap and reserves a slot in one actor turn before its first await (`reserved`, counted by `admits()` until the transfer is in `live`); `nil` sends the transfer to the foreground without any failure. Tested with `maxTasks = 1` and three concurrent starts, the first held inside the coordinator (`R-NET-3: concurrent transfers never take more background tasks than the cap`).

## D-9 — The background coordinator
- **Decision.** (1) **Attach-or-create by content:** `start(job)` first hands out a buffered staged outcome for the same `TransferID` (any attempt; the bytes are hashed at publication, transport.md §10.8) when its size is the job's `byteSize` (a checksum-less identity survives a manifest change of its size; a mismatched outcome is dropped, its file left to staging GC, review round 2), then joins the newest live OS task for that content, and only then creates a tagged download. A listed task is joinable only while no cancel or pause is ending it (`cancelling`, counted from before the control's first await until the task's terminal is processed) and its terminal was not processed yet (`processed`, the last `max(4 × maxTasks, 64)` names: a listing goes stale across its await, review round 1). A new download whose very name is still attached or being cancelled is refused as a name clash (`localIO(EEXIST)`), since two OS tasks under one tag would hand one task's terminal to the other's handle. **A join checks the joining job's size (review round 3):** the OS task's tag carries the size its creator expected, which a checksum-less identity may have changed since (a relaunch after a manifest change), so each waiter keeps its job's `byteSize` and a staged file of another size is delivered as `integrity(.truncated)` / `integrity(.sizeMismatch)` (the file stays in staging for the engine's discard or GC); joining is kept for every identity, since refusing it for checksum-less ones would duplicate their downloads after every relaunch (R-NET-3). **Controls per attach:** every attach gets a token; a handle's pause, cancel, priority change and its stream's termination act only while that attach still holds the name, so a handle replaced by a later attach (already ended `cancelled(.byClient)`) never reaches the transfer that replaced it. (2) **Buffer:** unclaimed successes are kept, oldest dropped first, up to `maxTasks` (their files stay in staging for launch reconciliation, ADR-028); unclaimed failures are dropped. (3) **Pause (T2-05):** the intent is recorded before `driver.cancel(…, producingResumeData: true)`; the session's cancellation event becomes `paused(resumable: data != nil)` whichever of the event and the returned data arrives first; the data is kept in memory (`keptResumeData(for:)`), the newest `maxTasks` pauses only (bounded, review round 1), and only for checksummed content: a checksum-less pause keeps nothing and is reported `paused(resumable: false)` (TR1-3, review round 3). The engine's restart of that content (a new attempt) continues from it, once (ruling 2). (4) **Pump (T2-10):** one detached task iterates the session stream only while a waiter whose terminal is still owed by the stream, a known live task or an events waiter exists (a waiter whose cancellation the pump absorbed for a pause waits for the pause's own call, not for the stream, review round 2); it forgets itself when nothing is outstanding, and the next start creates a new one over the same stream (sequential iterators; only concurrent `next()` calls trap). (5) **Launch:** `reattached()` activates the session, cancels foreign or undecodable tasks, and reports live tasks (`isRunning: true` for running **and** suspended tasks, the Model's meaning "not yet completed into staging") plus buffered staged outcomes, built after its last await (a task whose terminal was processed meanwhile is reported once, from the buffer, and never left in `live`). The reported outcomes leave the buffer: launch reconciliation adopts or collects their files (ADR-028), so a later start is never handed a file that may be gone; an outcome that arrives after `reattached()` is still handed to the next start for its content. (6) **Events:** `awaitBackgroundEvents()` returns after `.backgroundEventsFinished` was processed (every preceding event delivered); a `didFinishEvents` that arrives before anybody waits is counted and releases the next wait at once. (7) **Invalidation** releases the session without cancelling the OS's tasks, fails waiting handles with `cancelled(.byClient)`, and makes later starts and controls no-ops.
- **Consequences.** A download finished while the app was dead is reported by `reattached()` once its event was processed; deterministic in the background-relaunch case (events precede `didFinishEvents`), best-effort on a foreground launch, where the store's staging inventory adopts it anyway (ADR-028). "Hook not wired" detection (transport.md §10.7) needs the relay, which lives in Kit (`AssetClient`): left to WP-G, which sees whether a handler was stored.

## D-10 — Background handle controls and stream termination
- **Decision.** `TransferHandle`'s controls are synchronous and the driver is async, so each background control hops to the coordinator in one short-lived unstructured task. Per the Model contract, terminating a background handle's stream before its terminal element cancels the OS task.
- **Consequences.** **NEEDS-HUMAN-REVIEW (owner/orchestrator):** the engine's shutdown cancels its transfer drivers before `remote.invalidate()` (ADR-039), which therefore cancels in-flight background downloads; a killed or suspended process cancels nothing. If background downloads should survive an explicit `shutdown()`, the Model contract ("terminating the stream cancels the transfer") needs a background exception.

## D-11 — Ordering task creation against invalidation (`SessionGate`)
- **Context.** Creating a task on an invalidated `URLSession` raises an Objective-C exception; `invalidate()` must also return only after `.invalidated` (T2-04) whatever the caller's cancellation, and the session stream is single-consumer.
- **Decision.** A small actor per foreground backend: `start` creates its data task inside the gate, together with its priority, expected size, stream termination and `TaskMailbox` (review round 2: a task never exists without its mailbox, so an invalidation right after the gate still ends the stream) (refused once invalidation began, yielding an already-terminal `cancelled(.byClient)` handle); `invalidate` calls `invalidateAndCancel()` once and one unstructured task reads the stream to `.invalidated`, resuming every waiting caller. One actor hop per start.

## D-12 — Conditions: a path seam and an observation census
- **Decision.** `LiveDeviceConditionsSource` builds one `ConditionsObservation` actor per `conditions()` call: power and thermal observers on the injected `center` (an `OperationQueue` over one serial queue) and a `PathObserving` on the same queue; every element is a full snapshot (`.bufferingNewest(1)`). The live path observer wraps `NWPathMonitor` (its marker `Sendable` conformance is iOS 17+ and not enforced, APPLE-API-VERIFICATION §3 #7). A package initialiser takes a scripted path observer and power reading (the §6.5 seam); a registry counts active observations (`waitForObservations(equalTo:)`, event-driven) so termination is provable.

## D-13 — Smaller choices
- `Retry-After`: an RFC 850 two-digit year reads as 2000–2068 / 1969–1999 (Python `email.utils`'s pivot): RFC 9110's "50 years in the future" needs a clock, which the transport never reads (H-8). Names are case-sensitive; the weekday is checked for form only.
- Progress is rate-limited statelessly: first chunk, then one per crossing of `max(256 KiB, expected/64)`.
- The P-10 benchmark (`BenchTransport.swift`) reads `ContinuousClock.now` twice for an elapsed time it only prints: informational, never a budget input and never the wall clock; P-10's gate is the connection count (review round 3).
- **Saturating arithmetic (review round 3).** Every sum over a figure from outside the process is saturated or clamped first, because Swift traps on overflow in every build: a 206's announced total (offset + `Content-Length`) and the size guard's cap plus slack saturate at the bounds of `Int64` (`Saturating.add`), so an extreme value still reads as oversize; a negative configured cap is clamped to 0 when the job is built (`SizeGuard.clampedLimit`); a sidecar's resume offset is clamped into `0…byteSize` before the remainder hint is computed and enters a live transfer's `bytesReceived` only for a 206 (the 200 answering a resumed request restarted the partial); `maxTasks` is clamped before it sizes the processed-name table. Audited and left as they are: `Content-Range` and tag sizes parse at most 19 digits through `Int64(_:)`, which returns `nil` past `Int64.max`; `Retry-After` delta-seconds parse through `UInt32`; HTTP dates read at most four-digit years; the progress quantum divides only; redirect hops, attach tokens and counters are our own small counts. Tests: `ArithmeticSafetyTests` (Int64.max `Content-Length` on a resumed 206 through the loopback server and per chunk, size-guard extremes, `maxBytes` of `Int64.max` and `Int64.min` through a whole transfer, a resume offset of `Int64.min`, `maxTasks = Int.max`, `bytesReceived` for 200 versus 206); each test crashed with SIGTRAP or failed before its fix.
- A consumer that terminates a foreground stream marks the task `discard` (nothing more is appended) and cancels it; `fetchManifest` discards the attempt's partial on every terminal, so a failed or cancelled fetch leaves nothing in staging.
- `cancel(_:keepingPartial: false)` on the foreground backend discards the partial and sidecar after cancelling; a callback already past its marker check may still append once, which staging GC collects (R-CLN-3).
- A foreground handle's `cancel()` stops the task **and discards its partial**, as the Model contract says (review round 1): it marks `discard`, then (in one short task) discards the partial and only then cancels the task, so the terminal element `cancelled(.byClient)` follows the discard. A `cancel()` on a completed task does nothing (a staged file is the engine's). Residual: a completion already running when the mark is written can still report `staged` while the discard proceeds (the staged name is the partial's name, so the engine is told of a file that is gone). **WP-F obligation:** publishing a transfer the engine itself cancelled must treat `ENOENT` as that cancellation, not as a failure to retry.
- Transport log lines carry only class names and byte counts (`manifest fetch failed: transient`); each transfer is one `transfer` interval, begun at start and ended exactly once by the stream's `onTermination` (tested through the tap).
- The redirect hop count is stored with `URLProtocol.setProperty` on `(request as NSURLRequest).mutableCopy() as! NSMutableURLRequest`: `mutableCopy` of an `NSURLRequest` is documented to return the mutable class, and a conditional cast would add a branch no input reaches.
- The staged size and the sidecar's size come from staging (D-2). The per-chunk size guard stops anything past the cap or `byteSize`, and the completion checks the whole staged size again (more than the cap is `oversize`, anything but `byteSize` is `truncated` or `sizeMismatch`), because a completion already queued when the guard's cancel was issued still arrives (review round 1).
- `LiveBackgroundSessionDriver` keeps its session in a private actor (created at most once, never after `invalidate()`, which it orders against task creation); it decodes tags with the tested `BackgroundTaskTag`, labels tasks with `BackgroundTaskTag.label(_:priority:)` and takes its configuration from `BackgroundSessionConfiguration.make(identifier:discretionary:)`, both on the tested side, and makes no other decision (94 executable lines in the coverage export, under the 100-line working ceiling of ARCHITECTURE §14).

## D-15 — R-NET-7 on the background path: only bounded transfers run there
- **Context.** Review round 1: the background path dropped `TransferJob.maxBytes`; with `byteSize` absent (the Model allows it) a background download of any size was adopted and reported staged. The OS downloads a background task whole before a byte reaches us, so the cap can only be checked after the fact, and the tag (written by the decision-free driver from `startDownload(_:name:priority:expectedBytes:)`) has no field for it.
- **Options.** (a) Carry the cap in the tag (`ztak2 …`): the driver builds the tag, so its contract signature would change. (b) Route to the background session only transfers whose `byteSize` is known and ≤ the cap; the delegate already requires the staged size to equal `byteSize`.
- **Decision.** (b). `HTTPRemoteSource.routesToBackground` requires `expectedBytes != nil && expectedBytes <= maxBytes`; the coordinator refuses any other job with `transient(.backgroundSessionUnavailable(urlErrorCode: NSURLErrorUnknown))` (a defence against a routing defect: the engine's action for that error is a foreground retry, ARCHITECTURE §7.6), before activating anything.
- **Consequences.** Entries without `byteSize` always download in the foreground, where the size guard aborts while streaming. A `-` tag can no longer be created by this build; the delegate still stages such a download only when it holds bytes (tested directly). **Review round 3:** the source's path (`startIfAdmitted`) declines an unbounded job with `nil`, so the transfer runs in the foreground and nothing disables background for the process; only a direct `start` (no production caller) still answers `backgroundSessionUnavailable` (see D-18, declined).

## D-16 — Review round 1: dispositions not fixed in code
1. **The §12.5 test name `R-NET-8: a refused or invalid resume discards the partial and restarts from zero in the next attempt`** is not taken by WP-D: the discard on `resumeRejected` is the engine's action (ARCHITECTURE §7.6, "discard partial and sidecar; immediate fresh attempt"), not the transport's; a delegate callback cannot await `StagingSink.discard`. WP-D's test `R-NET-8: a refused or invalid resume yields resumeRejected and a fresh attempt stages the whole body` now asserts the transport's half: nothing is appended to a refused partial, a 416 leaves the earlier partial untouched under its own name, a too-short partial is left exactly as it was under the attempt's name (exclusive rename), and the fresh attempt sends no `Range`. The orchestrator should assign the §12.5 name to WP-F, which discards both names.
2. **Background pause `resumable`** stays `paused(resumable: data != nil)` as T2-05 and its regression test name require; the kept data cannot be used until `startDownload` takes it (D-14 #2), which is an orchestrator decision. The kept data is now bounded (`maxTasks` entries). *Resolved in review round 3 by ruling 2: the restart continues from the data; a checksum-less pause keeps none and reports `resumable: false`.*
3. **Package additions to contract files** are listed at the top of this file for acknowledgement; nothing else changed in them.

## D-14 — Contract proposals (both ratified and implemented in review round 3, see the rulings below)
1. `HTTPRemoteSource.makeBackgroundBackend(_:staging:policy:)` cannot receive the app key, the request timeout or the log route. Proposed: `makeBackgroundBackend(_:staging:policy:appKey: AppKey? = nil, requestTimeout: TimeInterval = 60, log: LogRoute = .tapOnly(nil))`. **Implemented** (ruling 1).
2. `BackgroundSessionDriver.startDownload(_:name:priority:expectedBytes:)` has no resume-data parameter, so a background pause's resume data (kept by the coordinator, T2-05) can never be continued, while `paused(resumable: true)` tells the engine it can.
