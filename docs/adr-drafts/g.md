**Proposed REENTRANCY rows** (the code cites them as "g-n (proposed)"):

| Row | Where | What is re-validated after the await |
|---|---|---|
| g-1 | `ClientLifecycle.current()`, `reopen(replacing:)` and `observeMemoryPressure`: waiting for a running reopen's task | `core` (the reopen installed it) and `closed`, read after the wait; a caller whose pair was already replaced gets the replacement without a second reopen |

| g-5 | `ClientLifecycle.shutdown`: waiting for a running reopen, then the current engine's `shutdown()` | `core`, read after the wait (the reopen stops at its next check of `closed`); then nothing (terminal) |

| g-7 | `EventForwarder.next`/`offer` (terminal waits resumed once by `offer`, `end` or `stop`), the stream's unfolding closure, `cancel()`'s hop, the pump's entry | Nothing: each terminal wait is resumed exactly once; `next()` and `offer` re-read their state after every await; the pump runs off the actor and re-enters only through `offer` and `end` |

**Contract change requests** (no public or package signature was changed; the contract files' bodies and private members only):
- **CCR-G1 (WP-D transport, behaviour only).** R-NET-3's "falls back to foreground when the hook is not wired" (transport.md §10.7, F-26) needs the transport to notice a `urlSessionDidFinishEvents` that arrives while no `handleBackgroundEvents` reached the source. `BackgroundTransferCoordinator` records it (`unclaimedFinishes += 1`) but disables nothing, and the facade cannot see it: the relay (`BackgroundEventsRelay`) is consulted by nobody below the facade, and `RemoteSourceFactory` passes no relay. Minimal change: in `BackgroundTransferCoordinator.process(.backgroundEventsFinished)`, when `finishWaiters` is empty, set `disabled = true` (background off for the process) and log a fault; `awaitBackgroundEvents()` keeps its current answer. No signature changes. Until then the facade test of that name covers the attestation half (G-6).
- **CCR-G2 (WP-F engine, behaviour only; blocking for S1-05 end to end).** `SyncEngine.registerGroup` returns `.success(token)` before the group holds any interest: the interests are added by `joinGroup` in an engine-owned task after a store read (`EngineCommands.swift:186-200`). A re-lane (`PrefetchHandle.cancel(after:)`, `PrefetchWindowController`) orders the old handle's release after the successor's *registration*, so the release lands before the successor's join, the asset's last interest drops, the job retires and its transfer is cancelled and started again at the new lane. Reproduced through the facade, deterministically (6 of 6 runs): `R-CAR-3: moving the window by one …` (assets 2 and 3 cancelled and restarted) and `R-CAR-3: a neighbour that becomes current is promoted without a second transfer` (1,001 of 1,002 transfers started more than once, 0 of 1,000 promotions reached the transport as `setPriority`). Both tests assert the correct behaviour inside `withKnownIssue("CCR-G2: …")`, so the suite stays green and each test fails ("known issue was not recorded") the moment the engine is fixed, which is the signal to remove the wrapper. Minimal change: in `performRegisterGroup`, add the group's interest synchronously to every listed id that already has a job (the re-lane case needs no store read), leaving only ids without a job to `joinGroup`; or make `performReleaseGroup` defer retiring a job while a group registered earlier than the release and naming one of its ids has not joined. No signature changes. The facade cannot work around it: no package API reports when a group's join finished.
- **CCR-G3 (WP-B store, one package read).** The facade owns the reopen after a replaced root (B-15), but it can only react to a call that fails with `.storageUnavailable(.rootVanished)`: the store exposes no read of `StoreCoreState.unavailable`. Observed with the root wiped and the store already flagged: a `sync` fails with `.storageUnavailable(.ioFailure)` (the run's staging listing), and `acquireLease` grants a lease on the old store (leases are reads), so `withAsset` runs its body with a URL under the vanished root; both reach the replacement only after another call meets `rootVanished`. Minimal change: `package var unavailableReason: StorageUnavailableReason? { state.core.unavailable }` on `AssetStore` (WP-B's `AssetStore.swift`); the facade would then check it before `withAsset`'s lease and after any `.storageUnavailable` result, and reopen. Pinned for now by `R-STO-9: after a replaced root the client's event stream follows …` (which asserts the `.ioFailure` and reopens through the next mutating call).

## G-1 — A client lifecycle owns the store, the engine and the reopen
- **Context.** ARCHITECTURE §8 and B-15: after `rootVanished` every commit and mutating call fails while reads work, and "the facade owns the reopen", calling `SnapshotMirror.reset()` before the replacement's first install (B-17). A closed `AssetStore` cannot reopen, and a `SyncEngine` holds its store for life, so a reopen means a new store and a new engine. The Stage 1 `AssetClient` held both as `private let`.
- **Options.** (a) No reopen: report `rootVanished` for ever (contradicts §8). (b) Rebuild only the store (impossible: the engine's store is fixed). (c) An internal actor, `ClientLifecycle`, holding the current `(store, engine)` pair and a generation, replacing the pair in one single-flight reopen; the facade's calls run on the current pair.
- **Decision.** (c). `AssetClient` keeps immutable stored properties (`configuration`, `environment`, `mirror`, `lifecycle`, the two relays); every async API goes through `perform` (G-5). The reopen: mark the old generation retiring, shut the old engine down (its store closes, so it can never install again), reset the mirror on the main actor, build the replacement from the same configuration, environment and mirror with the run-time retention scope, re-apply the newest memory-pressure request, re-register every live prefetch group, start the replacement. Each await re-checks `closed`, so a shutdown meanwhile builds nothing. Prefetch handles hold facade tokens (`ClientLifecycle: PrefetchRegistry`), each bound to the engine token of its generation, so a release after a reopen never reaches another engine's token; registrations on a retired engine are made again on the replacement.
- **Consequences.** `init` still does no I/O and spawns no task (the first pair is built synchronously; P-12 0.0017 ms). Between the reset and the replacement's first install `lookup` returns `nil` (readers see no store rather than a vanished one). Pins live in the vanished root's records and are lost with it. Tests: `R-STO-13: after a rootVanished reopen the facade resets the mirror …` (failed before the reset, `74059fb` → `34295b9`), `R-STO-9: concurrent calls that meet a replaced root share one reopen`, `R-CLN-11: prefetch registrations and the memory-pressure observer carry over to the reopened store's engine`.

## G-2 — Event streams follow the replacement engine
- **Context.** `events`/`subscribe()` streams were the engine's own; a reopen's shutdown of the old engine would end them with `clientShutDown`, telling the UI the client was shut down when it was not.
- **Options.** (a) Accept it. (b) Forward through an unbounded continuation (breaks R-SYN-12's backpressure). (c) A pull-through forwarder: one pump task reads the current engine's stream and hands each event to the consumer only when it pulls.
- **Decision.** (c), `EventForwarder`. At most one event waits in the forwarder, so the engine's bounded queues still apply backpressure. A `clientShutDown` from a retired generation (`ClientLifecycle.hasRetired`) ends that engine's stream only, and the pump continues with the replacement's; a real shutdown's `clientShutDown` is forwarded and is the last event. The pump runs off the actor (a `nonisolated static` function), so the engine stream's non-`Sendable` iterator never crosses an isolation boundary. A cancelled consumer stops the pump; the pump then pulls once more under cancellation, which runs the engine stream's cancellation handler and releases its subscription. `subscribe()` registers with the engine first (the replay contract) and hands that stream to the forwarder.
- **Consequences.** One unstructured task per active stream, not engine-owned (P-14 and R-SYN-14 count engine-owned tasks; the pump ends with its stream). Tests: `R-STO-9: after a replaced root the client's event stream follows the reopened store's engine without a clientShutDown`, `R-SYN-12: cancelling the consumer of the client's event stream releases its engine subscription`, `R-SYN-12: the client's event stream reports a sync as started and then finished …`, R-SYN-15's walk.

## G-3 — `setRetentionScope` and `subscribe` await `start()`
- **Context.** §8: "every async API awaits it". The engine records a retention scope before start and registers subscribers without starting, so these two APIs left the client in `created` (`R-CAR-1: every async API awaits start …` failed for both, `fe25074`).
- **Decision.** Both call `start()` first and propagate its failure, as every other async API does (a store that cannot open makes them throw `.storageUnavailable`); `setRetentionScope` then records the scope for a replacement engine (G-1).

## G-4 — `diagnosticReport()` contents and secrets
- **Context.** R-OBS-3, R-SEC-1, L4-R9.
- **Decision.** `DiagnosticReportBuilder` (pure): `SyncEngine.diagnostics()` through `perform` (it answers while degraded), then the engine's metrics with the mirror's lookup counts and its storage report, each replaced by empty figures when the store cannot answer. The configuration is summarised field by field (never dumped, so a future field cannot leak by accident): the app key as `<redacted>`/`none`, URLs reduced to scheme, host, port and path (no user, password, query or fragment). Engine counts are named (`lifecycle.<state>`, `jobs.<state>`, `queued.<lane>`, timers, tasks, subscribers, `launchEpoch`). JSON is sorted and indented, dates ISO 8601, non-finite numbers as strings, so encoding cannot fail on a value. `moduleVersion` is the constant `"1.0.0"` (no build tool writes one; bumped with releases).
- **Tests.** `R-OBS-3: diagnosticReport is valid JSON with state counts and the last errors and never the canary key` (trapped on the stub, `319f4bc` → `580d4de`), `R-OBS-3: diagnosticReport answers while the store cannot be opened …`, `R-SEC-1: the diagnostic configuration summary redacts …`, `R-SEC-1: the canary key appears in no description, dump, Mirror, error, event, metric or captured log line`.

## G-5 — Which failures `perform` repeats on a replacement
- **Context.** G-1 needs a trigger, and L4-R23 requires the facade's results to stay faithful.
- **Decision.** `perform` repeats the call on the replacement only for `.storageUnavailable(.rootVanished)` (after a reopen) and for `.shutDown` answered by an engine the lifecycle has retired (a sibling call's reopen shut it down mid-call: without this, concurrent callers of a vanished root failed with `.shutDown`, `6bf9a5f` → `7d212f9`); at most `AssetClient.reopenAttempts` (3) times, so a root that keeps vanishing reports the failure. Every other result, `ensureAvailable`'s included, is returned exactly as the engine gave it. `sync` and `withAsset`'s lease use the same path.
- **Consequences.** A retried mutating call (a purge) runs once on the replacement, which is what the caller asked for. Other storage failures (`.ioFailure`) are not treated as a vanished root: see CCR-G3. Tests: G-1's, and `R-SYN-10: the facade's ensureAvailable throws serverUnavailable with the time left …` and `… reports a member a throttle answered as missing with a fresh manifest` (L4-R23).

## G-6 — The R-NET-3 "hook not wired" test covers the attestation half
- **Context.** ADR-050 assigns `R-NET-3: background falls back to foreground when the background-events hook is not wired` to WP-G. Run-time detection is not possible from the facade (CCR-G1).
- **Decision.** The test shows what the composition root and the facade guarantee today: without the app's attestation (`BackgroundTransferPolicy.disabled`, ADR-026 option E) `LiveRemoteSourceFactory` builds a source with no background session, and the client's bulk transfers all run in the foreground. Its doc comment names CCR-G1 for the rest.

## G-7 — Test-first where Stage 1 had implemented the code
- **Context.** Most of `ZTronAssetKit` was implemented in Stage 1 (mirror, handles, window, chain, relays, most of `AssetClient`); WP-G's stubs were `diagnosticReport()` and the B-17 reopen.
- **Decision.** Failing tests were committed first wherever the behaviour was missing: R-SYN-15/R-ENV-6/R-OBS-3/R-SEC-1 (the stub traps), R-CAR-1 (G-3), R-STO-13 B-17 (the reset was held back one commit), R-STO-9 concurrency (G-5). Tests of behaviour Stage 1 had already implemented (fallback parity, composition, R-STO-7, R-CAR-8, R-CLN-11, R-OBS-2, the benchmarks) passed when added and are committed as tests only; CCR-G2's two tests failed on the merged engine and are recorded as known issues.

## G-8 — `KitContractTests.GatedRegistry.waitUntil` ends on cancellation
- **Decision.** Authorised edit (ADR-050, l2close): the census wait registers by id inside the continuation body and a cancellation handler resumes it (the `CensusWaiting` pattern), so a regression fails within its time limit; the assertions are unchanged (`585807a`).

## G-9 — Facade test harness
- **Decision.** `KitHarness` builds a real client over `FakeFileSystem`, `ManualTimeSource` and `FakeRemoteSource`, and drives the clock under the L4-R17 rule (never at or past the engine's clock fence, a copy of the Sync tests' seam through `@testable import ZTronAssetSync`); every wait is a condition wait that ends on cancellation (`waitUntil`, `awaitCondition`, census `require…` forms, streams). Benchmarks use `LiveTimeSource` and live dispatch executors over the fakes.
