## G-1 — A client lifecycle owns the store, the engine and the reopen
- **Context.** ARCHITECTURE §8 and B-15: after `rootVanished` every commit and mutating call fails while reads work, and "the facade owns the reopen", calling `SnapshotMirror.reset()` before the replacement's first install (B-17). A closed `AssetStore` cannot reopen, and a `SyncEngine` holds its store for life, so a reopen means a new store and a new engine. The Stage 1 `AssetClient` held both as `private let`.
- **Options.** (a) No reopen: report `rootVanished` for ever (contradicts §8). (b) Rebuild only the store (impossible: the engine's store is fixed). (c) An internal actor, `ClientLifecycle`, holding the current `(store, engine)` pair and a generation, replacing the pair in one single-flight reopen; the facade's calls run on the current pair.
- **Decision.** (c). `AssetClient` keeps immutable stored properties (`configuration`, `environment`, `mirror`, `lifecycle`, the two relays); every async API goes through `perform` (G-5), except `setRetentionScope`, which the lifecycle records and applies (G-3). The reopen: mark the old generation retiring, shut the old engine down (its store closes, so it can never install again), reset the mirror on the main actor, build the replacement from the same configuration, environment and mirror with the run-time retention scope, re-apply the newest memory-pressure request, re-register every live prefetch group, start the replacement. Each await re-checks `closed`, so a shutdown meanwhile builds nothing. Prefetch handles hold facade tokens (`ClientLifecycle: PrefetchRegistry`), each bound to the engine token of its generation, so a release after a reopen never reaches another engine's token; registrations on a retired engine are made again on the replacement.
- **Consequences.** `init` still does no I/O and spawns no task (the first pair is built synchronously; P-12 0.0017 ms). Between the reset and the replacement's first install `lookup` returns `nil` (readers see no store rather than a vanished one). Pins live in the vanished root's records and are lost with it. Tests: `R-STO-13: after a rootVanished reopen the facade resets the mirror …` (failed before the reset, `74059fb` → `34295b9`), `R-STO-9: concurrent calls that meet a replaced root share one reopen`, `R-CLN-11: prefetch registrations and the memory-pressure observer carry over to the reopened store's engine`.

## G-2 — Event streams follow the replacement engine
- **Context.** `events`/`subscribe()` streams were the engine's own; a reopen's shutdown of the old engine would end them with `clientShutDown`, telling the UI the client was shut down when it was not.
- **Options.** (a) Accept it. (b) Forward through an unbounded continuation (breaks R-SYN-12's backpressure). (c) A pull-through forwarder: one pump task reads the current engine's stream and hands each event to the consumer only when it pulls.
- **Decision.** (c), `EventForwarder`. At most one event waits in the forwarder, so the engine's bounded queues still apply backpressure. A `clientShutDown` from a retired generation (`ClientLifecycle.hasRetired`) ends that engine's stream only, and the pump continues with the replacement's; a real shutdown's `clientShutDown` is forwarded and is the last event. The pump runs off the actor (a `nonisolated static` function), so the engine stream's non-`Sendable` iterator never crosses an isolation boundary. The consumer's stream holds the forwarder through a `Consumer` token that the pump never retains: a cancelled consumer (`onCancel`) and a consumer that drops the stream without cancelling it (the usual `break` out of `for await`, for which `AsyncStream(unfolding:onCancel:)` calls no handler; the token's deinit runs instead) both stop the pump, which then pulls once more under cancellation, so the engine stream's cancellation handler releases its subscription (round 1, correctness lens: before, each abandoned stream kept one pump, one forwarder and one engine subscriber until shutdown, a regression from Stage 1's direct engine stream). Two iterators of one stream that pull at once are queued and served in turn, so neither waits for good (round 1). `subscribe()` registers with the engine first (the replay contract) and hands that stream to the forwarder. **Round 2 (requirements lens, a test gap):** the forwarder gained a test seam, `offerParked` (`nil` in production; one `nil` check when the pump waits in `offer`), so a test can drop the consumer's stream while the pump holds an event in `offer`, the path a `break` out of `for await` takes while a sync is still emitting.
- **Close-out (orchestrator ruling L5-R3, L5-V3-06).** The pump followed a reopen through `lifecycle.current()`, which waits for the whole reopen (the replacement's group re-registration and start included), and registered with the replacement only then, so a consumer that was reading lost what the replacement published from its installation on: always its `clientStarted`, and terminal asset events of calls that reached it during the reopen (PROBE-3 20 of 20, PROBE-4 2 of 4). Now the pump registers with the lifecycle before it reads (`ClientLifecycle.follow`), `performReopen` subscribes every registered forwarder to the replacement through the engine's eager-registering `subscribe()` and hands it the stream before installing the replacement (g-10: the replacement is `created`, unreachable, and cannot publish yet; forwarders registered during the pass are handed one too; a shutdown meanwhile installs nothing), and after a retired engine's `clientShutDown` the pump drains that stream to its end and reads the oldest stream handed over for an installed generation, falling back to the engine serving then only when none was handed over (a forwarder registered after the hand-over has no history to lose; its own registration's replay covers the state). `current()` still waits for the whole reopen (g-1 unchanged): the handed stream buffers meanwhile, subject to the engine's coalescing (one slot per progress key and per subject, H-9). **Decision on `clientStarted` (L5-R3):** the replacement's `clientStarted(generation:)` is forwarded, so consumers learn that a new generation started, matching the mirror's reset; the retired engine's `clientShutDown` stays hidden. Tests (failing first, `9d10eb4` → `33b5e39`): `R-SYN-12: a consumer of the client's events that was reading when a reopen ran receives the replacement's clientStarted` (PROBE-3's shape; the consumer pulls once, nothing while the reopen runs, then up to a marker the replacement publishes before the shutdown, whose `clientShutDown` would otherwise supersede `clientStarted` in the engine's queue) and `R-SYN-12: a terminal event the replacement publishes while the reopen still runs reaches a consumer that was reading` (PROBE-4's shape, parked at `registrationAnswered`). Both failed 3 of 3 before the fix and passed 5 of 5 after it.
- **Close-out cycle 2 (orchestrator ruling L5-R13; L5-C1-00, L5-C1-03, L5-C1-04).** The paragraph above is superseded where it says that a forwarder registered after the hand-over "has no history to lose": that is false for a `subscribe()` stream, which is registered (and buffering) from the moment `subscribe()` returns, while its forwarder became a follower only when its pump started, on the first pull. A reopen between `subscribe()` and that pull handed it nothing, and the pump then registered lazily with the replacement and lost everything the replacement had published (PROBE-A, PROBE-A2; 7 of 7 runs). The class is fixed by one design rule, G-16: a forwarder becomes a follower in the lifecycle turn that chooses the engine it registers with, before the registration's await; the pump never follows.
- **Consequences.** One unstructured task per active stream, not engine-owned (P-14 and R-SYN-14 count engine-owned tasks; the pump ends with its stream). Tests: `R-STO-9: after a replaced root the client's event stream follows the reopened store's engine without a clientShutDown`, `R-SYN-12: cancelling the consumer of the client's event stream releases its engine subscription`, `R-SYN-12: a consumer that breaks out of the client's event stream releases its engine subscription when the stream is dropped` (timed out with the subscriber still registered before the fix, `6475ece` → `4fdc02b`), `R-SYN-12: two iterators of one client event stream pulling at once both finish when the client shuts down`, `R-SYN-12: the client's event stream reports a sync as started and then finished …`, R-SYN-15's walk; since round 2 `R-SYN-12: a consumer that drops the client's event stream while the next event waits in the forwarder releases its engine subscription` (the replay's second event parked in `offer`, so `stop()` must end that wait; with `stop()`'s `resume(returning: false)` removed it failed at its time limit with the subscriber still registered and the continuation reported leaked, while the round-1 drop test passed) and `R-SYN-12: a stream from subscribe() dropped before its first pull releases its engine subscription`. Both passed when added: the code was right, the tests were missing.

## G-3 — `setRetentionScope` and `subscribe` await `start()`
- **Context.** §8: "every async API awaits it". The engine records a retention scope before start and registers subscribers without starting, so these two APIs left the client in `created` (`R-CAR-1: every async API awaits start …` failed for both, `fe25074`).
- **Decision.** Both call `start()` first and propagate its failure, as every other async API does (a store that cannot open makes them throw `.storageUnavailable`). `setRetentionScope` then goes through `ClientLifecycle.setRetentionScope` (round 1, correctness lens): the scope is recorded before it is applied, so a reopen from then on builds its replacement with it, and the newest recorded scope is applied again when a newer request was recorded or a reopen replaced the engine during the apply, so concurrent calls, which can reach the engine in any order, leave it on the newest request, the one a replacement is built with (REENTRANCY g-8). Before, the scope was applied first and recorded in a second hop, so a reopen in between built the replacement with the old scope although the call succeeded, and two calls could be recorded in the opposite order to the engine's.
- **Tests.** `R-CAR-1: every async API awaits start …` (all sixteen async APIs since round 1), `R-CAR-5: the retention scope set through the client is the replacement engine's after a reopen`, `R-CAR-5: concurrent retention scope changes leave the engine on the newest recorded scope, which a reopen keeps` (48 calls from tasks of mixed priority). Neither R-CAR-5 test failed on the old order in the runs made: the lost update needs the reopen to fall between the engine's answer and the record, which no seam reaches; the new order removes that window by construction.

## G-4 — `diagnosticReport()` contents and secrets
- **Context.** R-OBS-3, R-SEC-1, L4-R9.
- **Decision.** `DiagnosticReportBuilder` (pure): `SyncEngine.diagnostics()` through `perform` (it answers while degraded), then the engine's metrics with the mirror's lookup counts and its storage report, each replaced by empty figures when the store cannot answer. The configuration is summarised field by field (never dumped, so a future field cannot leak by accident): the app key as `<redacted>`/`none`, URLs reduced to scheme, host, port and path (no user, password, query or fragment), and the configured paths (`manifestPath`, `catalogPath`) cut at their first `?` or `#` (round 1, defence in depth: `summaryRedacts` failed on a manifest path carrying `?token=`, `6475ece` → `01835b7`). Engine counts are named (`lifecycle.<state>`, `jobs.<state>`, `queued.<lane>`, timers, tasks, subscribers, `launchEpoch`). JSON is sorted and indented, dates ISO 8601, non-finite numbers as strings, so encoding cannot fail on a value. `moduleVersion` is the constant `"1.0.0"` (no build tool writes one; bumped with releases).
- **Tests.** `R-OBS-3: diagnosticReport is valid JSON with state counts and the last errors and never the canary key` (trapped on the stub, `319f4bc` → `580d4de`), `R-OBS-3: diagnosticReport answers while the store cannot be opened …`, `R-SEC-1: the diagnostic configuration summary redacts …`, `R-SEC-1: the canary key appears in no description, dump, Mirror, error, event, metric or captured log line`.

## G-5 — Which failures `perform` repeats on a replacement
- **Context.** G-1 needs a trigger, and L4-R23 requires the facade's results to stay faithful.
- **Decision.** `perform` repeats the call on the replacement only for `.storageUnavailable(.rootVanished)` (after a reopen) and for `.shutDown` answered by an engine the lifecycle has retired (a sibling call's reopen shut it down mid-call: without this, concurrent callers of a vanished root failed with `.shutDown`, `6bf9a5f` → `7d212f9`); at most `AssetClient.reopenAttempts` (3) times, so a root that keeps vanishing reports the failure. Every other result, `ensureAvailable`'s included, is returned exactly as the engine gave it. `sync`, `withAsset`'s lease and, since round 1, `subscribe()`'s registration use the same path (`performOnCore` hands the operation the generation, which the forwarder needs), so an engine a reopen retired between `start()` and the registration is replaced rather than reported as `.shutDown`; that interleaving needs a reopen between two hops and has no test. Since close-out cycle 2 `subscribe()`'s registration goes through `ClientLifecycle.register(_:)` instead (G-16, L5-R13): an engine a reopen retired before it answered is not asked again, because the stream that reopen handed the forwarder (a follower since the turn that chose the engine) carries the registration; that path is tested (the event model, and `R-SYN-12: an events stream cancelled while its first registration waits for a reopen …`). A reopen whose loop finds its replacement already replaced by a newer reopen hands its callers the newest pair (G-10's back-to-back test). **Round 2 (correctness lens):** `handleBackgroundEvents` and `diagnosticReport()` took `lifecycle.current().engine` directly and now use the same path. Background events go through a static `performOnCore(lifecycle:_:)`, so the hand-off task still does not capture the client, and a `.shutDown` from an engine a reopen retired repeats the call on the replacement instead of completing UIKit's handler before the replacement made the session. The report reads diagnostics, metrics and storage from one engine inside one `perform` closure (`reportFigures(of:)`); a `.shutDown` from any of the three repeats the read, so the figures never mix generations or turn empty because a retired engine answered (after a real shutdown the report throws `.shutDown`, as every API does). Neither interleaving has a test (a reopen landing between two hops of one call, as for `subscribe()`); the paths are covered by the existing background-events and report tests.
- **Close-out amendment (orchestrator ruling L5-R4, CCR-G3, L5-V3-02).** The store gained one package read, `AssetStore.unavailableReason` (WP-B's `AssetStore.swift`, authorised), and `performOnCore` uses it twice: (a) with `reopensVanishedRootFirst` (only `withAsset`), before the call: a store that reports `.rootVanished` is reopened first, because a lease is a read that such a store still grants, so the body never gets a URL under the vanished root; (b) after any `.storageUnavailable(_)` failure that does not name the replaced root: the store is asked, and a `.rootVanished` answer makes the failure a vanished root (reopen and repeat, within `reopenAttempts`). `sync` now hands `.storageUnavailable(_)` outcomes to that path. Results stay faithful (L4-R23): only the store's own `.rootVanished` reopens, and every other storage failure is returned exactly as given, a read-only (B-34) store's `.ioFailure` included (pinned by a new test). After every reopen `reopenAttempts` allows, a call that reopens first and still finds the root vanished throws `.storageUnavailable(.rootVanished)` instead of leasing under it (`bce5122`; a root that vanishes again during each reopen, which no test reaches, listed as untested). A root that vanishes between the read and the call is met by the call as before, and a lease taken then is a read under B-15: accepted. `R-STO-9: a sync that fails for a reason other than a replaced root is returned as given and never reopens` pins `sync`'s side of L4-R23 (passed when added). The read costs one store hop, made only before `withAsset`'s lease and after a storage failure. ## G-12 — `observeMemoryPressure` never waits for a reopen (round 2)
- **Context.** Round 2, correctness lens, blocking: the facade's memory-pressure handler (built in `AssetClient.apply`) runs inside the engine-owned observer task. When every registered cache was deallocated without being unregistered, `PurgeableCacheRelay.purge` answers `.stop` and the handler calls `ClientLifecycle.observeMemoryPressure(epoch:handler: nil)`, which waited in `current()` for a running reopen. A reopen's first step, the old engine's `shutdown()`, cancels and joins every owned task of that engine, the observer included, and cancellation cannot end a wait on a task's value: the observer waited for the reopen, the reopen for the shutdown and the shutdown for the observer, and from then on every API waited in `current()` for good. Stage 1 called the engine's synchronous `observeMemoryPressure`, which answers `.shutDown` during a shutdown, so the cycle came with `ClientLifecycle` (G-1); the verifier's probe hung 3 of 3 times.
- **Options.** (a) Record the request, then call the current engine only when no reopen runs: a running reopen applies the newest recorded request to its replacement once installed, and the old engine's shutdown stops its observer. (b) Have the handler hand its stop to an unstructured task, so no engine-owned task waits on the lifecycle. (c) Both.
- **Decision.** (a), the fix the verifier validated: no wait for a reopen remains in `observeMemoryPressure`, whoever calls it. (b) would also break the cycle, but it turns the engine's documented "a stop requested from inside the handler ends the observer after the handler returns" into a stop that lands later and adds an unstructured task per stop, so it was not added. g-1 no longer lists `observeMemoryPressure`; its awaits are g-3's and g-9's.
- **Consequences.** A request recorded during a reopen reaches only the replacement, which is the engine that will serve; the old one is being shut down. Test: `R-CLN-11: a pressure event whose handler stops the observer while a reopen shuts that engine down leaves neither waiting for the other` parks the reopen before the old engine's shutdown (`LifecycleSeamPoint.reopenWillShutDownEngine`, G-10), sends the event, waits until the handler's stop is recorded (`pressureRecorded`), then lets the reopen go on; it waits for generation 0 to reach `shutDown` before awaiting the call that triggered the reopen, so a regression fails at the time limit instead of hanging the run. It failed so before the fix (`587c172`: "Time limit was exceeded" and generation 0 left `shuttingDown`) and passes after (`19a48b4`); it also checks that a caller of `current()` during the reopen gets the replacement, that the replacement runs no observer and that a cache registered afterwards starts one.

## G-13 — Pending claims keep a registered group's jobs until its join reaches them (close-out, L5-R1)
- **Context.** CCR-G2, blocking in every round (L5-V3-00, L5-V3-07): `performRegisterGroup` answers `.success(token)` before the group holds any interest (its join adds them later, in an owned task, after a store read), and a re-lane orders the old handle's release after the successor's registration only, so the release retired the job and the successor's join started its transfer again (995 to 1,001 of 1,002 transfers started twice in the 1,000-move facade test). The ruling widened it to the class: once `registerGroup` returned for a group naming x, and until that group is released, no other group's release, no waiter withdrawal and no caller cancellation may retire x's job or cancel its transfer, whether x had a job at registration or not (window 2: the predecessor's join creates the job after the successor's registration) and whether the group's join reached x or not.
- **Options.** (a) CCR-G2's proposal, a synchronous join of every listed id that already has a job: closes window 1 only. (b) Defer every release until earlier registrations joined: delays every cancellation behind unrelated joins. (c) The ruling's design: a pending claim per member, recorded in the registering turn, that keeps the job of the content it names until its join reaches it, its group is released, its join gives up or the engine shuts down.
- **Decision.** (c), in WP-F's files under L5-R1 (internal state and bodies only). `recordGroup` claims each member's content (`EngineState.claims`, keyed by `ClaimKey`: a checksummed entry's `ContentHash`, a checksum-less one's `TransferID`; formatting `TransferID.content`'s 66-character text for 10,000 members cost about 3 ms of the registering turn, so the four hash words are kept instead). The check sits on the interest-removal edge, `removeInterest`, through which every release, withdrawal and cancellation passes: a job whose last interest leaves while its content is claimed stays, keeps its lane (`Job.heldLane`) and its running transfer, and is remembered in `claimHeld`; the join then adds its interest (a promotion or demotion of a running transfer reaches the transport as a priority change, with no second start), and the content's last claim to end retires a job claims alone kept in that turn (`dropClaim`). `retire(_:)` itself is unchanged because the pre-transfer presence read (`EnginePresence.answeredFromStore`, not an authorised file) retires through it directly after answering every interest from the store and returns as if the job were gone: a claim check there would leave a downloading job with no driver; that exit (L4-R5) and the engine's other exits (a pruned or changed entry, failure, commit) stay unchanged, as the ruling requires. A claim ends when its join joins or skips the member (`joinMember`, after the interest is in place), on every early exit of the join (`endClaims(of:)`; more than `releasesPerTurn` of them over several turns since close-out cycle 2, L5-R15), when its group is released (claims dropped before the members' interests, chunked with them at `releasesPerTurn` a turn) and at shutdown (`resumeEverything`). A member the engine's copy does not list at registration (a registration before `start()`: the facade's prefetches before start and its re-registrations on a replacement) is claimed when `adoptApplied` lists it (`claimNewlyListed`), before any join runs. A claimed-only queued job may be dispatched at its held lane while no release is in progress (`isReleasedOnly`, in the unauthorised `EngineDispatch.swift`, makes it wait during one): it behaves as if the released interest were still there, except on failure (orchestrator ruling L5-R16, L5-C1-05): a job only a claim keeps ends on its first failed attempt as `failed(.nextRun)` with `assetFailed`, and the successor's join then starts a fresh transfer. That is L5-R1's unchanged failure exit, not a violation; a claim that inherits the held lane's retry policy is in ADR-054's Stage 3 backlog, and `EngineFailures.swift` is unchanged in Level 5. The invariant check counts the claims against the groups and requires every job without an interest to be one a claim keeps.
- **Consequences.** A claimed-only job that fails while no interest holds it is removed by the existing failure path, which publishes its `assetFailed`; the successor's join then starts a fresh attempt (a retry after a failure, not a duplicate). A claim names the content its member had in the engine's copy when claimed: a member whose entry later changes no longer protects its new content until its join reaches it (the ruling's "its entry now names different content" exit), and a stale claim keeps a job of the old content at most until that join. C2 figures under "L5-R1 C2 figures". Tests (new file `Tests/ZTronAssetSyncTests/Engine/EngineGroupClaimTests.swift`, failing first, `ab60002` → `21fc528`): windows 1 and 2, the only claiming group's release retiring the job in that turn with nothing leaked, a waiter's withdrawal, another id of the same content, groups registered before start; with the fix, a large group's claims dropped over several turns and shutdown ending every claim; and a large group released before start, whose follow-up had stranded its claims (`7410ef6` → `574e440`). Both facade R-CAR-3 tests lost their `withKnownIssue` wrappers (`3b79c39`) and passed 50 consecutive runs.

- **Close-out cycle 2 (orchestrator ruling L5-R15; L5-C1-06, L5-C1-08, L5-C1-09).** `endClaims(of:)` dropped every claim a join gave up in one turn, so a 10,000-member successor of a released 10,000-member predecessor whose join gave up would have retired 10,000 jobs the claims alone kept in one turn (about 85 ms at the measured ~8.5 µs a retirement). No running engine reaches a give-up after its join's read today, as the cycle-1 correctness verifier argued and no test contradicted: `planningView()` throws only for a store that is not open, `degraded` is set only during the start, `state.remote` is never cleared once set, a shutdown clears the groups before the join can exit, and a missing source does make the join give up but leaves no job to retire (joins and waiters fail first). That "no give-up after a running join's read" invariant is recorded here; the give-up is now bounded by construction all the same. More than `releasesPerTurn` claims go to `releasing` and are dropped at most `releasesPerTurn` a turn by the release follow-up, so a give-up's turn retires at most that many jobs; a later large release of the same group drops those leftovers first (`performReleaseGroup` merges them in); a degraded engine, which cannot spawn the follow-up and holds no job (its start failed first), drops them all in its turn, one table update each; shutdown also ends the claims left in `releasing`. `endClaims(of:)` became internal so a test can give claims up in one engine turn. Tests (`EngineGroupClaimTests`): `R-CAR-4: a join's give-up of more than releasesPerTurn claims retires at most releasesPerTurn jobs a turn` (failing first: the pre-change turn retired all 600, `c8b5bf1` → `04cf905`); `R-CAR-4: a group whose join gives up because the start failed ends every pending claim` and `R-CAR-4: a join that gives up after its read for a missing source ends every claim of a large group` (the reachable give-ups; mutant M11, `endClaims` a no-op, fails both, the second at its time limit); `R-CAR-3: a successor at the lane of the transfer a claim kept joins it with no priority change` (mutant M12, `heldLane` never set, fails it: the join sent `setPriority(.prefetch)`). The three that pin existing behaviour passed when added. The merge of a give-up's leftovers into a later large release needs a join that joined more than `releasesPerTurn` members before it gave up, which no running engine reaches; that branch has no test (its line runs in every large release). C2 figures under "L5-R15 C2 figures".

## G-14 — A shutdown from `created` joins every owned task (close-out, L5-R2)
- **Context.** L5-V3-05 (blocking): the `created` branch of `performShutdown` set `shuttingDown` and finished without cancelling or joining owned tasks, while `spawn` allows them in `created`. A cache registered before `start()` (PROBE-1), or a reopen's replacement shut down after its pressure request and before its start (PROBE-2), left the memory-pressure observer task and its subscription alive after `shutdown()` returned, keeping the engine, store and environment alive until the next pressure event.
- **Decision.** The ruling's change, made as the minimal one: `.created` takes the common path (cancel the tasks, cancel nothing in flight, resume every continuation with `.shutDown`, join the tasks), so `shutdown()` returns only once every owned task is cancelled and joined, whatever state it began in. From `created` there is no source to invalidate and no store to close (`launch` and `startTask` are `nil`), so it still never opens the store and never logs; a joined group join's `ensureStarted()` refuses during `shuttingDown`, so it cannot start the engine (pinned: the volume records no operation and the tap no line). The facade keeps the pressure request before the replacement's `start()`, which L5-R2 allows (the newest request is live from the replacement's first turn).
- **The class.** The spawn sites reachable while the engine is `created` are enumerated under "L5-R2 spawn sites"; each has a test that spawns it in `created`, shuts down, and checks, in the turn `shutdown()` returns in, that no owned task is left and the site's resource is released. ## G-16 — Followership precedes registration (close-out cycle 2, L5-R13)
- **Context.** Lost or leaked events in the forwarder came up in main-run round 1 (an abandoned pump leaked), round 3 (L5-V3-06: the replacement's events lost) and close-out cycle 1 (L5-C1-00, L5-C1-03, blocking: a `subscribe()` stream not pulled before a reopen lost the replacement's events; L5-C1-04: an `events` stream's first pull started the pump, which followed the lifecycle one hop later). Fixing shapes one at a time did not converge, so ruling L5-R13 orders one design rule for the class, an enumeration of the ways a forwarder obtains an engine stream, and a seeded model.
- **Options.** (a) The cycle-1 verifier's change: follow before `subscribe()`'s registration and let the pump reuse the key. It closes the `subscribe()` case, but an `events` stream keeps a window, and a registration a retired engine answers with `.shutDown` is still repeated on the replacement after its install, which loses the replacement's first events. (b) The ruling's rule.
- **Decision.** (b). A forwarder is recorded as a lifecycle follower in the same turn that chooses the engine it registers with, before the registration's await (`ClientLifecycle.register(_:)`, g-11), and the engine registers it eagerly (`subscribe()`, which replays the state):
  - `subscribe()` registers before it returns (`EventForwarder.subscribed`); an `events` stream registers on its first pull (`registerEvents`, from `next()` before the pump starts; after shutdown it is handed the last engine's stream, which yields only `clientShutDown`, and is no follower).
  - Every reopen hands every follower recorded before its installation the replacement's stream: the hand-over's last look at the followers, its check of `closed` and the installation happen in one turn (g-10).
  - A registration that a retired engine answers with `.shutDown` is not repeated: the forwarder already follows, so the stream that reopen handed it carries the registration (`ForwarderRegistration.first == nil`).
  - The pump never follows or registers by itself: it reads the registered stream, then, after each retired one, the stream handed over for the next generation. A forwarder drops a handed stream whose generation is not newer than the one it holds (`held`).
  - `stop()` gives the follower entry back when no pump started (a `subscribe()` stream dropped before its first pull leaves none), and `end()` when the pump ends, so an entry outlives neither the consumer's stream nor the pump.
  - **What each stream is promised.** A `subscribe()` stream receives every event of its registration's generation from that registration on, and every event of each later generation from that generation's first event on, `clientStarted` included; an `events` stream the same from its first pull on; both subject only to the engine's coalescing (one slot per progress key and per subject, H-9; a retired engine's `clientShutDown` is hidden, G-2).
- **The enumeration (L5-R13).** Every way a forwarder obtains an engine stream, and how the rule holds for it:

| # | Path | How followership precedes the registration |
|---|---|---|
| 1 | `subscribe()`'s eager registration | `subscribe()` → `EventForwarder.subscribed` → `register(_:)`: one lifecycle turn records the follower and reads the current engine, then `engine.subscribe()`; the stream returns only after both |
| 2 | An `events` stream's first registration | `next()` on the first pull, before the pump starts → `registerEvents(_:)` → `register(_:)`, as path 1; its history starts at that registration; after shutdown, the last engine's stream and no follower |
| 3 | The reopen hand-over | Covers every follower recorded before the installation (same-turn last check and install); a follower recorded later registered with the replacement itself, in its follow turn |
| 4 | The pump's fallback when a retired stream ends with nothing handed over | Kept only for the client-shut-down end: a recorded follower is handed every replacement installed after its follow turn, so nothing is handed over only when the reopen that retired the stream installed nothing because the client was shut down; the last engine's stream then yields only its `clientShutDown`, the real shutdown's (stated in `EventForwarder.forward`) |
| 5 | A registration repeated after `.shutDown` from a retired engine (G-5) | Removed: the follower was recorded before the answer, so the retiring reopen's hand-over carries the registration; after that reopen, a replacement newer than the chosen engine means success with no stream of its own, and no replacement means the client was shut down (`.shutDown`, entry given back) |

- **The model (L5-R13).** `Tests/ZTronAssetKitTests/EventContinuityModelTests.swift`, in the shape of L4-R20's gate model: seeded walks (SplitMix64, 10 steps, then a shutdown phase) over consumer actions (`subscribe()`; `events` and a first pull; pulls of 1 to 3 events; dropping a stream; cancelling a consumer), reopens (a root moved aside in one operation and `purge(.all)`; parked or not at `reopenWillShutDownEngine`, `replacementBuilt`, `replacementObservesPressure` or `registrationAnswered`, with up to three actions while parked; at most three per walk), publishing calls (`resolve` of a fresh on-demand asset, the walk's markers, one after every reopen that installs a replacement; `performMaintenance`; `sync(.force)`), and `shutdown()`, a third of the time while a last reopen is parked. The oracle is a direct subscriber on every engine before it can publish: generation 0 before `start()`, each replacement at `replacementBuilt`. Every consumer live at the shutdown drains its stream, and the walk checks I1 (no loss: every marker whose call began after the registration, or a later event of its subject; from every generation built by a reopen that began after the registration, every terminal event the oracle saw or a later one of its subject, and that generation's `clientStarted` itself whenever the consumer got one of its markers before its shutdown began), I2 (markers never go back a generation or arrive twice; no `clientShutDown` before the real shutdown began, at most one, last; every live consumer ends with it), I3 (at idle: no follower entry, which also means no pump is left, and no subscriber on any engine the walk saw, waited for with conditions) and I4 (after every step, at most one event waits in each forwarder). A failure prints its seed and walk; `EVENT_MODEL_SEEDS` replays chosen walks, `EVENT_MODEL_SEED_COUNT` runs more, `EVENT_MODEL_TRACE` appends each walk to a file. The suite runs 500 seeds in ten parallel cases of 50 under a 2-minute limit each. On the pre-fix forwarder it failed in every case at its first L5-C1-00 walk (seeds 1, 4, 6, 9, 20, 25, 32, 38, 87 and 93: "consumer n (subscribe(), registered at t…, live) never received marker m… (generation 1…3)"; `666ec0d`, which is `2e828d1` plus the model and its behaviour-neutral seams, since the model cannot compile against `2e828d1` alone; the model's one-step root replacement, `0ae3004`, was checked against the pre-fix forwarder too and failed at the same seeds); with the fix it passes 500 seeds (`8e48544`), and 5,000 seeds by hand (`EVENT_MODEL_SEED_COUNT=5000`: "Test run with 1 test in 1 suite passed after 17.501 seconds" on the final tree, debug, load 6.43 → 7.42). Over the 500 suite seeds the walks made 867 reopens, 135 of them ended by a shutdown while parked, parked at every one of the four points.
- **Seams the model needs (L5-R13: "a seam point is added only if the model needs it"; all `nil` or unused in production).** `LifecycleSeamPoint.replacementBuilt(ClientCore)` (the oracle must subscribe to each replacement before it is installed; no earlier point carries the replacement); `ClientLifecycle.setFollowerObserver(_:)` (one optional call per follower change, so I3 waits for no follower without polling) and `liveFollowers` (a read, for I4); `EventForwarder.bufferedEvents` (a read). `KitHarness.vanishRoot()` moves the root aside in one operation of the fake volume (L5-R14, pattern g).
- **Consequences.** `subscribe()` no longer goes through `performOnCore`; an `events` stream's first pull costs one lifecycle hop, and it registers eagerly (`engine.subscribe()`, the same replay as the lazy `makeEventStream()` registration it replaces); a registration repeated after a retired engine's `.shutDown` is gone. ## L5-R1 C2 figures

Measured with a temporary release-mode probe (`swift test -c release --scratch-path .build-g-perf -Xswiftc -enable-testing`, never committed) on a 10,000-entry on-demand catalog, timing single engine turns with `ContinuousClock`, 7 samples each, load average 4.84–4.92 (8 cores):
- **Registering turn** (`recordGroup`, 10,000 members): 4.27–4.40 ms, of which the existing de-duplication and sort (`Array(Set(ids)).sorted()`) is 3.44–3.51 ms, so the claims cost about 0.85 ms (one manifest probe, one `ClaimKey` and one counter update per member). An earlier draft that keyed claims by `TransferID` measured 7.2–7.5 ms (formatting 10,000 transfer texts); the `ClaimKey` replaced it.
- **Release turn** of a group released before its join (10,000 pending claims, no job): 0.14–0.16 ms (the first 512 claims; the rest in later turns of 512).
- **Claimed-only retirements**: the successor's release when its claims alone kept 10,000 jobs: 4.34 ms for the first turn of 512 retirements, against 4.30–4.60 ms for the existing chunked interest release of 10,000 joined members without claims (512 retirements a turn). The claims add nothing over the existing release chunking; the predecessor's release turn whose jobs the claims kept cost 0.47 ms.
- **`claimNewlyListed`** (10,000 members registered before start, claimed when the launch adopts the manifest): 1.01–1.05 ms.

The claim bookkeeping stays under the ruling's ~2 ms in one turn; releases drop claims at most `releasesPerTurn` a turn, as interest releases do. Every turn is within C2's 10 ms. (Observation for WP-F, not changed here: `releasesPerTurn`'s doc estimates about 1 µs per removal; a retirement of a queued job measured about 8.5 µs at this load, so a 512-member release turn is about 4.4 ms.)
