# ADR drafts — WP-B storage core (Stage 2, level L2)

Owner: WP-B. The orchestrator numbers these into `DECISIONS.md` at merge (ARCHITECTURE §1.2). Each entry: context · options · decision · consequences.

## B-1 — Live lock tokens carry a nonce parked in the descriptor's file offset
- **Context.** The conformance suite's stale-token clause (ADR-049) binds `LiveFileSystem.releaseLock`: descriptor numbers are reused after `close`, so a token holding only the descriptor would unlock a lock taken since. `LiveFileSystem` is a stateless struct; the iOS 15 floor and the unsafe budget rule out a lock table.
- **Options.** (a) A process-wide token table (needs a lock or an escape). (b) Write a nonce into `store.lock` (the file is documented empty). (c) Park a nonce in the descriptor's file offset with `lseek`, which writes nothing, and carry it in `FileLockToken.handle`.
- **Decision.** (c): `handle = nonce << 32 | descriptor`, nonce in `1...Int32.max` from `SystemRandomNumberGenerator` (a live conformer may draw, R-ENV-1 scan). `releaseLock` unlocks and closes only when `lseek(fd, 0, SEEK_CUR) == nonce`.
- **Consequences.** Release twice and stale releases are no-ops (conformance passes on the live conformer). `FileLockToken.handle`'s and `FileSystem.releaseLock`'s doc comments now describe the nonce-packed live handle and that releasing a stale token releases nothing (doc-only; no declaration changed).
- **Orchestrator ruling (L2 close-out).** Ruling (3): the doc-only edit of those two comments in `Sources/ZTronAssetModel/Environment/FileSystem.swift` is authorised; done in fix round 3.

## B-2 — Resource values are read through a fresh `URL`
- **Context.** `NSURL` caches resource values for the object's lifetime on threads without a run loop; the store keeps one root `URL` for its lifetime, so free space and backup exclusion read through it went stale (a live test caught it).
- **Decision.** `availableCapacity` and `storeAttributes` read through `URL(fileURLWithPath:)` built per call.
- **Consequences.** One small allocation per query; figures are current.

## B-3 — The v1 `index.bin` byte layout · **NEEDS-HUMAN-REVIEW** (on-disk format)
- **Context.** store.md §2.3 and ADR-012 fixed the shape; Stage 2 fixes the bytes (schema 1 is not shipped yet).
- **Decision.** Header (64 bytes, little-endian): magic `ZTAKIDX\0` · `schemaVersion` u16 · `sectionCount` u16 · flags u32 (bit 0 degraded) · `generation` u64 · `bodyLength` u64 (≤ 64 MiB) · `writtenAtMillis` i64 · launch epoch u64 · `storeID` 16 bytes. (store.md's `headerLength` field is dropped: 64 is implied by the schema; the launch epoch takes its room.) Body: sections `(tag, varint length, payload)` in increasing tag order, STAMPS `0x01`, STRINGS `0x02`, RECORDS `0x03`, DOOMED `0x04`; unknown tags `< 0x80` malformed, `≥ 0x80` skipped. Trailer SHA-256 over header and body. Dates are the IEEE bit pattern of `timeIntervalSinceReferenceDate` (exact round trips; store.md's whole seconds would lose sub-second stamps). STAMPS: presence bitmap, sync stamp (app version, completion, manifest digest, optional ETag), applied ETag, `syncDue`, `lastCleanupAt`, legacy stamp, legacy phase, applied manifest digest, wire shape, quarantine count. RECORDS: per-record flag varint (12 bits) with the omissions "expected = checksum" and "blob = expected"; DOOMED: sorted keys with `DoomReason`. Strings are interned by their UTF-8 bytes (identifiers differing only in normalisation stay distinct). The decoder accepts exactly one encoding per state (sorted DOOMED, no redundant hashes), so a valid file re-encodes byte-identically (golden fixture `Tests/Fixtures/index/v1/golden.bin` + `golden.json`, R-STO-12).
- **Consequences.** 10,000 records encode to 1.41 MB. A schema change adds `v2` fixtures and a decoder.

- **Orchestrator ruling (L2 close-out).** Ruling (2): B-3 stays **NEEDS-HUMAN-REVIEW** (on-disk format); no change in fix round 3.

## B-4 — The applied manifest is persisted through its records
- **Decision.** RECORDS are written in applied-manifest order; records not in the manifest follow, sorted and flagged *detached*; an applied entry without a record is written as `absent(.neverFetched)`. Load rebuilds `ValidatedManifest` from the non-detached entries plus STAMPS' digest, shape and quarantine count. Per-entry quarantine **diagnostics** are not persisted (`quarantined == []` after a reload; `quarantinedCount` kept).
- **Consequences.** No second copy of 10,000 entries. WP-C's legacy phase 1 keeps the invariant (records ⊆ applied ids) by construction.

## B-5 — Launch epoch, launch commit, read-only open
- **Decision.** `launchEpoch` is the generation of the commit every `open()` performs (persisted by that commit; `nextGeneration = 1 + max(generation, launch epoch)` over every parsed header). A failed launch commit leaves the store open on the loaded state with the commit due (store-1 S1-07); `OpenReport.generation` is then the loaded one.
- **Consequences.** One ordered commit per launch (P-5-cheap). If the launch commit fails before anything reached the disk, the next launch may reuse the epoch; staging names of that launch then collide only with this launch's (exclusive renames report `nameInUse`). The epoch also repeats on a wiped root (every fresh root starts at 1); B-17 makes that safe for the deletion protocol. When the load rule chooses `index.tmp`, `committedGeneration` is the newest generation outside it (`IndexLoadOutcome.survivingGeneration`) until the launch commit promoted `index.tmp` to `index.bin` (B-28; before fix round 3 the launch commit truncated it): keys doomed only in `index.tmp` wait for that promotion or a later commit (fix round 1).
- **Close-out cycle 4 amendment (review "I-5 / ADR-013 launch-epoch uniqueness").** Two more launches may take an epoch an earlier launch had. A read-only launch (B-34) computes `nextGeneration` without the header of the file it could not read, so it may take the previous launch's epoch even when that launch's commit succeeded (review probe: launch B commits generation 3 with epoch 3 and is killed; launch C, with EIO on the first stat or read of `index.bin`, opens with epoch 3). After a launch whose root barrier and launch commit both failed (B-36), a power loss can bring back older names, so a later launch may take that launch's epoch. Neither lifetime places anything under its epoch in WP-B: a read-only lifetime writes nothing, and the other counts nothing committed; staging names are L3's, where exclusive renames report `nameInUse`. **For the orchestrator:** ARCHITECTURE §4.5 and the ADR-013 note should say that a launch epoch is unique only across launches whose launch commit succeeded over a readable index, so L3's staging reconciliation never takes epoch equality alone for "this launch" (or the engine stages nothing while the store is `storageUnavailable(.ioFailure)`). Exposing the read-only state on `OpenReport`, the review's other option, would change a contract type and is not done here.

## B-6 — Degraded mode: when, and what it suspends
- **Decision.** Degraded when the load rule says so (no valid generation although a file existed, an invalid `index.bin`, a newer schema, a persisted degraded flag) **or** when no index exists but `blobs/` holds blobs. While degraded the reaper deletes nothing at all (S1-11's "DOOMED keys protected" generalised: the doom set itself is untrusted). Unreferenced blobs listed at launch are remembered as orphans; `apply` re-stats each candidate in one unit before binding it (proposed row b-5), then clears degraded.
- **Consequences.** R-STO-4's rebuild works without re-downloading verified assets.

## B-7 — Commit coverage and the coalescing window
- **Decision.** Mutations are counted (`markDirty`); a commit covers every mutation counted before its capture; at most one commit runs; commits start at most once per `commitMinimumInterval` — `runDueWork()` serves `.soon` mutations at the window, and `requireCommitted` sleeps on `TimeSource.sleep(until:)` in the **caller's** task until the window opens (proposed row b-2; the store still owns no task or timer). `requireCommitted` re-checks the phase first.
- **Consequences.** ≤ 4 commits/s by construction (P-5 rate benchmark: at most 4 in any second of a simulated 10 s bulk sync). Checksum-less and rescue publishes, which must commit before returning (S1-05), share these commits: a checksum-less bulk sync publishes at most `concurrency × 4` assets per second — acceptable for the legacy tier, recorded here for WP-F.

## B-8 — Snapshots: incremental table, fresh acknowledgements
- **Decision.** `presentTable` (one `SnapshotEntry` per present record) is updated per changed record, so an install wraps it in O(1) (the test invariant checker compares it with a rebuild). Acknowledgements count only for the store's epoch. The "fresh acknowledgement" of ADR-017 is the start instant (awake clock) of the newest acknowledged install: a key is deletable when its grace ended before that instant. An install started after the grace that came back unacknowledged makes the key acknowledgement-blocked: no deadline (store-1 S1-13), but every later `runDueWork()` retries the fresh install.
- **Consequences.** No busy alarm with a sink that keeps an older or foreign snapshot; recovery as soon as it acknowledges.

## B-9 — Benchmark statistics (P-2, P-5, P-6, P-13)
- **Decision.** Durations: p95 (store.md §11 R1 measured single-sample tails 2–3× the p95, scheduler noise on a shared machine; a max-based budget would flake, Q-5). P-5's budget is applied to the ordered commit a bulk sync performs (p95); durable commits (flush, close, adoption report) are judged on their median, their tail being the device-wide `F_FULLFSYNC` cache flush shared with all I/O. P-6 throughput: best of five runs per variant after a warm-up (interference only slows runs down); memory: peak resident delta sampled **inside every read** while the chunk is alive (`ReadSamplingFileSystem`, fix round 1; the baseline is taken before the warm-up). P-13: total wall time and the p95 of deletion-unit durations; the maximum is printed next to it. P-2 times the store's own load path (`IndexLoader.load`, which `open()` calls; fix round 1). C2 (no budget key): the longest hold of the store's actor seen by a probe that calls a cheap synchronous API in a loop, best of five runs, against the rule's 10 ms (B-19).
- **Consequences.** Recorded in `BenchStorage.swift`'s doc comment. **Fix round 1, declined:** asserting P-13's maximum instead of its p95 (review "benchmarks (P-13)"): the level's runs share the machine with other worktrees (load average 4–15), where single units measured 6.8–9 ms while the p95 stayed at 3.0–3.3 ms; a max assertion would fail on noise, not on the code. The maximum stays printed; the orchestrator decides when it numbers this ADR, and a max-based rerun belongs on a quiet machine.
- **Fix round 2.** The P-13 p95 failure under load is fixed in the code (B-10's amendment), not in the statistic: unit p95 is now 2.0–2.4 ms against 5 ms. The maximum still shows single 6–10 ms units (load average 3–4.5), which is preemption of the unit's thread, not unlink work; so the statistic choices (P-5 durable on its median, P-6 best of five, P-13 on its p95) remain **for the orchestrator to rule on** before merge, with the reference run `bash Scripts/verify.sh --perf` on a quiet machine (review "benchmarks (P-2, P-5, P-6) under machine load").

- **Orchestrator ruling (L2 close-out).** Ruling (1): P-2 on the p95 of cold loads, ratified. P-5 judges **both** the ordered and the durable commit on the **p95** (not the median) against `index_commit_ms`; the commits-per-second ceiling is a hard maximum (as implemented: the worst sliding second). P-6 best of five throughput runs, ratified. P-13: SPEC §6 "in batches ≤ `batch_ms_max` ms between suspension points" bounds **every** batch, so the test asserts the **maximum** deletion-unit duration (p50 and p95 printed beside it) and the code makes it fit by design (B-10's budget halved to 1 ms, justified by a measured unlink profile). Done in fix round 3: `BenchStorage.swift` asserts `p95 <= budget` for both P-5 durabilities and `max <= batch_ms_max` for P-13; the P-13 line also prints an unlink profile of the volume, each unit's on-CPU time and every unit over the budget.
- **Fix round 3 measurement and profile (release, this Mac: 8 cores, APFS; other worktrees building).** With the 1 ms unit budget, every P-13 run reclaims 10,000 blobs in 497–578 units and 0.59–0.71 s, unit p50 0.96 ms, p95 0.99 ms, unit **on-CPU max 1.00–1.11 ms**, but the **wall-clock max is 6.6–10.5 ms in every run** at load averages from 3.7 to 9.5 (1-minute `vm.loadavg` before each run: 9.5, 8.9, 8.4, 5.1, 7.1, 7.2, 3.9, 3.7), so the max assertion fails. The instrumented runs locate it: each run has 3–5 units over 5 ms, and **each of them contains exactly one blob unlink that blocked in the kernel for 4.6–9.3 ms** (`InstrumentedFileSystem` times every unlink under `blobs/`; the unit's thread was off CPU meanwhile: 0.19–1.05 ms on CPU against 5.0–10.5 ms of wall time). A single unlink otherwise takes p50 0.045 ms, p99 0.06–0.08 ms. The stalls arrive about every 150 ms of sustained unlinking (4–5 in a 0.7 s run, none in the 0.09 s profile pass of 2,000 unlinks), which matches the volume committing a metadata transaction while an unlink waits for it. Two experiments, not kept: a `.userInitiated` executor instead of the production `.utility` (stalls unchanged, 5.2–9.7 ms), and a full sync of `blobs/` before timing, so the reclaim starts on a settled volume (stalls unchanged, 4.6–8.5 ms). Under heavier load (16–26) single unlinks blocked up to 47 ms and every budget of this file missed (environment). **Belief, with that profile: the maximum probably does not fit even on a quiet machine on APFS**, because the overrun is one blocking `unlink(2)` waiting for the file system, which no bound on a unit's own work (time or count) can shorten: the unit's work is bounded at about 1 ms, and within a unit each next unlink is predicted from the slowest unlink that unit has seen itself, so a unit stops right after a slow unlink; every unit starts fresh (`slowest = 0`), so its first unlink is never predicted and nothing carries over between units (wording corrected in the close-out cycle 2, review "ADR accuracy (B-9 P-13 profile)"). The assertion is not weakened; the orchestrator's quiet-machine `--perf` run decides, and the printed line (units over budget with their on-CPU time, and the stalled unlinks) shows whether any overrun is the unit's work or the volume.

## B-10 — Deletion units are bounded by time as well as by count
- **Context.** P-13 bounds the time between suspension points (5 ms). Measured during this level with other worktrees building (load average 7–15): 64 raw `unlink`s took p50 5.3 ms, p95 7.8 ms in a standalone probe — the count bound alone cannot hold the budget on a busy or slow volume.
- **Decision (final value, as amended in fix rounds 2 and 3).** `deletionBatchSize` (64, ADR-035) stays the maximum; each deletion unit also stops once its time budget `BlobDeletionUnit.budget` = **1 ms** of the injected monotonic clock is spent: it makes at least one unlink, and before every later one it stops when the time spent plus the slowest unlink it has seen itself would pass the budget (the last unlink is predicted). The keys it did not attempt go first into the next unit, unchanged (no backoff). (The original decision of this level said 3 ms without prediction; superseded by the fix-round-2 amendment, 2 ms with prediction, and the fix-round-3 amendment, 1 ms. Number 1 ms.)
- **Consequences.** Units stay inside the budget under load (P-13 unit p95 3.2 ms with the original 3 ms; 0.99 ms with the final 1 ms, fix round 3); `ManualTimeSource` never advances inside a unit, so deterministic tests see count-bounded units. Deviation from ARCHITECTURE §4.4's "units of 64" wording, for the orchestrator.
- **Fix round 2 (review "benchmarks (P-13)", blocking).** Every unit ran right up to the 3 ms deadline (p50 3.03 ms) and then made one more unlink, so the only headroom for that unlink and any preemption was 2 ms; under load average 6–12 the unit p95 reached 5.26–5.27 ms against 5 ms. Now the budget is 2 ms **and** the unit predicts its last unlink: before each unlink after the first it stops when the time spent plus the slowest unlink it has seen would pass the budget. Test: `P-13: a deletion unit stops when its time budget is spent…` (two unlinks per unit at 1 ms per clock read, 10 units for 20 keys). Measurements under "Fix round 2" below.

- **Fix round 3 (orchestrator ruling (1) on B-9: P-13 is judged on the maximum).** The budget is 1 ms (a fifth of `batch_ms_max`), the last unlink still predicted. With a single unlink at p50 0.045 ms / p99 0.07 ms on this volume, a unit makes about 20 unlinks (10,000 blobs in about 500 units, 0.6 s against the 2 s budget) and its own work stays ≤ 1.08 ms on CPU; one unit plus one slow unlink stays far below 5 ms. Test: `P-13: a deletion unit stops when its time budget is spent…` now derives the expected unit count from the budget (one unlink per unit at 1 ms per clock read, which only the prediction achieves).
- **Orchestrator ruling (L2 close-out).** Ruling (2): B-10 (time-bounded deletion units) ratified; the §4.4 wording "units of 64" becomes "units of at most 64 and at most `BlobDeletionUnit.budget`" at merge.

## B-11 — Publication details
- **Decision.** (1) Ids are validated, not all-or-nothing: unknown and changed ids are skipped; `.unknownAsset`, `.assetFailed` or `.superseded` is thrown only when none remains; the returned dictionary lists the ids bound. (2) Ids sharing a checksum but not an extension get one blob per extension (B-18 since fix round 1: the destination key is acquired first; a live or rescuable one is bound in place without copying; otherwise the placed blob is copied to a staging name of its own, verified, and placed). (3) A cancelled hash renames `.verifying` back to `.part`, so the caller can retry with the same `StagedFile`. (4) Size cap and manifest size are checked before hashing; the hashed byte count must equal the claimed size (bytes added to a claimed file are a size mismatch). (5) A verified publication replaces a `purged` or `corrupt` name with `rename(.replacing)`; an `unreferenced` doom is rescued and committed before returning.
- **Consequences.** Covered by `StorePublishTests`, `StoreEdgeTests`, `StoreInternalsTests`.

## B-12 — Launch and `apply` adoption also bind records to live blobs
- **Context.** ARCHITECTURE §4.5 binds "an unreferenced, non-doomed blob" to records that expect it. A dedupe publish (a second id onto a live key) that returned before a kill is in no committed generation; restricting adoption to unreferenced blobs would re-download it.
- **Decision.** Adoption binds a record that accepts adoption (ADR-018's residencies) to any listed key that is live, unreferenced, or doomed `unreferenced` (rescued) — never to `purged` or `corrupt` dooms.
- **Consequences.** Strictly fewer downloads; for the orchestrator to reword §4.5.

- **Orchestrator ruling (L2 close-out).** Ruling (2): ratified (adoption binds records to live blobs); §4.5 reworded at merge.

## B-13 — Staleness and checksum-less expectations
- **Decision.** `AssetRecord.isStale` ⇔ the referenced blob differs from the expected key (expected hash with the entry's extension). A checksum-less publish records the digest of the written bytes as `expectedBlob` (R-INT-6), and a checksum-less content change (`remotePath`) clears it, which makes the present blob stale.
- **Consequences.** One rule for checksum, checksum-less and extension changes; `isStale`, `referencedBlob` and `expectedKey` are `package` for the planner.

## B-14 — `setResidency(.present)` and unknown records
- **Decision.** A transition to `present` through `setResidency` is honoured only for a key that can be referenced without I/O (live, or doomed `unreferenced`); otherwise, and for an unknown id, nothing changes. (`adoptVerifiedFile` is the I/O path.)

## B-15 — A replaced root stops all commits
- **Decision.** When the commit unit finds the lock file's identity changed, the store records `unavailable = .rootVanished`: every later commit and mutating API throws `.storageUnavailable(.rootVanished)` at once, `nextDeadline()` keeps no commit deadline, reads keep working; the facade reopens.

Since fix round 1 a replaced root also stops the reaper: `deletionBlocker` returns `.unavailable` (no deadline) while `unavailable != nil`, so nothing under a path that may now belong to another store is unlinked.

## B-16 — Test seams that stand in for WP-C at L2
- `AssetStore.testSetLease`, `testClearLeases`, `testSetRetentionScope`, `testSetIntegrity`, `testBumpPurgeEpoch`, `testExpect`, `testInsertRecord` (test-target extensions) write WP-C's fields the way WP-C's APIs will, so WP-B's reaper, adoption report and stamp logic are tested before WP-C exists. WP-C may switch these tests to its APIs.
- Live file-system tests and benchmarks use directories under `.build-tests/` at the repository root (git-ignored through `.build*`), removed by each test.

- **Orchestrator ruling (L2 close-out).** Ruling (2): ratified: these seams are internal test-target extensions that write WP-C fields the way WP-C's APIs will, documented as test seams and never public.

## B-17 — An acknowledgement counts only for an install that took effect (fix round 1, review probe P2)
- **Context.** ADR-016/§5: the store acknowledges only its own epoch. The epoch comes from the index files alone, so it repeats on a wiped root (B-5). After a `rootVanished` reopen (B-15) the process-wide mirror still holds the previous store's `(1, N)`: it refuses the new store's `(1, v ≤ N)` and answers `(1, N)`, which the old rule took for an acknowledgement of version N — grace started and the reaper unlinked a blob the reader-visible snapshot still listed.
- **Options.** (a) Floor the epoch with the wall clock (`max(nextGeneration, nowMillis)`): no strict uniqueness (clock jumps, two opens in one millisecond, a manual test clock), generations jump to 10¹². (b) The facade resets the mirror before a replacement store's first install (orchestrator; §5 says reset is for shutdown). (c) Count an acknowledgement only when the sink swapped in exactly the offered snapshot: `retired != nil` (an install that swapped returns the replaced snapshot, `InstallAck.retired`'s contract) and `installed == offered`, of this epoch.
- **Decision.** (c), in `AssetStore.acknowledges(_:_:epoch:)`. A refusal never counts, even one in favour of a newer snapshot of this store (that newer install's own acknowledgement does).
- **Consequences.** I-3 holds whatever the mirror holds. **For the orchestrator (liveness):** a replacement store whose epoch is ≤ the mirror's cannot install a snapshot until its version passes the old one (or never, with a smaller epoch): readers keep the old store's snapshot. The facade should call `SnapshotMirror.reset()` before a replacement store's first install (option b, an amendment to §5), or the orchestrator chooses a process-unique epoch. Regression test: `R-CLN-5: a replacement store whose epoch repeats never counts the previous store's snapshot as acknowledged`.

- **Orchestrator ruling (L2 close-out).** Ruling (4): `SnapshotMirror.reset()` after a `rootVanished` reopen is noted for WP-G; nothing more in WP-B, this entry stays.

## B-18 — Binders of one key are serialised (fix round 1, review probe P1)
- **Context.** Every bind of one digest under a second extension copied into the same staging name (`…-4294967295.parttmp`) in truncate/append units with awaits between them, then renamed it into `blobs/` without hashing it: two concurrent binds tore each other's copy (I-1, I-2 violated). And a `replaced` key (doomed `purged`/`corrupt`) was live while its file was still being replaced, so a concurrent binder could bind a record to the damaged bytes.
- **Decision.** `acquireReference` waits whenever the key is in `publishing`, whatever its table state; a `new` or `replaced` acquisition holds the key in `publishing` until its placement unit finished (or was given up, `abandonAcquisition`). `bindCopy` acquires the destination key **before** copying: `reused`/`rescued` bind in place without I/O (a live or rescuable key's file is complete, I-2); `new`/`replaced` copy into `staging/c-<hash>.<epoch>-<seq>.parttmp` with a store-allocated sequence counting down from `UInt32.max` (`StoreCoreState.nextCopySequence`), hashing while copying, and the copy is placed only with exactly `byteCount` bytes hashing to the name (I-1 even if the source changed). `setResidency(.present)` refuses a key in `publishing`.
- **Consequences.** A key in `publishing` is never doomed (rescue and replace make it live synchronously, a new key enters the table only after its placement), so `deletionBlocker`'s `.publishing` case was unreachable and is removed; §4.4's "no publication in flight" holds structurally (documented in `AssetStore+Reaper.swift`). Tests: `R-INT-1: two publications binding one digest under a second extension copy it once and never place a torn copy`, and the copy failure, replacement and close tests in `StoreSweepTests`.

- **Orchestrator ruling (L2 close-out).** Ruling (2): ratified.

## B-19 — The store's actor is never held for long at 10,000 assets (C2; fix round 1, review probe P4)
- **Context.** `open()` reconciled and built the snapshot table of 10,000 records on the actor (about 62 ms in release); `apply` diffed and wrote 10,000 records before its first unit (15–16 ms); re-adopting 10,000 blobs in one `apply` (a rebuild after a lost index, R-STO-4) took 61 ms.
- **Decision.** (1) `LaunchState.build` (reconciliation and snapshot table) runs in one bulk unit; `open()` only assigns. (2) `ApplyPlan.compute` (diff, identity, the added records, the adoption candidates) runs in one bulk unit against values captured on the actor; the plan is discarded and made again if `manifestRevision` changed meanwhile. (3) `apply` and `admit` are serialised by a gate (`StoreCoreState.applyGate`), and `apply`'s inserts, content changes, adoptions and prunes yield the actor every `AssetStore.sweepChunk` (512) items, re-checking the phase; each write re-reads the record it touches (R8's pattern). (4) DOOMED is derived inside the commit unit from the blob table captured at the same instant (`IndexCommitInput.completeContent`).
- **Consequences.** Measured in release on this Mac (longest probe wait, best of five; load average 3–6): open 0.7 ms, first apply 0.7 ms, unchanged re-apply 0.04 ms, prune of all 2.1 ms, re-adoption of all 3.0 ms (59.6 ms with the chunking disabled, which the benchmark caught). Between chunks other calls see an `apply` in progress: records not yet added or not yet pruned (persisted as detached records by a commit captured meanwhile, B-4), adoptions partly done; every such state is a valid store state. **Superseded in fix round 2 (B-23):** such a state is valid in memory, but persisting it is not, so no commit captures it any more. The C2 benchmark: `C2: open and apply of 10,000 assets never hold the store's actor for more than 10 ms at a stretch`.

- **Orchestrator ruling (L2 close-out).** Ruling (2): ratified.

## B-20 — A doomed key always gets a commit and an install (fix round 1, review probe P3)
- **Decision.** Whenever a key becomes doomed (`releaseReference` dooms the last reference, or a dropped rescue/replacement restores its doom), the store marks a `.soon` mutation and a due install. A provisional reference dropped after a failed placement, with the other references pruned meanwhile, used to doom the key with no commit and no install ever covering it: `nextDeadline()` stayed `nil` and the bytes stayed `pendingReclaim` for good.
- **Consequences.** Test: `R-CLN-1: a reused placement that fails after a prune dooms the key with a deadline and is reaped`.

## B-21 — A publication re-validates its records after every post-binding await (fix round 1, review probe P5)
- **Decision.** After the S1-05 commit and after the snapshot install, `publish` keeps only the ids whose record still exists, still wants these bytes and is still present at the returned blob, re-reads each location from the current snapshot entry, and throws `.superseded` when none remains (ARCHITECTURE §4.3 step 9, store-2 S2-15); `.closed` once the store closed.
- **Consequences.** Tests: `R-INT-2: a prune during a checksum-less publication's commit yields superseded and never returns the URL`, `R-INT-2: a prune during a publication's snapshot install yields superseded and never returns the URL`.

## B-22 — Non-finite dates are clamped when the index is written (fix round 1)
- **Decision.** The decoder rejects non-finite dates, so the writer clamps them (`+∞` → `distantFuture`, `−∞` and NaN → `distantPast`) instead of writing an index no launch can load.
- **Consequences.** Test: `R-STO-12: a non-finite date is clamped when written, so every later generation stays loadable`.

## B-23 — `apply`'s writes are fenced from every commit (fix round 2, review probes 2 and 4) · blocking
- **Context.** B-19 made `apply` yield the actor between chunks after it had already installed the new applied manifest, ETag and digest. A commit captured at a yield (the coalesced commit of `runDueWork`, `flush`, `markSynced`, `markSyncDue`, a checksum-less or rescue publication, `adoptionReport()`'s durable commit, `close()`'s durable commit) persisted the new ETag with records partly added, changed or pruned; B-4 rebuilds the manifest from the records, so after a crash or a clean close the index claimed ETag two while thousands of entries kept manifest one's content. The engine's conditional GET (R-NET-5) then gets `304` and never re-applies them. Measured before the fix: 5,120–5,632 of 6,144 records stale after a commit woken mid-apply, and after `close()` mid-apply.
- **Options.** (a) Defer `appliedManifest`/`etag` to the last chunk: avoids the `304` trap only; commits still persist half the records and other readers (the adoption report) still see half state. (b) A commit fence held from `apply`'s first write to its last.
- **Decision.** (b). `ApplyGate.writing` is raised in the same turn as `apply`'s last phase check (after its plan unit) and lowered right after its last synchronous write; while it is up `requireCommittedInternal` waits on `ApplyGate.writeWaiters` before any capture, `adoptionReport()` waits before capturing, `runDueWork()` makes no commit and `nextDeadline()` reports no commit deadline (`apply`'s own commit, right after the fence drops, covers every pending mutation; reporting the window would only make the alarm spin), and `close()` drains units, then waits for the fence before its durable commit. `apply`'s writes no longer throw between chunks: once begun they run to the end even if `close()` began meanwhile (close waits for them), and the phase and writability are checked again by `apply`'s commit, which then unwinds with `.closed`. Proposed REENTRANCY row b-8; row b-7 amended.
- **Consequences.** Every committed generation holds either the previous manifest with its records or the new one with all of its records. A commit asked for during the writes waits for them (a few milliseconds at 10,000 entries, B-19's measurements). Snapshots built during the writes still show records partly applied (each record individually valid, in memory only). Tests: `R-NET-5: a commit asked for while apply writes its chunks waits for the whole apply…`, `R-NET-5: close while apply writes its chunks waits for the whole apply…`, `R-NET-5: while apply's writes are fenced no commit, adoption report or close captures the state…` (the fence held at a known point through the seam `testRaiseApplyFence`).

## B-24 — A doom under replacement is persisted (fix round 2, review probe 3) · blocking
- **Context.** `acquireReference` makes a key doomed `purged` or `corrupt` `live(1)` and holds it in `publishing` while the verified bytes replace the name. A commit captured during that placement derived DOOMED from the blob table and dropped the key, so after a crash before the replacement rename launch saw an unreferenced, undoomed name and adopted the rotten bytes, `verified`, into the record (probe: the reopened snapshot served them).
- **Decision.** `StoreCoreState.replacingDooms[key]` keeps the previous doom from the `.replaced` acquisition until the placement finished or was given up (`releasePublishing`); `IndexCommitInput.replacingDooms` carries it and `completeContent` writes it to DOOMED although the table says `live`. Mirrors `deletingDooms`.
- **Consequences.** A crash before the rename leaves the name doomed with its reason: never adopted, reaped after acknowledgement and grace, the record re-downloads. A crash after the rename but before the binding commit loses one verified download (the name is reaped as doomed), never correctness. Test: `R-STO-5: a commit during a corrupt key's replacement keeps the key doomed, so a crash never adopts the rotten bytes`.

## B-25 — A rescue or replacement that binds nothing is doomed afresh (fix round 2, review probe 1) · blocking
- **Context.** `dropProvisionalReference` restored the key's old `DoomInfo` verbatim (old `eligibleAt`, `sinceSnapshotVersion`, `droppedInGeneration`). While the provisional reference was held the key was live, so another record could gain it (`apply` adoption, a dedupe publish), appear in an acknowledged snapshot and lose it again; a release from 2 to 1 references only decrements. The restored, long-expired `eligibleAt` then let the reaper unlink the blob at the same instant the snapshot without it was acknowledged: no grace (I-3).
- **Options.** (a) Restore only when `snapshots.version` and `nextGeneration` are unchanged since the acquisition. (b) Always doom afresh.
- **Decision.** (b): `DoomInfo(reason: previous.reason, sinceSnapshotVersion: version + 1, droppedInGeneration: max(previous, nextGeneration), eligibleAt: nil, failedUnlinks: previous.failedUnlinks)` plus `scheduleDoomedKey()` (B-20). Strictly more conservative than restoring; the reason (`purged`, `corrupt`) and the unlink backoff are kept.
- **Consequences.** A dropped rescue waits one more acknowledgement and grace (a rare path: the placement failed, the records changed, or the store closed). Test: `R-CLN-5: a rescue that binds nothing after another record gained and lost the key is doomed afresh and waits a new grace`.

## B-26 — A failed publication leaves nothing in staging (fix round 2, review "staging hygiene")
- **Decision.** A hash unit or placement unit that fails with a file-system error discards the claimed `.verifying` file and its sidecar (`discardClaimed`) before `.fileSystem` is thrown; a failed placement of an extra-extension copy removes the copy. Cancellation still hands the claim back as `.part`; `.closed` leaves the files to staging collection (no I/O after close).
- **Consequences.** The engine retries under a new attempt name, so the discarded bytes were of no further use; nothing full-size is stranded until the next staging collection. Tests: `R-INT-2: EIO while hashing the claimed file fails the publication and discards the claim and its sidecar`, `R-INT-1: EIO on placing a copy under a second extension binds nothing under it and leaves no copy in staging`, and `R-STO-5: EIO on the blob placement rename…` now also asserts an empty staging directory.

## B-27 — A fan-out created by a failed placement still dirties `blobs/` (fix round 3, review probe 4) · blocking
- **Context.** The placement unit creates `blobs/<aa>/` before its rename. When the rename failed, the store dropped the fact that the fan-out was new; the next placement into it found it present (`createdFanOut: false`), so the commit that referenced that blob barrier-synced the fan-out but never `blobs/`, and a power loss dropped the fan-out's entry with the committed blob in it (ARCHITECTURE §3 "barrier-synced before the commit that references a blob in it").

## B-28 — The commit unit never drops the newest valid generation (fix round 3, review probe 1) · blocking
- **Context.** Three gaps combined (probe 1): (1) the ENOSPC fallback of step 2 removed `index.tmp` and then `index.prev` without checking `index.bin`; (2) a step-5 failure (`index.tmp → index.bin`) after step 4 left no `index.bin`, the committed generation only in `index.prev`; (3) a launch whose load rule chose `index.tmp` truncated it in its launch commit. After a crash or EIO between steps 4 and 5, a launch on a full volume therefore deleted every generation: the store ran with no index on disk, the next launch was degraded with the epoch back at 1 (I-5), and a `corrupt`-doomed name was re-adopted and served (§4.4).
- **Options.** (a) Track on the actor whether `index.bin` holds the committed generation. (b) Have the unit prove it on the ENOSPC path from the file itself. (c) Never drop `index.prev` on ENOSPC (no room is ever made).
- **Decision.** (b), with a rollback and a promotion step:
  1. **ENOSPC fallback.** `index.prev` is removed only when `index.bin`'s header names the committed generation (`IndexCommitInput.committedGeneration`) and its size is exactly `64 + bodyLength + 32` (`IndexCommitUnit.currentHolds`). `index.bin` only arrives by renaming a synced, complete `index.tmp`, and each attempt has a generation of its own, so that header identifies the committed file; a rotten, foreign or newer-attempt `index.bin` names another generation and `index.prev` is kept. Reading 64 bytes happens only on the ENOSPC path.
  2. **Rollback.** When step 5 fails after step 4 moved `index.bin`, the unit renames `index.prev → index.bin` (exclusive, so it never overwrites anything that did reach `index.bin`). `index.bin` is never missing after a failed commit; the synced `index.tmp` stays and a later launch may still load it.
  3. **Promotion.** When the load rule chose `index.tmp`, `LaunchState.promotion` (→ `CommitBookkeeping.pendingPromotion`) holds its generation, and every commit attempt first **syncs `index.tmp`** (barrier, or full for a durable commit; since the close-out cycle 2, see the amendment below), then renames it to `index.bin` (steps 4–5 with the same rollback) and syncs the root, before it writes `index.tmp` again. `IndexCommitOutcome.promotedName` clears the pending promotion (the file is gone from `index.tmp` even if the sync failed); `promotedDurably` raises `committedGeneration` to the promoted generation, the ENOSPC check then uses it. Until then `committedGeneration` stays `survivingGeneration` (B-5).
  The case "`index.bin` missing, `index.prev` chosen" needs no promotion: (1) keeps `index.prev`, and a successful commit skips step 4 and renames `index.tmp → index.bin`.
- **Consequences.** On a full volume the newest generation always stays on disk, so I-5 and the DOOMED reasons survive (probe 1 now: `index.bin` holds the promoted generation after the full-volume launch and its close). A loaded `index.tmp` costs one extra file sync, rename pair and root sync at the launch commit. ARCHITECTURE §4.1 ("On ENOSPC at step 2: remove `index.tmp` and `index.prev`") and §3 (`index.prev` "removed on ENOSPC at commit") need the wording "…and `index.prev` only while `index.bin` holds the committed generation", plus step 0 (promotion) and the step-5 rollback, for the orchestrator. Tests: `R-STO-4: ENOSPC at a launch after a crash between commit steps 4 and 5 keeps a valid generation on disk and never re-adopts a corrupt doom` (probe 1, crash and EIO variants), `R-STO-4: the ENOSPC fallback removes index.prev only while index.bin holds the committed generation` (committed / missing / rotten / other generation), `R-STO-4: EIO on either commit rename keeps the previous generation on disk…` (now asserts `index.bin` holds the committed generation for both renames), `R-STO-4: keys doomed only in a loaded index.tmp wait for a commit that survives the failed launch commit` (now parameterised by the failing promotion step, rename or sync: the earlier ENOSPC trigger no longer fails the promotion, which is the fix), and two enumerations in `StoreCrashTests`: `R-STO-5: a fault at every commit step, a kill, then a launch on a full volume preserve I-1…I-5` (EIO on `tmp → bin`, EIO on `bin → prev`, EIO on the root sync, ENOSPC on the write, each at every commit of the first sync) and `R-STO-5: crash at every boundary, then a launch on a full volume, preserves I-1…I-5` (all four crash modes, 75 points each). Both enumerations failed on the previous unit (lost generations, "no valid index", I-5).
- **Close-out cycle 2 amendment (review "crash-consistency (index commit protocol, launch promotion)", probe VP7) · blocking.** The load rule accepts any complete `index.tmp` whose checksum verifies, which includes one a killed process wrote at step 2 and never synced (killed before step 3). The promotion renamed that file to `index.bin` and synced only the root, never the file's data; `promotedDurably` then raised `committedGeneration` to its generation, so on a full volume the ENOSPC fallback saw `index.bin` naming the committed generation and removed `index.prev`, the last generation whose data was synced. A power loss then left no valid generation (`powerLossKeepMetadata`: the epoch restarted at 1, the record was lost and the `corrupt`-doomed name was re-adopted and served; `powerLossDropUnsynced`: `index.bin` reverted to empty, degraded). It also let the reaper count an unsynced generation as committed. **Decision:** the promotion syncs `index.tmp` at the commit's level before its renames (`IndexCommitUnit.run`, step 0), so the statement of item 1 ("`index.bin` only arrives by renaming a synced, complete `index.tmp`") holds for the promotion too, and `promotedDurably` means the promoted data and name are both ordered. A failed file sync renames nothing and leaves the promotion pending. **Tests:** `R-STO-5: a launch that promotes an index.tmp written but never synced before a kill keeps a valid generation through a full volume and a power loss` (probe VP7, both power-loss modes); `R-STO-4: keys doomed only in a loaded index.tmp wait…` gains the case `syncFile` (EIO on that sync: nothing renamed, promotion pending, the key keeps the `commit` blocker); and both full-volume enumerations now end the full-volume lifetime in a kill **or** a power loss in either mode (`fullVolumeEnds`): `R-STO-5: crash at every boundary, then a launch on a full volume that ends in a kill or a power loss…` (4 crash modes × 3 ends × 75 points) and `R-STO-5: a fault at every commit step, a kill, then a launch on a full volume that ends in a kill or a power loss…` (4 faults × 3 ends). Without the sync line the new test, the `syncFile` case and the crash enumeration fail (48 issues; kill points 17, 52, 64 and 69, the `synchronizeFile index.tmp` of each commit, under both power-loss ends). After a power loss, `fullVolumeLifetime` compares with what the same power loss would have left before the lifetime ran; it accepts a degraded result only where that baseline held no valid generation at all (a torn first `index.tmp` whose name `open()`'s root sync made durable while its data never was: nothing valid to lose), and only for power-loss ends, so the pre-existing kill-ended check is unchanged.
- **Close-out cycle 3 amendments.** Three more gaps of the same class (the commit unit dropping or hiding the newest valid generation): the first two from the review, the third found by the state-space enumeration of B-33:
  1. **Step 4 runs only when `index.prev` is absent or `index.bin` holds the committed generation** (probe VPC2-D) · blocking. Step 4 renamed `index.bin` over `index.prev` whenever `index.bin` existed. With a rotten `index.bin` (bit rot; the load rule chose `index.prev`, degraded), the launch commit moved the rotten file over the only valid generation; step 5 then failed (EIO), the rollback moved the rotten file back, the synced `index.tmp` was the only valid generation left, and close()'s flush on a full volume removed it in its ENOSPC fallback: lifetime 3 found no valid index, lost the record and served the `corrupt`-doomed name. **Decision:** `replaceCurrent(with:committed:…)` moves `index.bin` only when `index.prev` is absent or `currentHolds(committed)`; otherwise the source is renamed straight over the invalid, foreign or uncommitted `index.bin`, so `index.prev` keeps the committed generation. Both call sites (the promotion and step 5) pass the unit's `committed` (for the promotion that is `survivingGeneration`). `currentHolds` reads 64 bytes, now on every commit whose `index.prev` exists (an `itemInfo` and a 64-byte read; P-5 is the orchestrator's quiet-machine run to judge). Test: `R-STO-4: a rotten index.bin never replaces a valid index.prev, so EIO on step 5 and then a full volume keep a valid generation` (kill and power-loss-keeping-metadata ends); it failed on the previous unit with 10 issues ("the committed generation 4 is still on disk": `nil`; no valid generation after the full volume; record lost; corrupt name served), and passes now.
  2. **A pending promotion whose `index.tmp` vanished completes without a commit** (probe VPC2-K). Every commit attempt began by syncing `index.tmp`; when it was gone (an outside deletion inside the private root, or a rename that took effect but reported failure) the sync threw `notFound`, the promotion stayed pending and every later commit failed, close()'s durable flush included. **Decision:** `IndexCommitUnit.promote` checks `itemInfo(index.tmp)` first; `nil` sets `promotedName` (no longer pending) and leaves `promotedDurably` false, so the vanished generation never counts as committed; the commit then runs steps 1–6 and supersedes whatever reached `index.bin`. A `notFound` from the sync itself is not taken for a vanish (the file existed a moment before): the promotion stays pending and the next attempt's `itemInfo` decides. (Close-out cycle 4, both reviews: the code caught the sync's `notFound` as well, so the launch commit then truncated and rewrote the loaded `index.tmp` in place; only the stat decides now. Test `R-STO-4: a notFound from the promotion's sync of an index.tmp that exists keeps the promotion pending and the file unchanged`, which failed with 4 issues before: the promotion resolved, `index.tmp` rewritten, the launch commit reported as committed.) Test: `R-STO-4: a pending promotion whose index.tmp vanished stops blocking commits and never counts as committed` (failed with 3 issues: `notFound` instead of the injected EIO, the promotion still pending, `notFound` from the durable flush).
  3. **A step-4 rename that took effect but reported failure is undone** (found by B-33: a rename whose result was lost). `replaceCurrent` threw before step 5 with `index.bin` already moved, so a failed commit left `index.bin` missing (I-c; `index.prev` kept the committed generation, so nothing was lost, but the unit's own promise "index.bin is never missing after a failed commit" broke). **Decision:** when step 4 throws and `index.bin` is absent (a failed stat counts as present), `index.prev → index.bin` (exclusive) is done as after a failed step 5. The enumeration showed 765 violations on the previous unit (every initial disk, on the launch commit and the flush) and none now.
  The ordering of the unit is now: 0. promotion (vanished → done without commit; else sync `index.tmp`, steps 4–5 with their condition and rollbacks, root sync); 1. barriers; 2. write with the ENOSPC fallback; 3. sync; 4. `index.bin → index.prev` only when `index.prev` is absent or `index.bin` holds the committed generation (undone if it took effect but failed); 5. `index.tmp → index.bin` (step 4 undone on failure); 6. root sync. **For the orchestrator:** ARCHITECTURE §4.1 step 4 needs "only when `index.prev` is absent or `index.bin` holds the committed generation; otherwise step 5 renames straight over `index.bin`", step 0 the vanish rule, and steps 4–5 the undo of a failed or effect-losing rename; §3's `index.prev` row "replaced (step 4, under the condition of §4.1)".

## B-29 — The scheduled commit backs off after failures (fix round 3, review probe 6)
- **Context.** A commit that keeps failing (ENOSPC on a full device, EROFS, EIO) was retried every coalescing window: `nextDeadline()` reported the window for good, every `runDueWork()` re-encoded the whole index and logged an error (probe 6: 200 windows, 201 failed commits, 607 log records). Not an invariant break, but the engine's alarm never went quiet (R-SYN-14's spirit) and the log filled.
- **Decision.** `CommitBookkeeping.consecutiveFailures` counts failed attempts in a row. The **scheduled** commit (`nextDeadline()`, `runDueWork()`) opens at `lastAttemptAt + min(300 s, commitMinimumInterval × 2^failures)` (`scheduledCommitOpens()`; 0.5, 1, 2, 4 … s with the default 0.25 s window, at most 5 minutes as the unlink backoff); a success resets it. **Explicit** callers (`requireCommitted`, hence `flush`, `apply`, `admit`, `markSynced`, `adoptionReport`, `close`) wait only for the coalescing window (≤ 4/s, P-5) and try at once. Only the first failure of a streak logs an error; the success that ends a streak logs one info line with the count; `StoreMetrics.commitFailures` still counts every attempt.
- **Consequences.** On a full device the store keeps serving its in-memory state and retries every 5 minutes at worst, or as soon as the engine or the app asks for a commit. A zero window (test configurations) means no backoff. Test: `P-5: failed commits back off exponentially, explicit flushes still try at once, success resets, one error per streak`.

## B-30 — An admission gives the applied manifest a digest no fetched manifest has (fix round 3, review "applied-manifest metadata after admit")
- **Context.** `ValidatedManifest.digest` documents "equal digests mean nothing to reconcile", and the applied digest is persisted. `admit(_:)` changed the applied entries but kept the previous digest, so afterwards the digest described entries that were no longer applied; a planner (WP-F) that skips `apply` when the fetched digest equals `planningView().appliedManifest.digest` would never prune an admitted entry once the server served that payload again.
- **Options.** (a) The zero digest (`ValidatedManifest.empty()`'s): conflates "admitted" with "nothing applied yet". (b) A derived digest. (c) Document for WP-F that digest equality must not short-circuit after an admission (a rule nobody can test from WP-B).
- **Decision.** (b): `AssetStore.admittedDigest(after:revision:)` = SHA-256(`"ZTronAssetKit.admitted-manifest.v1"` ‖ 0x00 ‖ previous digest ‖ manifest revision, big-endian words). A fetched digest is the SHA-256 of the payload bytes, so equality would need a SHA-256 preimage; each admission yields a new value (the revision grows); a no-op admission changes nothing. The ETag is untouched (sync-2 S2-28: an admission never stores the point fetch's ETag; the stored one still validates the last applied full manifest, so a 304 means that manifest is unchanged, and the engine's run applies it anyway when its digest differs).
- **Consequences.** After an admission the next fetched manifest is always applied (and prunes admitted entries it does not list); the applied digest survives a relaunch with the entries. WP-F may keep a digest short-circuit. Test: `R-SYN-8: after a point admission the applied digest matches no fetched manifest, so the server's manifest is applied again and prunes it`.

## B-31 — A cancelled hash whose claim cannot be handed back discards it (fix round 3, review "publish cancellation hand-back")
- **Context.** A cancelled hash renames `.verifying` back to `.part` (exclusive) so the caller can retry with the same `StagedFile` (B-11 (3)). When a producer recreated `.part` meanwhile (an append opens it with `O_CREAT`), the rename failed inside `try?` and the claimed full-size file stayed in staging as `.verifying` until staging GC.
- **Decision.** The same metadata unit, on a failed hand-back, removes the claimed `.verifying` and its sidecar (as B-26 does for other failures; the sidecar describes the discarded bytes, not the producer's new `.part`), and leaves the new `.part` alone. The call still throws `.cancelled`.
- **Consequences.** A retry with the same `StagedFile` then claims the producer's new `.part` and is judged on those bytes (size, hash). Test: `R-INT-1: a cancelled hash whose claim cannot be handed back discards the claimed file and keeps the producer's new .part`.

## B-32 — Every return of `close()` means "flushed durably, lock released" (fix round 3, review probe 2) · blocking
- **Context.** A `close()` arriving while another was draining or flushing returned at once (`phase == .closing`), before the durable commit and the lock release, although `close()` documents both; a caller that then reopened the root (facade shutdown and re-create, two shutdown paths) got `.locked`.

- **Consequences.** Concurrent closes all return after the same durable commit and unlock. Test: `R-STO-9: a second close() during the first one's durable commit returns only after the commit and the lock release` (probe 2: close #1's durable commit held on a `SteppedBlockingExecutor`; close #2 parks; once it returns a new store on the same root opens).

## B-33 — An exhaustive state-space test of the index commit unit and the load rule (close-out cycle 3, item 2)
- **Context.** Round-3 probe 1, VP7 and VPC2-D were three bugs of one class (the commit unit or the launch losing or hiding the newest valid generation under rot, faults, full volumes and crashes), found one probe at a time.
- **Decision.** `IndexCommitStateSpaceTests` (`Tests/ZTronAssetStorageTests/Core/IndexCommitStateSpaceTests.swift`) enumerates, never samples:
  - **Initial disks:** every combination of {absent, valid older (9), valid committed (10), valid newer-uncommitted (11), rotten: bad header, bad body, truncated} for `index.bin`, `index.prev` and `index.tmp`, plus, for `index.tmp` only, the newer generation written but never synced (VP7's kill between steps 2 and 3): 7 × 7 × 8 = 392 disks, every item synced except that `index.tmp`. Pruned, each justified in the code: the unsynced state for `index.bin` and `index.prev` (they only ever receive a synced `index.tmp` by rename); a rotten header naming the committed or another file's generation (every attempt has a generation of its own, files are only renamed; a rotten header *below* the valid ones behaves like one above them except for `nextGeneration`, so the higher one, which also tests I-5, covers both); names not yet ordered by a root sync, which a companion suite starts from (close-out cycle 4 amendment 2 below). Two valid files of one generation are equally unreachable but kept.
  - **Volume scripts:** free; full at close (the launch commit has space, every `index.tmp` write after it fails with ENOSPC: VPC2-D's sequence); full from the launch (probes 1 and VP7).
  - **Events:** none; one injected fault at **every** file-system operation of the lifetime, the load's stats and reads included: EIO at every operation, ENOSPC at every mutation (no query returns it), and at every rename a rename that **took effect but reported EIO**; a crash before every mutation in each of the four crash modes (torn writes at writes only: elsewhere a torn write is a kill).
  - **Lifetime:** what `open()` and `close()` do to the index: `IndexLoader.load`, `LaunchState.build`, `open()`'s root barrier, the ordered launch commit and the durable flush, folded through `IndexCommitLedger` (new, shared with `AssetStore.commitNow`, so the test cannot drift from the actor's bookkeeping). Every case's survivor (the end of the run as a kill, or its crash) is reopened by a fault-free launch, and the disk the reopen leaves is loaded again, as a kill and as a power loss would leave it.
  - **Invariants:** I-a the newest durable generation (the newest valid one the same crash would have left before the case; every generation the store counted committed: loaded, durably promoted or committed) is never lost unless a newer valid one replaces it, under every crash view at the end of every run, in every crash survivor and after the reopen; an attempt whose commit failed is not durable in this sense even if its synced `index.tmp` would survive a power loss (the next attempt rewrites `index.tmp` in place, ADR-015; the store never counted it). I-b the generation the store counts committed is a valid file after every commit attempt and, at the end of every run and reopen, under each view (a crash inside a unit is held to I-a against what was committed before the unit, since a promotion inside it may legitimately replace it). I-c a failed commit leaves `index.bin` present and valid whenever it was valid before. I-d the launch after the reopen reaches the reopen's generation or a newer one with a larger epoch; the reopen's epoch exceeds every generation the case counted committed (I-5; a launch whose own launch commit failed may see its epoch again, B-5). I-e (liveness) on a free volume, close()'s flush succeeds after a fault in an earlier phase (VPC2-K's class).
  - **Size:** 98,263 cases (1,176 fault-free runs, 47,341 faults, 49,746 crash cases), each violation printed with its full description (initial disk, volume, event, view).
- **Affordability without sampling.** Every case runs; only identical work is shared: the fault-free run records the disk before every mutation (a crash before mutation k leaves exactly that disk under the crash's view), so only torn writes are run again, from the start of their commit; a run with a fault resumes from the fault-free run at the start of the commit the fault falls in; the checks after a commit and at the end of a run are computed once per `RunKey` (the effects of the run's mutations from the initial disk and its bookkeeping: the fake is deterministic, so equal keys mean the same volume and memory); a reopen depends, after `open()`'s root barrier, only on the survivor's index files as a kill and as a power loss keeping metadata leave them, and is computed once per pair. Cost (this Mac, load 4–6): about 55 s of CPU in debug. **Scheduling:** every case of every suite starts its one-minute time limit when the run starts, so 392 parallel cases made every storage test, this one's included, last as long as the whole run (48 s under TSan: 1.2× headroom). ## B-34 — A launch that cannot read an index file serves read-only and writes no index file (close-out cycle 3, found by B-33)
- **Context.** `IndexLoader` turned a failed stat into "absent" and a failed read into "torn". The launch then committed over a generation it had never read: with only `index.tmp` valid, an EIO on its stat or read made the launch a fresh, empty store that rewrote `index.tmp` (generation 1 over 11); with a valid `index.bin`, the launch loaded the older `index.prev` and step 5 replaced the unread `index.bin`; on a full volume the fallback removed `index.prev` because `index.bin` held "the committed" generation. The enumeration flagged every initial disk.
- **Options.** (a) Treat an unreadable file as rotten (status quo): loses it. (b) Fail `open()`: a persistent EIO would keep the store from opening at all. (c) Retry the read: helps transient errors only, and a persistent error still needs (b) or (d). (d) Open on what was read, but write no index file in that lifetime.
- **Decision.** (d). `IndexLoadOutcome.unreadable` names every index file whose stat or read threw (a short read is still "torn"); `LaunchState.unavailable` is then `.ioFailure` and the launch `degraded`; `open()` installs `unavailable`, logs once, and skips the launch commit; `unavailable` already stops scheduled commits, the reaper, and `close()`'s flush, and makes every writing API throw `.storageUnavailable(.ioFailure)` (`checkWritable`). Lookups are served from the loaded state. A later launch reads again.
- **Consequences.** A transient EIO while loading costs one read-only lifetime (writes throw; the engine surfaces `storageUnavailable(.ioFailure)`), never a generation. `open()`'s other writes are unchanged: the root barrier (a sync), and the deletion of foreign names under `blobs/` (never adopted, never an index file). `OpenReport.degraded` is true for that lifetime. Test: `R-STO-4: a launch that cannot read an index file serves read-only and never writes over it` (a failed stat and a failed read of `index.bin`): failed with 10 issues before the fix (the launch wrote `index.tmp`, renamed over the unread file, and the next launch opened degraded), passes now; the enumeration covers EIO at each of the load's stats and reads for every disk; `R-STO-4: an index file whose read ends early is torn, not unreadable, and the launch still commits` pins the other side (no error, fewer bytes: torn, as before). **For the orchestrator:** ARCHITECTURE §4.2 ("never trap") needs "a stat or read that fails with an error makes the launch read-only (§4.5): it commits nothing in that lifetime", and §4.5 "→ commit if anything changed" "unless an index file was unreadable".
- **Close-out cycle 4 amendment (reviews "I-5 / ADR-013" and "availability under persistent media errors").** A read-only launch may take the previous launch's epoch (B-5's amendment). A persistent media error on any index file keeps every launch read-only until the file is repaired or removed; that includes an unreadable `index.prev` beside a valid `index.bin`, which the protocol never leaves newer than `index.bin` (review probe: three launches with persistent EIO on the stat of `index.prev`, each read-only). The extra cost over the status quo is limited to a read error on `index.prev` whose stat succeeds: a persistent stat error there fails every commit at step 4's stat anyway. Allowing commits in that one case (the review's optional relaxation) is not done here: it would let step 4 replace a file the launch never read; for the orchestrator to decide.

## B-35 — An `open()` parked on a running open returns that open's report (close-out cycle 4, review "flaky test openAndCloseInterleavings") · blocking
- **Context.** A second `open()` parked on a running open re-read the phase after it resumed (`awaitOpen`). A `close()` parked on the same open was resumed by the same call, and the scheduler, not the order of parking, decided which reached the store first; when the close did, it set `closing` and the second open threw `.closed`. Cycle 3's fix ordered the parking only. Both reviews reproduced the failure (`StoreEdgeTests.swift:147:6: Caught error: .closed`, at repetitions 22, 50, 257, 384, 587 and 893), and so did this cycle before the change: repetition 397 of 3,000 at load 5.
- **Options.** (a) Hand each parked `open()` the outcome of the open it waited for. (b) Split the test so no scenario depends on the order of waking.
- **Decision.** Both. `StoreCoreState.openReportWaiters` holds the further `open()` calls; `resumeOpenWaiters` resumes them with `openReport`, which only a successful open sets and which is `nil` while an open runs, so each gets the report of the open it waited for, or `nil` (→ `.notOpen`) when that open failed. They no longer re-read the phase, so a close that began meanwhile cannot change what they return (the call overlapped the open, so returning its report is as valid as returning just before the close). Other async APIs and `close()` still park on `openWaiters` and re-read the phase. The test is now five scenarios on their own harnesses: `R-STO-9: open runs once for concurrent callers: a call made while an open runs returns that open's report` (one lock acquisition), `R-STO-9: close() during a running open waits for it, then flushes and releases the lock` (a new store on the same fake opens), `R-STO-9: an open() parked beside a close() on a running open returns that open's report, whichever resumes first` (started together, no parking order), `R-STO-9: an open() parked on an open that fails throws notOpen, and a later call opens`, and `R-STO-9: close() drains an in-flight publication, which unwinds with closed, and the next launch adopts its blob` (unchanged).
- **Consequences.** `open()`'s documented "a second call returns the first report" now holds for every call made while the open ran. A parked call after a failed open throws `.notOpen` (before: `.notOpen`, or `.closed`, or the report of a later open, depending on scheduling). Evidence: the four open/close scenarios, `swift test --filter … --repeat-until fail --maximum-repetitions 3000`, twice, at load 25–27 (a TSan build and six CPU-bound processes beside them): 3,000 repetitions each, both runs passed.

## B-36 — A launch counts nothing committed until a root sync ordered the names it read (close-out cycle 4, found by enumerating unordered names) · blocking
- **Context.** A killed process may rename an index file (a promotion, step 4 or 5) and die before its root sync: the next launch loads the newest name, which a power loss can still undo. `open()`'s root barrier orders it; when that barrier failed (it is tolerated), the store still counted the loaded generation committed. With the launch commit failing too (a full volume), the reaper then unlinked a blob that generation had dropped while the generation a power loss brings back still lists its entry (test: its bytes were gone, so they would be downloaded again), and the ENOSPC fallback and step 4 treated `index.bin` as the committed file. SPEC's I-1…I-5 held (I-2 through `needsHeal`; the epoch case is B-5's), but §4.4's "the generation that dropped k is committed" did not.
- **Options.** (a) Count nothing committed until a root sync orders the names (the barrier, or a commit's step 6). (b) A separate "durable" generation for the reaper beside the reported one. (c) Fail `open()` when the barrier fails.
- **Decision.** (a). `installLoadedState` sets `committedGeneration` to 0; after the barrier `open()` raises it to `LaunchState.committedGeneration(rootOrdered:)`: the loaded (or surviving) generation when the barrier succeeded, 0 when it failed (never lowering a commit made before the barrier). The next successful commit raises it as before. The state-space harness uses the same function, so it cannot drift.
- **Consequences.** After a failed barrier, until a commit succeeds: no deletion waits only on the loaded generation (keys wait with the `commit` blocker), the ENOSPC fallback keeps `index.prev`, step 4 renames over `index.bin` instead of moving it, and `OpenReport.generation` and the snapshot's `indexGeneration` read 0 (an `apply` returns only after its own commit succeeded). **For the orchestrator:** `OpenReport.generation`'s doc ("the committed generation after launch reconciliation", `StoreTypes.swift`, a contract file) could add "0 when the launch could not order the names it read and its launch commit failed". Tests: `R-CLN-5: a launch whose root barrier fails unlinks nothing a power loss could still need, until a commit succeeds` (failed with 3 issues before: the blob was reaped, the blocker was not `commit`, and lifetime 3 had lost the bytes), and `IndexCommitUnorderedNamesTests` (B-33 amendment 2).
