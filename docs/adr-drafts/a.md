Stage 2, level L1, branch `wp/a`. One entry per non-trivial decision, in the `DECISIONS.md` shape (context · options · decision · consequences); the orchestrator numbers them at merge. ## A-1 — A two-pass streaming manifest decoder instead of `JSONSerialization`/`JSONDecoder`
- **Context.** R-MAN-1/2/3 and P-3: decode untrusted bytes in both wire shapes, quarantine per entry, reject structurally, never trap, ≤ 1 s and ≤ 4× the payload at 32 MiB, ≤ 80 ms for the 3.3 MB reference. Foundation's decoders materialise every key and value (an `NSString`/`String` per token, a dictionary per object) before the schema is applied, impose their own nesting limits, and on the iOS 15 runtime are the Objective-C `JSONSerialization`; a 32 MiB payload of short strings or one huge unknown member costs several times the payload before validation starts.
- **Options.** (a) `JSONDecoder` with a lenient `Decodable`; (b) `JSONSerialization` plus a schema walk; (c) a hand-written reader that validates RFC 8259 JSON in UTF-8 and materialises only what the schema needs.
- **Decision.** (c): `JSONCursor` (bytes, strings with escapes and UTF-8 validation, numbers, literals, iterative `skipValue` with the depth checked before a container is entered), `ManifestParser` (schema), `ManifestRules` (per-entry rules shared with `violations(of:limits:)`), `ManifestFootprint` (A-8), `SurveyedIdentifiers` (A-2). Two passes over the same parser: a *survey* that validates, finds repeated identifiers and counts without materialising, then a *build* with exactly reserved buffers that materialises an entry only once it is known to be accepted, reading its members again from the payload (fix round 3: a quarantined entry costs nothing but the diagnostic the bound has room for, and string arrays are built at their exact count without a scratch buffer). Printable ASCII is scanned eight bytes at a time (SWAR, `loadUnaligned`), keys are matched by length and first byte, the identifier index is built once and handed to `ValidatedManifest` through an internal `init(decoded:positions:…)` (no public or package signature changed).
- **Consequences.** Release: the 3.28 MB / 10,000-entry reference decodes in p50 18.4 ms, max 18.8 ms over 15 runs (budget 80 ms); a dense 32 MiB / 100,000-entry manifest in 193 ms at worst (P-3-scaled limit 818 ms); random, truncated, deeply nested and unterminated payloads are rejected by the survey before any allocation (peak growth ≈ 10 KB at 32 MiB). Debug: the dense 32 MiB manifest takes about 2.9 s of CPU (two passes; unoptimised code is 11–15× slower), TSan more. No recursion anywhere, so no input can exhaust the stack whatever `maxNestingDepth` is set to. Keys and enumeration values are compared with their escapes decoded on the fly, without allocating (fix round 2): with the former decode-then-compare, 32 MiB of the shortest escaped 8-byte unknown keys (`"\/bcdefgh":0`, whose decoded length matches two field names) took 889 ms of CPU with `assets` before `schemaVersion` (740 ms inside one entry), over the 818 ms P-3-scaled threshold; they now take 328–330 ms (190 ms). Every literal compared is ASCII, so a `\u` escape beyond U+007F ends the comparison at once.

## A-2 — Read-only byte views in production code
- **Context.** C1 forbids mutable pointers and caps unsafe escapes at 3 (0 used). Scanning `Data` through its subscript or copying it to `[UInt8]` costs time or a full payload copy (1× of the 4× budget).
- **Decision.** The decoder reads the payload through `Data.withUnsafeBytes` as an `UnsafeRawBufferPointer` that never escapes the call; the rules read a string's UTF-8 through `utf8.withContiguousStorageIfAvailable` (or a copy for bridged strings), and `AssetID.hash(into:)` feeds the same bytes to `Hasher.combine(bytes:)`. The survey pass keeps the identifiers it has seen (under `.reject` every valid one, under `.keepFirst` the accepted ones) in `SurveyedIdentifiers` (fix round 3, replacing round 2's `Set<SurveyedIdentifier>` of 24-byte views): an open-addressing table of 32-bit payload offsets, at most half full, whose identifiers are hashed (a per-process seeded `Hasher` over the decoded bytes, in eight-byte words) and compared by their decoded bytes read again from the payload, escapes decoded on the fly (`JSONDecodedBytes`), so nothing is copied or materialised. It lives only inside the survey, within the same `withUnsafeBytes` call. The 32-bit offsets cap what the decoder reads at 4 GiB − 2 bytes whatever `maxPayloadBytes` says (documented on the limit; a larger payload is `payloadTooLarge` with that cap as `limit`). All are read-only views; no mutable pointer, no `unsafeBitCast`, nothing the unsafe gate matches (`UNSAFE escapes found=0`). Every read is preceded by an explicit bounds check, so malformed input throws instead of trapping.
- **Consequences.** The unsafe budget stays at 0 of 3. A reviewer who reads C1 as "no pointers at all" would ask for a `[UInt8]` copy; that costs 1× of the budget and about 30 % of the decode time.

## A-3 — Values are checked on the payload's bytes before they are materialised
- **Decision.** Every text rule (identifier, `fileExtension`, `remotePath`, tag length, checksum) runs on the payload's bytes (or the decoded bytes of an escaped string). A value over its field's length limit is never turned into a `String`: a 32 MiB identifier is quarantined as `identifierTooLong(bytes:)` with `QuarantinedEntry.identifier == nil` ("when one could be read" is read as "when it was within its limit"). Unknown members are validated and skipped without allocation. The quarantine records the first violation in field order (identifier, fileExtension, remotePath, localPathComponents, localFileName, byteSize, checksum, tags, policy); `violations(of:limits:)` returns all of them in the same order, from the same functions.

## A-4 — Hardening choices R-MAN-2 leaves open
- **Decision.**
  1. *Path components* are capped at 32 per entry (the index's per-record limit, store design §2.3), quarantined as `malformedField("localPathComponents")`. The cap is internal (`ManifestRules.maxPathComponents`): `ManifestLimits` is a contract type.
  2. *Repeated members.* A repeated known member inside an entry quarantines it as `malformedField(<name>)`; a repeated `schemaVersion` or `assets` makes the envelope `unexpectedShape`. Parsers disagree on which duplicate wins, so the decoder never guesses.
  3. *Duplicate identifiers* are checked among identifiers that pass the identifier rules. `.reject` (remote manifests) reports `duplicateIdentifier` at the second occurrence, quarantined occurrences included: a repeated identifier makes the manifest ambiguous. Since fix round 3 the survey finds it, so it is reported before any later error inside the assets (`[a, a, b, …past maxEntries]` is `duplicateIdentifier`, `[a, b, c, a]` with two entries allowed is `tooManyEntries`) and before `decodedSizeExceeded`; an error of the document itself (not JSON, too deep, an envelope's version or shape) still comes first (A-4.9; verifier round 3 found 1,017 of 40,000 random manifests reporting `tooManyEntries` instead). `.keepFirst` (the legacy `manifest.json`) keeps the first occurrence that can be kept: only an *accepted* identifier makes a later occurrence a duplicate, quarantined as `malformedField("identifier")` (`ManifestEntryViolation` has no duplicate case, A-11.2). So `[{a, "p.ng"}, {a, "png"}]` keeps the second entry and legacy migration adopts its file instead of downloading it again (fix round 1; it was "any valid occurrence", which kept nothing in that case and contradicted the option's doc).
  4. *Unknown `policy` values* quarantine the entry (`malformedField("policy")`): the value set is closed within `schemaVersion` 1, and a publisher that adds one bumps the version.
  5. *Encoding and leniency.* UTF-8 only (RFC 8259 §8.1), a leading BOM tolerated; invalid UTF-8, raw control characters in strings, lone or mismatched surrogate escapes are `undecodable(.notJSON)`. **Trailing commas** (fix round 3, R-MAN-1): one comma before `]` or `}` after a member or element is accepted, exactly where the prior art's `JSONDecoder` (and `JSONSerialization`) accepts one on this host: `[{…},]`, `[{…,}]`, nested ones, whitespace around it; `[,]`, `{,}`, `[1,,]` and a leading comma stay `notJSON` (`R-MAN-1: a trailing comma decodes exactly where the prior art's JSONDecoder accepted one` compares each case with `JSONDecoder` at run time). It costs one whitespace skip and one byte comparison after a comma. **Recorded R-MAN-1 deviation — UTF-16 and UTF-32:** the prior art's decoders also detect UTF-16/32 (with a BOM, and from the null-byte pattern without one); this decoder rejects them as `notJSON`. Accepting them means transcoding the whole payload first, a copy of up to 1.5× the payload out of R-MAN-3's 4× and a second decode path, for an encoding no publisher tool emits (every shipped fixture is UTF-8; JSON exchanged between systems must be UTF-8, RFC 8259 §8.1). Orchestrator: confirm no published manifest is UTF-16.
  6. *Numbers.* `byteSize` accepts any JSON number whose exact decimal value is an integer, as the prior art's `JSONDecoder` did when it read `byteSize` into `Int` (R-MAN-1, fix round 1): `1234.0`, `1.234e3`, `1E3`, `12340e-1`; a non-zero fraction (`1.5`, `1e-1`) is `malformedField("byteSize")`. The value is computed from the digits (`JSONCursor.integralValue(of:)`, no floating point, linear in the number's length whatever the exponent) and saturates (`1e400` is `byteSizeOutOfRange(Int64.max)`). `schemaVersion` still needs integer syntax (`1.0` makes the envelope `unexpectedShape`): the envelope is new, so no published manifest spells it otherwise.
  7. *remotePath.* A colon in the first segment is a scheme (RFC 3986 §4.2); `//` after the optional scheme is an authority. The `..` check reads the path as an origin or the transport might (fix round 1): the path ends at the first `?` or `#` (so `a/..?x` and `..#frag` are parent segments); segments are separated by `/`, `\`, `%2F` and `%5C` (either case), so `a/..%2Fb`, `%2e%2e%2fsecret` and `a\..\b` are parent segments; a dot may be spelled `%2e`. `..foo`, `...`, `.` and `%41` stay allowed. Since fix round 3 (orchestrator decision 3) a `?` or `#` anywhere is `RemotePathViolation.queryOrFragment`, reported last (`a/..?x` is `[parentSegment, queryOrFragment]`), so such an entry is quarantined with a diagnostic instead of failing every fetch in the transport (TR1-10); `%3F` stays allowed (it is a literal `?` in a path segment). No shipped fixture has either character.
  8. *Control characters* are Unicode Cc: C0, DEL and C1 (U+0080–U+009F), for identifiers and remote paths; format characters (U+200B, U+202E) are allowed.
  9. *Envelope.* `schemaVersion` (integer ≥ 1) and `assets` (array) are both required; members may come in any order, and since fix round 3 the verdict never depends on it (fix round 2 had left an exception, refuted by verifier round 3: with a supported version first, a `tooManyEntries` in `assets` was thrown before a later member that was not JSON or nested too deep). It is reached in a fixed order: the whole document must be JSON within the nesting limit (`notJSON`, `nestingTooDeep`); then exactly one `schemaVersion` must declare an integer (a missing, repeated or non-integer version is `unexpectedShape`) that this build interprets (else `unsupportedSchemaVersion`, whatever `assets` looks like and whether it exists: a later schema may restructure or drop it, and WP-F/WP-G must be able to tell "the app needs an update" from "the manifest is broken"); only then does the v1 shape apply (`assets` present, an array, not repeated). `assets` is parsed in place only when a supported version precedes it; otherwise it is skipped (validated only) and parsed once the document has been read, so an unsupported version is never interpreted. An error inside `assets` (too many entries, a repeated identifier) is *recorded* where it occurs and the rest of the document is still validated; it is reported only after the document, version and shape checks, so every member order gives the same error (`R-MAN-2: an envelope's verdict never depends on member order …`, five later members in four orders each). Before the round, `{"schemaVersion":2,"assets":{"a":{}}}`, its reverse and `{"schemaVersion":2,"packs":[]}` were `unexpectedShape`, and an invalid tail was `unsupportedSchemaVersion` or `notJSON` depending on member order (`R-MAN-2: an envelope declaring an unsupported schemaVersion is rejected as unsupported whatever its assets member looks like`).
  10. *Entry limit.* Every element of the assets array counts, quarantined ones included; the first element past the limit records `tooManyEntries(count: limit + 1, limit:)`, and the elements after it are only validated as JSON (fix round 3, A-4.9).
  11. *Required members* are the prior art's four: `identifier`, `fileExtension`, `remotePath`, `localPathComponents`; optional members given as `null` are absent; a non-object element is `malformedField("entry")`, counted by the survey like any quarantine (A-8).
  12. *Path-like text is not validated here.* `localPathComponents` elements and `localFileName` have no content rule beyond being strings (32 components at most): `..`, `/`, `\`, NUL, control characters and empty strings are accepted, as the prior art accepted them. The new store never uses them (R-SEC-2: manifest text never becomes a store path component); only legacy migration (WP-C) derives source paths from them (`<legacy root>/<components>/<resolvedFileName>.<ext>`). **WP-C must validate them before building a legacy path**: reject an empty, `.` or `..` component, one containing `/`, `\` or a Cc character, or over 255 bytes, and check that the standardised result stays under the legacy root. A Model rule would quarantine entries the prior art served (R-MAN-1) without protecting anything the store reads (fix round 1, declined as a Model rule).

## A-5 — How R-MAN-3's bounds are measured, and in which configuration
- **Context.** R-MAN-3's 1 s is a property of the shipped (optimised) decoder. The unit tests run unoptimised (`--quick`) and, in `--full`, under TSan, where the same dense 32 MiB decode takes about 2.9 s and over 20 s respectively. This allocator keeps no high-water mark (`max_size_in_use` reads 0) and no public allocation hook exists.
- **Decision.** Time is the decoding thread's CPU time (`CLOCK_THREAD_CPUTIME_ID`, immune to other tests and processes). The heap is `malloc_zone_statistics` in-use bytes: exact before and after the call (the result alive), and a peak sampled by a second thread that polls at a 10 % duty cycle, spinning on its own CPU time (no sleep): back-to-back polls hold the zones' locks and starved the decoder (a first version took 8 minutes). The §11 test, renamed in fix round 3 to what it asserts in every harness run, `R-MAN-3: seeded fuzz of random, truncated, mutated and deeply nested manifests never traps, and outside Thread Sanitizer stays within 4x the payload in linear time` (it was "… stays within 1 s and 4x the payload"; orchestrator: update ARCHITECTURE §11's R-MAN-3 row), checks every outcome in every configuration; asserts ≤ 4× (peak and retained) for each of its 38 limit-scale cases except under TSan (whose allocator replaces malloc; detected by its runtime image), each accepted one measured after the allocator was made to serve its entry array and identifier index from freed blocks nearly twice their size (A-8); asserts ≤ 1 s only when the target is built optimised, and in an unoptimised build asserts that time is linear (32 MiB ≤ 64× the CPU of 1 MiB; a quadratic path would be about 1,000×). Small payloads are measured exactly by `R-MAN-3: a small payload's decoded form stays within 4x the payload, with no floor` (A-8). The harness's release run proves the time bound through `P-3: the reference decode rate holds … at the 32 MiB payload limit …` (BenchModel.swift), whose threshold is P-3's budget scaled to 32 MiB (818 ms, stricter than 1 s), so no literal threshold enters the benchmark target. **That benchmark is R-MAN-3's time proof**: the harness's unit runs (debug, TSan) never assert the 1 s bound (orchestrator: record it so in `TRACEABILITY.md`/`VERIFICATION.md`). Since fix round 1 it also runs the allocation worst-case classes, which `verify.sh --perf` runs optimised: minimal entries of 16-byte strings (also under `.keepFirst`), 25-byte path components (24-byte ones until fix round 2, A-8), 61 one-byte tags per entry, huge identifier, tag and checksum, and 100,000 entries sharing one identifier under `.keepFirst`; since fix round 2 also the two size-class shapes of A-8 and three escaped-key shapes (A-1). Since fix round 2 it measures the decoding thread's CPU time, like the unit test, instead of wall time: on a host busy with other agents' builds a 200 ms decode had read 685 ms of wall time, 16 % below the threshold; the decoder is single-threaded and does no I/O, so on a quiet device CPU time is its wall time. Under TSan the limit-scale cases shrink to 1 MiB. **Not verified:** allocation on an iOS device; the model assumes Apple's allocators as measured on macOS 27 (A-8), and no device was available (orchestrator: list it under "Not verified" in `VERIFICATION.md`).
- **Consequences.** Measured in fix round 3 (debug, R-MAN-3 test, retained = peak unless noted; A-15 has the full list): every accepted limit case at most 3.74× (minimal entries of 16-byte strings padded to the estimate's limit, with the reuse forced); dense 32 MiB 1.31×; 32 MiB `localFileName` 1.0×; escaped 32 MiB `localFileName` 0.39×; every rejected class at most 0.06× (the survey's own state). Release: the P-3 limit benchmark's worst case is 325 ms of CPU against 818 ms (A-15). The base seed is printed (`ZTRON_MANIFEST_FUZZ_SEED` replays a run; `ZTRON_MANIFEST_RULES_SEED` the rules-agreement test).

## A-6 — `AssetID` equality and hashing, same semantics, fewer calls
- **Decision.** Equality stays byte-wise: lengths first, then `String ==` as a fast reject (bytes equal ⇒ canonically equal, so "not canonically equal" proves "bytes differ"), then the byte comparison. Hashing feeds the UTF-8 count and the bytes in one `combine(bytes:)` from contiguous storage, or from a copy for bridged (UTF-16) strings, so both representations of the same bytes hash alike (tested). Indexing 95,000 identifiers dropped from 0.44 s to 0.06 s in debug.

## A-7 — The R-OBS-1 interval seam · **NEEDS-HUMAN-REVIEW** (public API addition, authorised by ARCHITECTURE §13.5 item 2)
- **Decision.** `LogIntervalName` (`plan`, `transfer`, `verify`, `commit`, `gc`, `eviction`); `LogRoute.interval(_:category:_:) -> LogInterval` begins a signpost on the sink's signposter (`OSSignposter.beginInterval` with a fresh `OSSignpostID`, one static name per case) and reports a `.began` `LogIntervalEvent` to the tap; `LogInterval.end()` ends both (end it exactly once, typically with `defer`; it may span awaits; `isSignposted` is `false` under `TapOnlyLogSink`). `LogTap` gains `recordInterval(_:)` with a default that records the event's rendered `.debug` line, `interval <name> <began|ended>[: <message>]`, which `LogIntervalEvent(line:)` parses back; existing taps (`RecordingLogTap`) therefore see intervals without a change. The tap is told even though the unified log receives a signpost rather than a line (ADR-047's "the tap sees what the unified log receives" holds in substance). Tests use `OSSignposter.disabled`, so nothing reaches the unified log.
- **One end per interval** (fix round 2). `LogInterval` is a copyable struct and `end()` has no once-guard: a guard shared by copies needs a lock or an atomic, and the iOS 15 floor (no `Mutex`, `Atomic` or `OSAllocatedUnfairLock`) and C1 (no `@unchecked Sendable` class) rule both out. A second end of one interval makes the os overlay's `endInterval` assert in a debug app build under `OSLogSink` (`checkStateAndGetFormatStringPointer` in the SDK's `os.swiftinterface`) and log a double-end error otherwise, while tests, whose signposters are disabled, cannot see it. `~Copyable` with `consuming func end()` was tried and declined: it compiles under `defer`, but a dictionary cannot hold it (`[Int: Span]` fails with "does not conform to protocol 'Copyable'", checked with the iOS 15 SDK), and a transport keeps one interval per transfer in flight. So the rule is documented on `LogInterval` and `LogRoute.interval`, and proposed for §10 like a REENTRANCY row: **each interval has one owner that ends it in one place** — a `let` ended only by the `defer` that follows it, or, for an interval that outlives its scope (a transfer until its terminal update), the single code path that removes it from the owner's state; owners' tests assert through the tap that every began edge has exactly one ended edge (`R-OBS-1: every end of an interval reaches the tap, so an owner's test sees a double end as a second ended edge`). A-11.6 proposes making that check exact.
- **Owners** (enforced by `R-OBS-1: every signpost interval has a call site once the work package that owns it has no stub left`): plan → WP-F (`ZTronAssetSync`), transfer → WP-D (`ZTronAssetTransport`), verify and commit → WP-B, gc and eviction → WP-C (`ZTronAssetStorage`). The test accepts a missing call site only while the owner's target still contains `fatalError("WP-<owner>` stubs in code (since fix round 2 a comment quoting one does not count), and prints the intervals still pending; today all six are. A call site is a `.interval(.<name>` in code. The orchestrator should confirm the transfer owner (WP-E's Apple transfers may wrap themselves too; any call site satisfies the rule).

## A-8 — An allocation bound checked before anything is built (rewritten in fix round 3)
- **Context.** R-MAN-3: "never allocates more than 4× the payload", for any input. A one-pass decoder reached 4.31× (growth copies of the entry array and the identifier index). Rounds 1 and 2 added a survey and an estimate capped at 3× the payload with a 64 KiB floor, and claimed that a freed large block is reused only down to about two thirds of its size (1.49×), which the 25 % headroom covered. **Verifier round 3 refuted both**: (a) measured with this WP's own `DecodeMeasurement`, 100,000 entries of an inline identifier, one 16-byte path component and one 16-byte tag, padded to the estimate's limit, read 4.18× (4.06× with three components): the 14,400,032-byte entry array was served from a cached free block of 25,165,824 bytes (1.75×); the test corpus never held these shapes, so "minimal 16-byte entries at 3.47× are the highest case" was wrong too; (b) below 16 KiB the floor allowed up to 20.7× (100 × `{}`, 301 bytes, kept 6,240 bytes of diagnostics).
- **What the allocator does** (measured in this round with throwaway C probes, not committed: in a freshly forked child, allocate and free a block of B bytes, allocate R bytes, and compare the address and the in-use growth; a binary search found the smallest R that reused the block): a freed block of B bytes above 2 MiB is cached and serves *every* later request of more than B / 2 bytes, counting B whole: for B = 4, 8, 16, 24 and 32 MiB the smallest request that reused it was exactly B / 2 + 1 (growth 2.000× of it); dozens of such blocks stay cached at once, and the smallest that fits is taken. A request of at most 2 MiB measured exactly its `malloc_good_size` whatever was freed before (blocks from 16 KiB to 2 MiB, 200 request sizes each). So a decoder's in-use growth can be up to twice its large requests, depending only on what the process freed earlier (a download that grows a buffer leaves such blocks).
- **Decision.**
  1. *The model counts that worst case* (`ManifestFootprint.allocated(_:)`): a request above 2 MiB is counted at twice its size rounded to 32 KiB; at most 2 MiB, the block it is served from, rounded to the coarser of Apple's two allocator designs as in round 2 (segregated size classes: 16-byte steps to 128 bytes, then four classes per power of two, so 544 → 640; magazine: 16-byte quanta to 1,008 bytes, 512-byte quanta to 15 KiB; 32 KiB steps above 15 KiB). A dictionary's occupancy bitmap is counted in whole words (it was counted in bits, so four buckets of `AssetID` and `Int` were estimated at 160 bytes for a 192-byte block).
  2. *The cap is 3.75× the payload, for every size; there is no floor.* The estimate is an upper bound of the in-use growth, and it is tight: with the reuse forced, the densest accepted limit case measures 3.74× for an estimate of 3.75×. The 6.25 % below 4× is for what a process-wide measurement adds to the decode (another thread's allocations), so a measurement of the decode stays below 4×. Over the cap, the manifest is `decodedSizeExceeded(bytes: estimate, limit: cap)` (orchestrator decision 1), before anything is built.
  3. *Small payloads need no floor*, because nothing outside the bound allocates: up to `ValidatedManifest.linearLookupLimit` (8) entries there is no identifier index (lookups scan at most eight entries; one minimal entry, 82 bytes, takes 192 bytes, 2.34×); `JSONCursor`'s container stack is a 64-bit word within the default nesting limit (an overflow array, counted in the estimate, only when `maxNestingDepth` is raised above 64); the rules report a first violation without building an array; identifiers are hashed and compared without copies; the build materialises an entry only once it is accepted, and string arrays at their exact count; the quarantine keeps only the diagnostics that fit (item 5).
  4. *What the survey counts*: the strings and string arrays of accepted entries, the entry array, the index (past eight entries), the largest transient (the decoded copy of an escaped string, validated or materialised; under `.keepFirst`, the identifier string of an entry looked up and then quarantined), and the stack overflow. Every element of the assets array is counted (round 1), and under `.keepFirst` the repeats of an accepted identifier exactly (round 1). Quarantined entries cost only their diagnostics.
  5. *Bounded quarantine reporting* (orchestrator decision 2): `ValidatedManifest.quarantinedCount` counts every quarantined element; `quarantined` keeps the first `ManifestLimits.maxQuarantineDiagnostics` (default 256: about 14 KiB, enough to see what is wrong with a manifest and small next to any manifest that has that many invalid entries) and fewer only when their array and identifier strings would not fit in the room the estimate leaves below the cap (`ManifestFootprint.diagnosticCapacity`; the kept ones are a prefix in payload order). So R-MAN-2's per-entry quarantine now holds at any density, and diagnostics can never reject a manifest: 20,000 × `{}` (60,001 bytes), which round 1 rejected whole, is 20,000 quarantines with 256 diagnostics; `[{}]` (4 bytes) keeps none, 100 × `{}` (301 bytes) 20, 1,000 × `{}` 212.
  6. *The survey's own peak* is bounded separately (it runs before the cap is checked): its identifier table takes 4-byte slots at most half full, so while it doubles, old and new slots take 24 bytes per identifier, for at least 19 payload bytes each (`{"identifier":"x"},`); the slots of 100,000 identifiers are 1 MiB (below the reuse threshold). Next to it at most one decoded copy of an escaped string (freed before the next insert, so never next to a doubling) and, under `.reject`, the identifier of a recorded duplicate. The worst small case is two escaped one-byte identifiers (`[{"identifier":"\/"},{"identifier":"\/"}]`-like, 42 bytes): a 48-byte table and a 48-byte copy, 2.3×; the ratio falls as identifiers accumulate. Measured at scale: 100,000 identifier-only elements, 0.75× peak; every rejected limit case at most 0.06×.
- **The exact bound.** For any payload of P bytes and any options, the heap the decode adds (as `malloc_zone_statistics` counts it, whatever the process freed before) is at most 3.75 × P in the build pass and at most 2.3 × P in the survey, on this host's allocator (macOS 27). **One exception, not proportional to any input:** the first decode in a process instantiates CryptoKit's SHA-256 state and Swift runtime metadata for the decoder's generic types once (1,392 bytes measured in a test process: a one-entry manifest retained 1,584 bytes on its first decode and 192 bytes on every later one); the tests decode once before measuring. **Not verified:** iOS devices' allocators (A-5); the model assumes their large-block reuse is no worse than twice the request, as on macOS 27.
- **Consequences.** Measured (debug, `R-MAN-3: seeded fuzz …`, retained = peak; A-15): minimal entries of 16-byte strings padded to the cap 3.74×; the verifier's shapes padded to the cap 2.77× (one component and one tag), 3.16× (three components), 3.11× (60,000 entries of 16-byte strings with three components); 100,000 minimal entries 2.08×; the size-class shapes 3.43× and 3.23×; realistic dense 32 MiB 1.31×. Small payloads, exact (`R-MAN-3: a small payload's decoded form …`): 22 shapes from 3 bytes to 15 KB, at most 3.67× (1,300 × `{}` keeps 256 diagnostics, 14,336 bytes for 3,901), one realistic entry 2.59×; each equals the estimate to the byte. **What is rejected now:** the cost of counting reuse falls on entry-dense manifests whose arrays exceed 2 MiB (more than about 14,500 entries): at 100,000 entries an entry must average about 111 payload bytes when all its strings are inline (minimal entries are 81: 100,000 of them were accepted at 8.1 MB and now need padding to 11.1 MB), 162 bytes with 16-byte identifier, path and file name. A catalog entry is 250–350 bytes (P-3's reference averages 328), so no realistic manifest comes near. Below that size minimal entries decode at 2.3–2.8×. Rejected at any size: payloads made mostly of 16–18-byte strings in arrays (a 64-byte block and a 16-byte slot for 19–21 payload bytes; 20-byte components fit), and one entry whose 32 path components are a byte each (832 bytes for 219, 3.8×; with three-byte components it fits).
