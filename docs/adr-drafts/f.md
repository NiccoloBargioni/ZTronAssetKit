## F-1 — One state value, owned tasks keyed by spawn id, token-keyed joins
- **Context.** ARCHITECTURE §7 and ADR-039/042: every awaiting caller must be resumed exactly once (by its result, its own cancellation or shutdown), and shutdown must join everything it owns.
- **Options.** (a) Per-feature actors (a run actor, a dispatcher actor); (b) one actor whose mutable state is one value (`EngineState`), with owned tasks and continuations in keyed tables.
- **Decision.** (b). `SyncEngine` keeps `var state: EngineState`; every owned task is spawned through `spawn(_:_:)` under a unique key and removes itself through `taskEnded` (shutdown cancels and joins them all); every suspended caller (waiters, unknown-id waiters, start/sync/entry joiners, groups, condition waits, run completions) sits in a table keyed by an `InterestToken` and is resumed only by `removeValue(forKey:)?.resume(...)`, so a second resume is impossible by construction. Cancellation handlers hop to the actor and withdraw only their own token. Overlapping access to `self.state` (Swift exclusivity) is avoided by computing into locals and writing back once, never by reading `state` inside a closure that mutates it.
- **Consequences.** No `@unchecked Sendable`, no locks (`UNSAFE escapes found=0`). `invariantViolations()` checks the cross-table invariants (waiter ⇒ interest, job ⇒ interest, downloading ⇔ active attempt, group member ⇒ interest, running ≤ maximum, lane-queue and subscriber-order bounds, no illegal transition, no stranded pending run); the 10,000-operation model test (`R-SYN-2`) checks them after every operation and `R-SYN-12: the invariant check reports every broken engine invariant it guards` proves the oracle is not vacuous.

## F-2 — The planner mirrors `apply`, and the space verdict is pure
- **Decision.** `PlanBuilder.plan` is a pure function of (manifest, planning view, scope, policy, free space): relocations are metadata-changed ids that have records; prunes are removed ids with records; a reuse needs the content among live blobs and a record that accepts adoption (never `absent(.evicted)`); held back are `failedUntilEntryChanges` and integrity quarantines; ineligible are out-of-scope, on-demand (unless the scope is explicit) and unverified entries the policy refuses. Fetch order is `(policy rank, manifest index)`. Space: zero bytes always fits; `room = min(volumeOpportunistic − reserve + pendingReclaim, max(0, budget − (used − pruneBytes)))`; a shortfall is `needsEviction(shortfall)` when eviction is permitted, else the largest fitting prefix (`partial`), else `insufficient(required: need + reserve, available: volumeOpportunistic)`. Sums saturate. A user-lane plan (`ensureAvailable`) plans against `volumeImportant` (sync-2 S2-23).
- **Consequences.** Planning runs off the actor (`@concurrent nonisolated static func planOffActor`, C2). P-4: 10,000 entries in 11.3 ms (budget 20), ratio 2.02 at 20,000 (max 2.5). When eviction cannot free the shortfall the engine replans with eviction not permitted, so an over-budget catalog still syncs its prefix (`R-SYN-11: a catalog larger than the budget syncs its largest fitting prefix essential-first and stays due`, which also shows the stamp is not written).

## F-3 — Run settling and pending runs (with a race fixed in this level)
- **Decision.** A run settles `finished` when every planned fetch ended, or `blocked(reason)` when every outstanding job is blocked or offline (`awaitingSpace` never settles a run). A blocked run drops its interests and leaves one pending run whose gate is the reason: conditions (debounced by `pendingRunDebounce`), breaker (cooldown deadline or close) or throttle (its end). `fulfilPendingRun` starts it only while no run exists.
- **Finding (test first).** The alarm that opens a gate can run before the blocked run's own task has finished it (both wait for the actor); `fulfilPendingRun` then found the run in place and returned, the deadline was consumed, and the pending run was stranded until the next explicit sync. Failing test `R-SYN-6: a pending run whose gate opens while the blocked run is still finishing starts once it has finished` (500 iterations with no debounce; failed 5 of 6 runs before the fix), committed before the fix together with the `strandedPendingRun` invariant. Fix: `reconsiderPendingRun()` after every run finishes and after every breaker record: an open gate starts the run, an unarmed one is re-armed (debounce, breaker deadline, throttle deadline, watcher).
- **Consequences.** The model test now also catches a stranded pending run. A breaker whose probe ended without a verdict (`halfOpen(probe: nil)`) lets the pending run probe.

## F-4 — The breaker half-opens lazily; manifest fetches are gated too
- **Decision.** `CircuitBreaker` is a pure value per origin: the 5xx cooldown is exact (`30 s · 2^(trips−1)` to 600 s), the auth cooldown is jittered to `[0.5c, c]` with keyed randomness (ADR-024); the open → half-open transition happens in `admit` (the first transfer admitted after the cooldown is the probe, with a watchdog), and the alarm's breaker deadline only unblocks jobs and fulfils the pending run. A manifest fetch goes through the same breaker and the origin throttle; a fetch that trips the breaker (a key-rejected 403) ends the run `blocked(.circuitOpen)` with a pending run, and a run started while the breaker is open asks for nothing (`R-SYN-5: a run started while the breaker is open ends blocked without asking for the manifest`).
- **Consequences.** `circuitChanged(.halfOpen)` is published when the probe is admitted, not at the cooldown's end. A transfer probe's admission was applied without being published (failing test first: `R-SYN-5: a transfer that probes after the cooldown publishes the half-open breaker before it closes`); it now goes through `breakerChanged` like a manifest probe's. Breaker events share one coalescing slot per origin (R-SYN-12), so a subscriber that pulls late may see `closed` without the `halfOpen` before it.

## F-5 — Store deadlines after a publication (F-12 of the level-3 notes)
- **Context.** `store.nextDeadline()` scans the blob table, so calling it after every publication made a bulk sync O(n²) (the 10,000-asset stalled-subscriber test took minutes).
- **Decision.** `refreshStoreDeadlineAfterPublish` skips the read when the alarm already wakes for the store within two snapshot-install intervals; `runDueWork()`'s report re-arms from the newest deadline then. Every other path (apply, purge, maintenance, launch) reads it.
- **Consequences.** A publication only ever adds work due within the store's coalescing windows, so nothing is missed; the 10,000-asset test runs in seconds.

## F-6 — Unknown identifiers: one point fetch per refetch interval, never a wrong notFound
- **Decision.** An identifier absent from the applied manifest joins (or starts) one manifest fetch; the fetched manifest's entry is admitted (`store.admit`, no ETag stored, sync-2 S2-28) and fetched without a run; an identifier the fresh manifest does not list is cached as unknown for `unknownIDRefetchInterval` (bounded LRU of `unknownIDCacheCapacity`). An unusable manifest answers `serverUnavailable`, a throttle `serverUnavailable(retryAfter:)`, an open breaker its cause.
- **Consequences.** `R-CAR-2: misspelt identifiers trigger at most one manifest fetch per refetch interval`; `R-CAR-2: an identifier a fresh manifest lists is admitted and fetched without a run`. B-30 holds the other way: the engine never skips `apply` on digest equality, so the admitted digest (which no fetched manifest can match) only ever causes an apply that would have happened anyway.

## F-7 — Launch reconciliation and staging claims (C-9)
- **Decision.** `TransferReconciler.plan` (pure, sorted by name): attach the newest running task of a wanted transfer, cancel the others; adopt the newest completed staged file of a wanted transfer; resume the newest partial that has a sidecar; discard everything else. Staging GC at launch and in maintenance is passed every transfer the engine still works on: jobs (those verifying or committing, i.e. with a publication in flight, included), draining attempts and launch resumes.
- **Consequences.** `R-CLN-3: staging GC during maintenance keeps the file of a publication in flight, however old` (the claimed file is aged past `stagingClaimGrace`; with the claims removed the test fails with a second download, checked by hand in this session).

## F-8 — Legacy migration loop (R9, RE-S29)
- **Decision.** After `open()` reports `legacyMigrationPending`, one owned task calls `migrateLegacy(maxFiles: 64)` while the engine runs and `!finished`; a call that leaves `remaining == 0 && !finished` (phase 4 could not finish, or phase 3 was interrupted) defers to the next maintenance window, which restarts the loop; a throwing call defers likewise. The launch run waits for the loop (it would otherwise download what migration is about to adopt). A resolve or lease of a legacy id not yet adopted calls `adoptLegacyNow` first.
- **Consequences.** `R-STO-11: the launch run waits for legacy migration and downloads nothing it adopted`; `R-STO-11: a resolve during migration adopts that legacy file first and never waits for the whole catalog` (the migration is held at its first file throughout).

## F-9 — Apple-tier gating on the engine's own conditions (E-17) and the engine half of R-NET-8
- **Decision.** Apple-tier transfers and update-checking manifest fetches wait for the engine's first `DeviceConditions` and start only when the lane's `NetworkAccess` admits them (the HTTP tier attempts and reports offline itself). A refused or invalid resume (`resumeRejected`) discards the partial and its sidecar, and the next attempt starts from zero; after a resumed attempt ends, the earlier attempt's sidecar is discarded too (found by `R-STO-1: a cancelled, paused or failed foreground transfer leaves no byte outside the store root`, failing test first).
- **Consequences.** Tests: `R-SYN-7: Apple-tier transfers and update-checking manifest fetches start only when the engine's DeviceConditions satisfy their NetworkAccess`, `R-NET-8: a refused or invalid resume discards the partial and restarts from zero in the next attempt`, `R-NET-8: an invalid resume yields resumeRejected and the engine's next attempt starts fresh`.

## F-10 — An engine without a remote source fails fetches at once
- **Context.** When `makeRemoteSource` throws, the engine still serves what is present, but a waiter for an absent asset hung (failing test first, commit `12124e8`).
- **Decision.** The construction error is kept; runs and fetches of absent assets fail with it at once (`missingSourceError`); resolves of present assets still succeed.

## F-11 — Log lines carry no identifiers or error details (R-OBS-1)
- **Decision.** Engine log lines name the failure class and a hashed identifier (`AssetLog.hashed`), never an asset id, a URL or an error's payload; details go to the diagnostics ring (32 entries, oldest dropped, `R-OBS-3: the diagnostics keep the last 32 errors`). The package-wide R-OBS-1 scan found the earlier interpolations.

## F-12 — Benchmarks (P-4, P-7, P-11, P-14)
- **Decision.** Thresholds from `QualityBudgets` only. P-4: median of 21 plans after 3 warm-ups at 10,000 and 20,000 entries with 10 % churn. P-7: a synthetic catalog streamed by `stageGenerated` into real files under `.build-tests/` with the resident size sampled at every transfer start; a quarter catalog first, so "does not grow with catalog size" compares two deltas. P-11: the real HTTP source against the loopback server with real latency, concurrency 1 against the configured concurrency (benchmarks may sleep, sync-2 S2-14); the timed sync starts after `start()`, so it includes the part of the launch run that overlaps it. P-14: a sync driven to quiescence on `ManualTimeSource`, then the census.
- **Consequences.** Release measurements in this level: P-4 11.32 ms (budget 20.0), ratio 2.02 (max 2.5); P-7 4.6 MiB for 256 MiB and 0.5 MiB for 1,024 MiB (max 48.0); P-11 speedup 3.73 (min 3.0); P-14 0 timers, 0 tasks.

## F-13 — Test harness: drive the clock without timing out a fetch
- **Decision.** `EngineHarness.drive` advances the manual clock only to the next sleeper and otherwise waits for an engine change or a new sleeper (never wall time); `syncDriven` bounds each step to half the manifest fetch deadline, because `sync` joins the launch run, whose fetch may still be in flight when the driver starts (under parallel load a jump to the deadline turned the run into a "timed out, applied manifest" run). Tests that wait for conditions events wait for the engine's state (the armed debounce), not for a replayed event.

## F-14 — Not verified
- **OI-2.** `FakeFileSystem`'s barrier equals a full sync, so the engine's durability-ordering claims (a publication is acknowledged only after the store's commit; reconcile is committed before the first transfer) are verified against that model only, not against a device's `F_BARRIERFSYNC` behaviour.
- Device-only behaviour: real background `URLSession` relaunches, real On-Demand Resources packs (R-APL-3 runs end to end through the engine, the store and `AppleHostedRemoteSource` over WP-F's `FakePackBackend` since the close-out, F-21; a real Apple-hosted pack is not exercised), real `NWPathMonitor`, thermal and Low Power Mode signals; the engine's handling of each is tested through fakes.
- P-11 includes part of the launch run (F-12); its speedup is a lower bound of the steady-state one.

## F-15 — A run whose manifest fetch timed out writes no stamp (fix round 1; needs a ruling)
- **Context.** Verifier finding: a run whose fetch passed `manifestFetchDeadline` ran on the applied manifest, ended `.complete` and wrote the stamp, so under `.oncePerAppVersion` a slow-network launch of a new version marked the version synced without fetching its manifest.
- **Options.** (a) Keep stamping; (b) end `.completeWithFailures` (with no failure listed); (c) end `.complete` with `manifestFresh == false` and write no stamp (and leave `syncedThisLaunch` false).
- **Decision.** (c): the outcome still says what happened (the applied manifest is complete locally, `report.manifestFresh` says it was not refreshed), and the sync stays due under every policy, so the next due check fetches again. ARCHITECTURE §7.10's "markSynced only for `.complete`" now reads "only for a `.complete` run with a fresh manifest".
- **Consequences.** `R-SYN-6: a manifest fetch past its deadline falls back to the applied manifest and leaves the sync due` (a second lifetime of a new app version; `isSyncDue()` stays true).

## F-16 — Offline runs retry once on the debounce, then wait for a network edge (R-SYN-13; fix round 1)
- **Context.** Verifier PROBE-7: a run that ends offline while the engine's conditions read the path satisfied (URLSession says -1009/-1018/-1020 under some VPN or roaming paths) set a conditions-gated pending run that bulk admission scheduled after `pendingRunDebounce`; the next run failed the same way, for ever: one manifest request per debounce with no conditions change (10 requests over 10 timer cycles).
- **Options.** (a) Open the conditions gate only on a satisfied-path edge after any offline failure; (b) back off pending-run retries exponentially (still a poll, every 300 s at most); (c) one debounced retry, then edge-only.
- **Decision.** (c). `EngineState.offlineRunsWithoutEdge` counts runs in a row that ended offline (reset by a satisfied-path edge and by any run that ends otherwise); the first is retried after the debounce once conditions admit bulk work (a path monitor often reports satisfied a moment before connections work, or its first element was not in yet); a later one that ends while the path reads satisfied sets `PendingRun.awaitsNetworkEdge`, which `considerPendingRun` and the gate state honour until `apply(conditions)` sees an edge. (a) alone broke `R-SYN-6: a pending run whose gate opens while the blocked run is still finishing starts once it has finished`, whose single offline failure must still be retried.
- **Consequences.** At most one automatic retry without an edge, then no timer at all (`R-SYN-13: runs that keep failing offline while the path reads satisfied run again only after a network edge, never on a timer`, failing first: the old code scheduled the debounce again). The pending run keeps the conditions watcher (work), so an edge is seen.

## F-17 — Two test budgets (fix round 1)
- **Decision.** `R-SYN-12: a stalled subscriber's backlog never exceeds one slot per progress key and subject during a 10,000-asset sync` gets `.timeLimit(.minutes(3))`: 9.5 s on macOS, but 58.4 s under the thread sanitizer and 35.8 to 57.3 s on the iOS Simulator under load (an overrun restarts the runner, `ios.md` item 8); no assertion changed. `R-STO-1: a cancelled, paused or failed foreground transfer leaves no byte outside the store root` compares the `CFNetworkDownload_*` files created since the test began whose leading bytes are a run of one of the test's bodies, instead of the process-wide count, which other suites running in parallel on the simulator disturb; an empty file holds no byte, so the requirement checked is unchanged.
- **Close-out cycle 1 (L4-R8; L4-V3-03, L4-V3-15).** The verifier measured the 10,000-asset test in the full sanitizer suite at 115.3 s (load average about 15 to 25) and 151.0 s (load rising to 73), against 180 s. This cycle cut its cost (F-21: one slot pass per `pump` round, `checkRunSettled` stops at the first working claim, the backlog read from the queue's high-water mark instead of a sampler after every mutation) and raised the limit to `.minutes(4)` (240 s). Measured on this host after the change (the sanitizer build of `ZTronAssetSyncTests`): alone 15.1 s at load average 2 to 3 (17.8 s before the change, same host and load); in the whole package's sanitizer suite 17.5 s at load 3.8 to 11 (each test bundle runs in its own process, one after another, so "in-suite" means alongside the other 213 Sync tests); in the Sync sanitizer suite run beside this WP's own iOS Simulator test run, 72.5 s at load average 79 to 141 (median 119), 30 % of the new limit; 0 ThreadSanitizer reports in every run. A load around 25 was not produced on purpose; at about five times that load the test used 30 % of its limit, which bounds its time at a load around 25 from above (an inference from the measurements, not a measurement at 25). On the iOS 27 Simulator it took 8.6 s (load average 12 to 65); debug alone 3.8 to 3.9 s. `R-SYN-6: a pending run whose gate opens while the blocked run is still finishing starts once it has finished` now takes 1.4 to 1.5 s under the sanitizer in-suite (two cases; 55.9 s and a time-limit overrun before) and keeps its 1-minute limit.

## F-18 — Fix round 1: engine findings (each with a failing test first)
- **Stale drain (PROBE-1).** `ActiveAttempt.terminalReceived` is set when `finishAttempt` consumes the terminal element (and from the start for the publication of a drained file, which has no stream). `retire` and `applied` record a drain (`DrainingAttempt`, with its driver's key) only for an attempt whose stream is still open; `publish` discards the file when its job was retired before it began. Test: `R-SYN-4: a resolve cancelled while its failed attempt is handled leaves no stale drain, so the next resolve downloads`. New invariant: a drain whose driver ended.
- **Run claims (PROBE-2).** `reroute(_:interest:asset:from:)` releases the run's claim on the old transfer (`releaseRunClaim`), for supersession, a partial move in `applied` and an unbound commit; an asset that left the manifest drops a group member (an `ensureAvailable` group completes) and forgets a heal. `checkRunSettled` treats a claim on a job that lost the run's interest as failed (`.cancelled`), so a missed release can never strand the run. Tests: `R-SYN-6: a run whose job is superseded while it publishes still settles once its asset's new content commits`; `R-SYN-4: a waiter whose asset changed content while its shared job published follows the new content` (the same audit found that `committed` answered such a waiter `.notFound` and counted the run's asset as failed before rerouting it). New invariant: a run claim on a job without the run's interest.
- **`ensureAvailable`'s apply (PROBE-3).** It now calls the run's `applied(_:etag:report:)` (generation, `assetRemoved(.pruned)`, `snapshotChanged`, T21/T22 on jobs) as soon as the store committed, whatever the caller does next, then re-reads the store deadline (RE-S40). Test: `R-SYN-10: ensureAvailable's apply announces pruned ids and stops their jobs, as a run's apply does`.
- **Scope during start (PROBE-4).** See f-1. Test: `R-CAR-5: a retention scope set while start is in progress reaches the store`.
- **Cancelled start joiner (PROBE-5).** `ensureStarted` answers `.cancelled` while start still runs. Test: `R-SYN-15: a caller cancelled while start runs gets cancelled, never shutDown`.
- **S1-13 (PROBE-6).** A fetched manifest removes the ids it lists from the negative cache, and an id the newest manifest lists is point-admitted, never answered from the cache. Test: `R-CAR-2: an identifier a run's fetched manifest lists is never answered notFound before the run applies it`.
- **Joiners of parked jobs (PROBE-8).** `addInterest` applies the fail-fast policy to a new interest in a job that stays `blocked(reason)` (or `failed(.whenOnline)`, as `.offline`), so it gets the answer a new job would get. Test: `R-SYN-4: a resolve that joins a job blocked for lack of space is answered at once, as a new job would be`.
- **Also.** RE-S36/RE-S20 lifecycle re-checks after `store.location` and the unreachable branch's `availability`; launch reconciliation's wanted set is computed off the actor (`wantedTransfers`, C2); maintenance announces what deep verification quarantined (`assetRemoved(.quarantined)`, as `reportUnreadable` does); start and sync joiners wake `awaitCondition` waits when they register.

## F-20 — Fix round 2: engine findings (each with a failing test first) and the round's other changes
- **Context.** The round-2 verifiers (correctness and requirements lenses) found nine blocking engine defects and several non-blocking ones; each blocking one came with a probe. - **The engine follows the store's manifest (PROBE-R2-A, S1-13/T22).** A publication the store answers `.superseded` while the engine's copy of the applied manifest still names that content (a store `apply` whose await has not returned, or one the engine never saw) no longer answers `.notFound`: the interests wait on a fresh, *held* job of the content (`heldForManifest`, never dispatched) until the copy catches up, either when the `apply` in flight returns (`applyAndFollow`, which counts in-flight applies) or, when none is in flight, by a re-read of the store (`catchUpWithStore`, REENTRANCY f-9); then `followApplied` moves them (T22) and the last catch-up releases the held jobs (T11 for any the copy still maps there). ## F-21 — Close-out cycle 1: round-3 findings, each with a failing test first, and the rulings applied
- **Context.** Verification round 3 of the main run left 17 findings (L4-V3-00…16, 8 blocking) and the orchestrator ruled on them (L4-R1…R15, above). Every defect below has a regression test committed before its fix (CLAUDE.md P3); every test is gated per `@Test` for both platforms (ADR-051).
- **Present assets get no job (L4-V3-07, L4-V3-08, F-19; L4-R5).** *Options.* (a) A presence read (an await) before each job is created: impossible where jobs are created, inside the synchronous `pump`/materialisation/reroute turns. (b) A "bound since the plan" set per run and per `ensureAvailable` group: covers materialisation only, not the reroutes of T22 nor joins. (c) One engine-side ledger of the bindings the engine learns, consulted wherever an interest would create or join a job. *Decision:* (c). `EngineState.boundContent` maps an id to the transfer whose content the store bound it to. It is fed by a commit's locations (`committed`), an apply's reuses (`applied`), and the store reads the engine already makes (a resolve's planning view, a point admission's view, a catch-up's view, a 404's location reads). An entry goes when the engine learns the binding ended or may have: an apply's prunes, evictions and content changes, a purge (at its start and when the store returns), maintenance (at its start and after its eviction step), a quarantine, a recorded integrity failure or 404, a store read that finds nothing, a catch-up's view that no longer shows it present. It is consulted by `materializeRun` (the run counts the asset as fetched), `materializeEnsures` (the member is done), `reroute` (a waiter is answered by a store read, a group drops the member, a run counts it as fetched, a heal is forgotten), `joinGroup` (skipped), a resolve's registration and a point admission's join (answered by a store read), and a heal (forgotten). A waiter answered from the store (`Waiter.fromStore`) holds no interest; an owned task reads `store.location` (RE-S36) and, when the read finds nothing (the binding ended meanwhile), puts it on the job path. *Lifetime:* the ledger is kept whole while a run exists (its plan is a snapshot), while an `ensureAvailable` group has fetches left to materialise, and while a store read whose answer registers an interest is in flight (`presenceReaders`: a resolve from its first read to its registration, a prefetch join, a point admission, `ensureAvailable` until its group exists); otherwise `reconcileIdle` trims it to the ids of jobs (`pruneBoundContent`). It therefore scales with outstanding work and a plan in progress, never with the catalog. *Deviation from the ruling's feed list:* an apply's `relocated` ids are not fed, because `AssetStore+Apply` relocates absent records too (`diff.metadataChanged`): feeding them would make a run skip fetching an absent asset. A relocation keeps the content (and so the transfer), so no job moves for it and nothing is downloaded twice. *Defence in depth (404):* before `recordFailure`, one `store.location` read per id of the job (f-10; O(1) each, where a planning view would scan the blob table on the store's actor, C2): an id the store serves at its current content while the engine's copy maps it to the failed content is answered from the store and left out of the failure; the failure is recorded for the job's other ids even when the job ended during the reads (ADR-032). *Store guard not added:* applied temporarily in this worktree (`record.referencedBlob == nil || record.isStale` in `AssetStore.recordFailure`'s guard), it fails WP-C's pre-existing `R-CLN-4: bytes a quarantine or a recorded failure dooms while quota eviction computes its candidates count toward its need`, case `failure` (EvictionOverlapTests.swift:213, :216, :218): that test records a 404 for a present record and expects its blob doomed. The ruling authorises the guard and a new store test, not a change to WP-C's test, so the guard was reverted. The remaining window is one await between a location read and `recordFailure`'s write, in which only a legacy adoption (`migrateLegacy`, `adoptLegacyNow`) or an apply's adoption of an orphaned blob of the same content can bind the id: the job is that content's only download (ADR-020). **Question for the orchestrator:** rule whether WP-C's test case may target a stale record instead, so the guard can go in. *Tests (all five failed first, `3fc568d`; fixes `bf46fad`, `3de75ec`):* `R-SYN-4: a waiter whose asset an apply binds to content already present is answered from the store and downloads nothing` (PROBE-R3-3), `R-NET-6: a 404 for content an apply already bound never fails the asset that holds it` (PROBE-R3-3b), `R-SYN-10: ensureAvailable does not download a member another interest committed after its plan` (PROBE-R3-2), `R-SYN-6: a run does not download an asset another interest committed after its plan, and counts it as fetched` (F-19, closed), `R-NET-6: a 404 never marks failed an asset the store bound to that content while the transfer ran` (the presence re-check). The resolve and prefetch-join windows (a commit the engine processes between a store read and the registration) have no deterministic probe with the fakes (the reads have no executor unit to hold); they use the same ledger check. *Accepted residue (L4-R5, Stage 3 with OI-15):* the late joiner of shared content (L4-V3-12, "G") still downloads it a second time.
- **Space and staging (L4-V3-09, L4-V3-10; L4-R6).** `ensureAvailable` plans against important capacity but its measured read is the ledger's base; an attempt that fails with ENOSPC goes through `resumePoint(after:)` (a sidecar keeps the partial for resume, anything else is discarded) before the free-space decision. Tests (failed first, `22a6aa0`; fix `439a8ac`): `R-SYN-11: ensureAvailable's plan against important capacity never admits a prefetch parked for opportunistic space` (PROBE-R3-1), `R-CLN-3: an attempt that fails for lack of space leaves no partial without a sidecar in staging` (PROBE-R3-4).
- **Catch-up announces what it follows (L4-V3-14; L4-R7, L4-R10).** Reproduced with a store `apply` the engine did not make (what an `apply` that throws after its in-memory writes leaves): the engine followed the store's manifest but never announced the prune. `catchUpWithStore` now publishes `assetRemoved(.pruned)` for the ids its copy lists and the view does not (in the copy's order), takes the view's generation and publishes `snapshotChanged`, then follows (T21/T22). The engine's ETag is kept (the view carries none). Test (failed first, `2c88268`; fix `cc2e3d6`): `R-SYN-10: a catch-up with the store's manifest announces the ids it pruned and the store's generation`.
